# 스킬 작성 형식

이 저장소의 모든 스킬 문서(SKILL.md, `references/`, `playbooks/`)는 just 문체 하나로 쓴다. 설치와 검사 절차는 [skill-sync](../SKILL.md)가 맡는다.

## 적용 범위

- 분류(git, code, docs, design, tools, just)와 관계없이 새 스킬과 기존 스킬에 모두 적용한다. 분류나 출처에 따른 예외는 없다.
- 사용자 지시가 먼저다. 사용자 지시가 없으면 작업 대상 저장소의 같은 주제 규칙 파일(`AGENTS.md`, `CONTRIBUTING.md` 등)을 따르고, 그것도 없으면 스킬을 따른다. 이 순서는 여기에만 적고 스킬마다 되풀이하지 않는다.
- 템플릿 코드 블록과 인라인 코드 안의 예시는 산출물에 그대로 나올 글자다. 문체 규칙을 적용하지 않는다.
- 커밋 본문, PR 본문, 이슈 댓글처럼 스킬이 만드는 산출물의 끝말은 그 스킬의 템플릿이 정한다. 스킬 문장의 문체와 섞지 않는다.

## frontmatter

```yaml
---
name: git-commit
description: "Git 커밋 메시지를 쓰거나 검토할 때, 변경을 나눠 커밋할 때 쓴다."
---
```

- `name`은 폴더 이름과 같고 영어 소문자, 숫자, `-`만 쓴다.
- `description`은 큰따옴표로 감싼 한 줄이고 1024자를 넘지 않는다. 한국어 문장 하나 이상으로 쓰고 마침표로 끝낸다.
- 언제 쓰는지 말하는 문장은 `~할 때 쓴다.`나 `~에 쓴다.`로 끝낸다. 무엇을 하는지 설명하는 문장을 그 앞이나 뒤에 더해도 된다.
- 헷갈리기 쉬운 이웃 스킬이 있으면 description 끝에 한 문장으로 가른다(`동기는 why를 쓴다.`).
- description은 늘 올라가는 카탈로그라 짧게 쓴다. 본문은 스킬을 쓸 때만 올라가므로 규칙을 빠짐없이 쓴다.
- frontmatter에는 `name`, `description`, `disable-model-invocation`, `user-invocable` 네 칸만 둔다.

호출 칸은 스킬이 불리는 방식으로 고른다.

| 종류 | 예 | 호출 칸 |
|---|---|---|
| 자동 호출형. 모델이 description을 보고 고른다 | git-commit, code-style, just-setup | 두 칸 모두 쓰지 않는다 |
| 명시 호출형과 입구. 사용자가 `/이름`이나 `$이름`으로 부를 때만 쓴다 | just-mode, how, unslop | `disable-model-invocation: true` |
| 내부 참조형. 다른 스킬이나 훅이 경로로 읽고 메뉴에 보이지 않는다 | principle-* | `disable-model-invocation: true`, `user-invocable: false` |

- `user-invocable: false`는 `disable-model-invocation: true`와 함께만 쓴다.
- `disable-model-invocation: true`인 스킬은 `agents/openai.yaml`에 `policy` 아래 `allow_implicit_invocation: false`를 둔다. 그래야 Claude Code와 Codex가 같은 방식으로 부른다. 자동 호출형은 이 줄을 두지 않는다.
- `agents/openai.yaml`에는 `interface` 아래 `display_name`, `short_description`, `default_prompt`를 두고, `default_prompt`는 `$이름`으로 스킬을 부른다.

## 본문 구조

본문은 다음 순서로 쓴다. 3번과 5번, 6번은 필요할 때만 둔다.

1. `# 제목`. 문서마다 하나만 둔다.
2. 한 줄 목표 문단. 이 스킬이 무엇을 끝내는지 한두 문장으로 쓴다. 제목 바로 다음에 두고 목록, 표, 제목을 그 자리에 두지 않는다.
3. `## 언제 쓰나`, `## 쓰지 않을 때`. description만으로 가를 수 없는 조건이 있을 때 쓴다.
4. 단계나 규칙. 순서가 있으면 `## 단계` 아래 `1.` 번호 목록으로 쓰고, 단계마다 설명이 길면 `## 1. 단계 이름` 절로 나눈다. 순서가 없는 규칙은 주제별 `##` 절 아래 `-` 목록으로 쓴다. 어기면 안 되는 금지를 모을 때는 `## 하지 않는 것` 절을 쓴다.
5. `## 답변`. 사용자에게 돌려줄 항목을 적는다. 산출물 틀은 `## 형식` 절에 두거나 `references/` 파일로 뺀다.
6. `## 구분`. 비슷한 스킬과 무엇이 다른지, 이 스킬이 맡지 않는 일은 어느 스킬이 맡는지 적는다.

```markdown
---
name: example
description: "예시 작업을 할 때 쓴다."
---

# 예시

입력을 확인하고 결과 파일을 만든다.

## 단계

1. 입력 경로를 확인한다.
2. 결과 파일을 쓴다.

## 답변

- 만든 파일 경로를 적는다.

## 구분

- 결과를 검토하는 일은 **example-review** 스킬이 맡는다.
```

## 문장

- 서술문으로 쓴다(`~한다`, `~다`). 목록 항목도 서술문이다. `커밋 분리`, `작성 표시 금지`처럼 명사로 끝나는 개조식 줄을 쓰지 않는다.
- 한 문장에 생각 하나를 담는다. 문장은 짧게 쓴다.
- 금지는 `~하지 않는다`로, 꼭 해야 하는 일은 `반드시 ~한다`로 쓴다.
- 번역투와 AI 티는 **unslop** 스킬의 패턴으로 지운다. 특히 채우기 구절(23번), 수동태(29번), 어려운 말(31번), 지나친 압축(33번)을 본다. 화살표(`→`)로 문장을 대신하지 않는다.
- 엠 대시(`—`)를 쓰지 않는다. 문장을 끊어야 하면 마침표나 쉼표를 쓴다.
- 문장 중간에 콜론을 쓰지 않는다. 목록이나 예 앞의 콜론은 괜찮다.
- 굵은 머리말은 마침표로 끝낸다(`**검증.** 결과를 직접 확인한다.`). `**검증:**`처럼 콜론을 쓰지 않는다.
- 굵게는 용어를 정의할 때, 어기면 안 되는 경고, 스킬 이름을 가리킬 때(`**git-issue** 스킬`)만 쓴다.
- 표는 비교와 대응(고르는 표, 대응표)에만 쓴다. 순서가 있는 지시는 번호 목록으로, 조건별 지시는 목록으로 쓴다.

## Markdown 문법

- 제목 단계를 건너뛰지 않는다. 한 문서에 같은 `##` 절 이름을 두 번 쓰지 않는다.
- 목록 기호는 `-`를 쓰고 번호 목록은 `1.`, `2.`처럼 실제 번호를 쓴다. `*`, `+`, `1)`을 쓰지 않는다.
- 코드 울타리에는 언어를 적는다(`sh`, `text`, `json`, `yaml`, `python`, `markdown`). 명령 앞에 `$`를 붙이지 않는다.
- 저장소 안 링크는 상대 경로로 쓴다. 절대 경로와 `file://`을 쓰지 않는다.
- 줄 끝에 공백을 남기지 않는다. 블록 사이에는 빈 줄 하나를 둔다. 문단은 한 줄로 쓴다.

## 다른 스킬과 하위 문서 잇기

- 다른 스킬이 맡는 일은 다시 쓰지 않고 그 스킬로 보낸다. 규칙마다 정본은 하나다. 공통 규칙은 공통 스킬에 두고, 종류별·언어별 스킬에는 그 종류에만 있는 규칙과 템플릿만 둔다.
- 같은 분류(같은 상위 폴더)의 스킬은 상대 링크로 건다. 본문에서는 `../{스킬}/SKILL.md#{절}`, 하위 문서에서는 `../../{스킬}/SKILL.md#{절}`로 쓴다.
- 다른 분류의 스킬은 이름으로 가리킨다(`**git-issue** 스킬의 닫기 절`). 설치본은 분류 폴더 없이 평탄해서, 분류를 넘는 상대 링크는 원본과 설치본 중 한쪽에서 깨진다.
- 다른 스킬의 하위 문서 하나만 필요하면 스킬 이름 뒤에 경로를 인라인 코드로 적는다(repo-docs `references/writing.md`). 그 문서만 읽고 SKILL.md 전체는 읽지 않는다. 경로는 이름으로 찾은 스킬 폴더를 기준으로 푼다.
- 상황별 내용은 `references/{역할}.md`로 빼고, 본문에는 언제 읽는지를 경로와 함께 쓴다(`커밋 메시지를 쓰기 전에 references/commit-template.txt를 읽는다`). 조건 없는 참고 링크로 의무를 대신하지 않는다.
- 같은 스킬 안에서는 본문에서 `references/{역할}.md`, 하위 문서끼리 `{역할}.md`, 하위 문서에서 본문으로 `../SKILL.md#{절}`을 쓴다.
- 매 작업에 쓰는 핵심 규칙, 필수 검사, 형식 정본은 본문에 둔다. 규칙을 하위 문서로 옮길 때 대상, 조건, 필수, 금지, 예외, 실패 처리를 빠뜨리지 않는다.
- 종류별 템플릿은 작성, 갱신, 검토할 종류의 것만 읽는다. 새 문서를 처음부터 쓸 때는 반드시 해당 템플릿을 읽는다.

## 실행 코드

- 실행 코드는 `scripts/`에, 산출물에 넣는 자원은 `assets/`에 둔다.
- 본문에는 실행 명령과 쓰는 조건을 적는다. 런타임, 버전, 의존성은 그 명령 옆에 적는다.
- Python은 표준 라이브러리를 먼저 쓴다. 외부 도구는 공식 명령과 패키지를 쓴다.
- CLI 스크립트 머리에는 `인자:`와 `출력:` 설명을 둔다. 형식은 [일관성 검사 기준](consistency.md#스크립트-형식)을 따른다.

## 용어

- 낱말 선택은 repo-docs `references/writing.md`의 용어 절을 따른다.
- `.local/decisions/<과업>.tsv`는 결정 기록이라 부른다. repo-docs-decision이 저장소에 남기는 ADR은 공개 결정 기록이라 부른다. 작업 일지나 진행 로그라고 부르지 않는다.
- 그림 도구의 제품 이름은 Torso다. `ThinkFlow`, `띵스플로우`라고 쓰지 않는다. 명령은 `torso`, 원본 확장자는 `.torso`, 마크다운 코드 블록의 언어 이름은 `torso`, 원본 첫 줄은 `torso`다. 저장소 링크는 `https://github.com/woonyong-choi/torso`를 쓴다.
- 범용 규칙에 특정 프로젝트, 제품, 회사, 글꼴 이름을 넣지 않는다. 실제 도구에 기대는 내용은 선택 어댑터 절에 두고, 실제 명령의 이름과 인자는 그대로 쓴다.

## 간결성

- 뜻이 같으면 가장 짧은 문장을 쓴다. 대상, 조건, 의무, 예외, 실패 처리, 근거는 줄이면서도 남긴다. 뜻이 흐려지는 축약은 하지 않는다.
- 결정을 바꾸지 않는 글은 지운다. 이유는 헷갈리기 쉬운 규칙에만 붙인다.
- 중복 설명과 상투어를 지우고 공통 규칙은 정본을 가리킨다. 규칙을 빼거나 기계적으로 나눠서 길이를 줄이지 않는다.
- 채울 사실이 없으면 지어내지 않고 빈 칸을 보고한다.

## 작성 표시

커밋, 작성자, 문서 어디에도 AI 작성 표시를 넣지 않는다. 표시 목록의 정본은 repo-docs `references/writing.md`의 문체 절이다. 공개 저장소 기록은 사용자의 것으로 남는다.

## 바꾼 뒤 확인

1. `python3 tools/skill-sync/scripts/skill_check.py .`를 돌리고 `total 0`이 될 때까지 고친다. 검사 항목과 한계는 [일관성 검사 기준](consistency.md)에 있다.
2. 검사는 문장 끝말과 개조식 여부를 보지 않는다. 문체는 사람이 읽고 확인한다.
3. 다른 스킬과 용어, 서로 가리키는 규칙, 금지 항목이 어긋나지 않는지 확인한다.
4. 하위 문서로 나눴으면 원본과 설치본 양쪽에서 링크와 앵커가 열리는지, Claude zip에 하위 문서가 들어가고 `SKILL.md`가 정확히 하나인지 확인한다.
5. 크기를 비교하는 표는 실제 스킬만 넣는다. UTF-8 SKILL.md 전체 바이트(frontmatter와 개행 포함)로 재고, 기준 커밋과 스킬별 전후, 합계를 적는다. 하위 문서를 포함한 작업별 읽기량은 본문 합계와 따로 적는다.

## 행동 검토

- 바꾸기 전에 요청, 근거, 실제 응답으로 무엇이 실패하는지 정한다. 비공개 대화를 공개 시험 자료로 옮기지 않는다.
- 바꾼 뒤에는 실패 사례, 쓰이지 않은 사례, 적용하지 않아야 하는 사례, 원래 잘 되던 사례를 대조한다. 기대, 관측, 미확인을 기록이나 응답에 적는다.
- 손으로 대조한 것, 실행한 것, 독립 평가를 나눠 적는다. 정답을 알려 준 실행이나 형식 통과로 행동이 나아졌다고 말하지 않는다.
- 기존 설정, 명령, 자료로 검토한다. 시험만을 위해 프로젝트 지침을 더하지 않는다.
- 승인 전 설치와 활성화를 막는 방식은 저장소 배포 정책이 정한다. 정책이 없으면 검토 전에 설치, 활성화, 기존 스킬 대체를 하지 않는다.
- 규칙은 그 규칙을 소유한 스킬 하나에 두고, 실행 순서와 스킬 고르기는 just-mode 하나가 맡는다. 하위 스킬이 입구를 다시 부르거나 절차를 복제하거나 중계 스킬을 더하지 않는다.

## 본보기

**git-commit** 스킬이 이 형식으로 처음 바꾼 본보기다. 제목, 목표 문단, 단계, 형식, 하지 않는 것, 답변, 구분 절의 쓰임을 그 파일에서 본다.
