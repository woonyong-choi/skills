# 테스트

근거가 있는 최소한의 테스트만 두고, 각 테스트를 자동으로 판정되게 쓴다.

## 고르기

- 커버리지나 테스트 개수를 목표로 삼지 않는다.
- 무엇을 단언할지, 기대값을 어디서 가져올지, 언제 지울지는 **principle-test-behavior-not-implementation** 스킬을 따른다. 실패 테스트와 수정의 커밋 순서는 **principle-sequence-verifiable-units** 스킬을 따른다.
- 테스트마다 근거가 하나 이상 반드시 있어야 한다. 근거는 설계 문서 요구사항 표의 행, 재현된 버그의 이슈 번호, 공개 계약(입출력 형식, 호환, CLI), 지켜야 하는 규칙(접근성 대비 등) 중 하나다. 근거 없이 테스트를 더하지 않는다.
- 새 테스트를 더하기 전에 기존 검사 실행, 기존 테스트 수정, 입력 추가를 먼저 검토한다. 새 테스트는 기존 검사로 잡지 못하는 회귀 위험에만 최소한으로 더하고 이유를 보고한다.
- 근거가 있는지와 테스트가 실제로 무엇을 검증하는지는 따로 확인한다.
- 같은 동작의 입력만 다른 테스트는 입력과 기대값 표를 쓰는 테스트 하나로 합친다. 같은 규칙을 여러 파일에서 되풀이해 검증하지 않는다.
- 시간과 성능 기준 테스트는 CI에 두지 않고 로컬 측정 스크립트로 뺀다. 결과가 흔들리는 테스트는 근거 있는 테스트로 인정하지 않는다.

## 쓰기

- 성공과 실패는 자동으로 판정되게 한다.
- 테스트마다 테스트 데이터를 새로 만든다. 테스트끼리 상태를 공유하지 않는다.
- 입력은 근거에 해당하는 경계값, 빈 값, 잘못된 입력으로 고른다.
- 새 내부 함수를 직접 부르는 단위 테스트처럼 수정 전 코드로 돌릴 수 없는 테스트는 따로 분류해 보고한다. 공개 명령과 공개 API의 계약 테스트는 수정 전후에 같은 테스트로 비교한다.
- 끝없는 반복이나 메모리 폭증을 재현할 때는 생성 횟수 상한, 자식 프로세스 메모리 상한, 제한 시간으로 멈추게 한다. 실제로 메모리 부족을 일으키지 않는다.
- 이름은 `대상_조건_결과`로 짓는다. 대상은 공개 API나 사용자 동작이고, 조건이 없으면 뺀다(`parse_empty_input_returns_error`). 실제로 검증하는 범위보다 넓은 이름을 쓰지 않는다.
- 본문은 준비, 실행, 확인 순서로 쓰고 단계 사이에 빈 줄을 둔다.
- 테스트 하나는 동작 하나를 본다. assert 여러 개는 같은 동작을 확인할 때만 쓴다.
- 테스트 위치는 언어 관례를 따르고, 관례는 언어별 스킬에 있다.
