# 오류와 로그

실패의 종류에 따라 처리 방법, 메시지, 로그 레벨을 정한다.

## 실패 종류별 처리

- 입력, 파일, 네트워크, 외부 프로세스처럼 일어날 수 있는 실패는 오류 값이나 예외로 호출하는 쪽에 넘긴다.
- 코드에 버그가 없으면 일어날 수 없는 경우는 단언(assert)으로 중단한다. 메시지에는 그 조건이 성립해야 하는 이유를 쓴다.
- 테스트에서는 단언 실패로 중단해도 된다.
- 테스트 밖에서 구현을 미룬 채 실패하는 자리표시 코드를 두지 않는다.
- 예외로, 여러 작업이 함께 쓰는 공개 계약을 검토하는 초안 PR에는 미완성 자리표시를 둘 수 있다. `TODO(#{번호})`로 이슈를 남기고, PR을 준비 완료로 바꾸기 전에 0개로 만든다. 이 예외는 언어별 자리표시 금지보다 우선한다.
- 오류를 넘길 때는 무엇을 하다 실패했는지 덧붙인다(`failed to read config file`).
- 라이브러리 공개 API는 호출하는 쪽이 경우별로 처리할 수 있는 오류 종류를 돌려준다. 모든 오류를 한 타입으로 묶는 방식은 실행 파일(앱) 코드에서만 쓴다.
- 오류는 한 곳에서 한 번만 처리한다. 로그를 남기거나 넘기거나 둘 중 하나만 하고, 로그는 최종 처리하는 곳에서 남긴다.
- 오류를 무시하면 이유를 주석으로 쓴다. 빈 catch를 두지 않는다.

## 메시지

- 오류와 로그 메시지는 영어로 짧게 쓴다. 대소문자와 마침표는 언어 관례를 따르고, 관례는 언어별 스킬에 있다.
- 경로나 id 같은 관련 값을 넣는다. 비밀번호, 토큰, API 키, 개인정보는 넣지 않는다.

## 로그 레벨

| 레벨 | 쓰는 때 |
|---|---|
| error | 작업이 실패해 사람이 확인해야 할 때 |
| warn | 실패는 아니지만 예상 밖이라 재시도나 기본값 대체로 진행할 때 |
| info | 시작, 종료, 설정 적용처럼 드문 주요 상태 변화 |
| debug | 문제 원인을 찾을 때 필요한 값 |
| trace | 함수 진입, 반복마다의 세부 흐름 |

- 반복마다 찍히는 로그는 debug 이하로 둔다.
- 진단 메시지는 로그 라이브러리로 남긴다. CLI 도구는 로그를 stderr에 쓰고 stdout은 프로그램 결과에만 쓴다.
