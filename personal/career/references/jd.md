# JD 분석

공고 분석 단계에서 경력 원본을 읽기 전에 JD 원문으로 회사, 직무, 요구를 확정한다. 고정 길이 보고서를 만들지 않고 다른 스킬에 기대지 않는다.

## 경계

- 사용자가 준 JD 원문에서 시작한다. 회사 짐작, 검색 결과, 이전 지원, 지원자 정보로 시작하지 않는다.
- 회사, 직무, 팀, 공고를 확정하기 전에는 경력 원본을 쓰지 않는다. JD 분석 단계에서는 지원자 경험을 고르거나, 순위를 매기거나, 추천하지 않는다.
- 기존 분석 파일에 있는 후보 추천은 믿지 않는 제안으로 보고, 고르는 일은 구성 계획에서 한다.
- 직무 사실의 정본은 JD 원문과 회사 공식 자료이고 분석 파일은 해석이다. 최근 맥락은 가설을 보강할 때만 쓰고, JD 문구를 무효로 만들거나 지원자 사실을 만들어 내지 않는다.

## 출처와 최신성

`jd.md`에 다음을 적는다.

- 원문 URL이나 파일, 캡처 시각(절대 날짜와 시간대), 수집 경로(`direct`, `official-api`, `embedded-data`, `detail-iframe`, `official-html`, `user-supplied-text`), 공고 ID나 본문 해시를 적는다.
- 회사, 직무, 팀, 근무지와 근무 방식, 고용 조건과 연차 조건, 식별 신뢰도, 남은 신원 문제를 적는다.

기존 분석은 다음을 모두 채울 때만 다시 쓴다.

1. 원문 출처와 캡처 시각이 적혀 있다.
2. 같은 공고, 회사, 직무다.
3. 이번 실행에서 동적 공고를 다시 확인했다. 할 수 없으면 이유를 적었다.
4. 명시 사실, 최근 근거, 추정, 불확실을 갈라 두었다.
5. 출처에 접근할 수 있거나 관련 내용이 남아 있다.

하나라도 못 채우면 새로 분석한다. 분석 파일만 있고 원문을 되살리거나 확인할 수 없으면 원문을 요청하고 멈춘다.

## 수집 순서

출처는 다음 순서로 쓴다.

1. 사용자가 준 JD URL, 본문, 파일을 먼저 쓴다.
2. 다음으로 같은 공고의 공식 채용 페이지와 공식 엔드포인트를 쓴다.
3. 공식 API, JSON-LD, 내장 데이터(`__NEXT_DATA__` 등), 상세 iframe, 공식 HTML을 쓴다.
4. 직무 해석에 의미 있는 공식 회사, 제품, 뉴스룸, 기술 블로그를 쓴다.
5. 더 강한 출처가 없을 때만 믿을 만한 2차 보도를 쓴다.

- 검색 요약, 숫자 ID, 채용 플랫폼 요약만으로 공고, 회사, 직무를 짐작하지 않는다. 막힌 화면 대신 공식 데이터 경로를 쓴다.

## 근거 표시와 신뢰도

| 표시 | 뜻 |
|---|---|
| `[명시]` | JD에 직접 적혀 있다 |
| `[최근근거]` | 날짜가 있는 JD 밖 출처다 |
| `[추정]` | 이유를 적은 해석이다 |
| `[확인필요]` | 확인하지 못했다 |

- 최근 주장에는 출처, 날짜, 직무 해석을 바꾸는 이유를 함께 쓴다. 추정을 회사 사실로 쓰지 않는다.

| 신원 신뢰도 | 뜻 | 처리 |
|---|---|---|
| `high` | JD나 공식 연결이 회사와 직무 하나를 확정한다 | 진행한다 |
| `medium` | 신원은 하나지만 공식 연결이 일부 모자란다 | 맥락 주장을 낮춰 진행한다 |
| `low` | 후보가 여럿이다 | 멈춘다 |

## jd.md 내용

다음 순서로 쓴다.

1. 출처 기록과 조사 한계를 쓴다.
2. 신원과 신뢰도를 쓴다.
3. 채용 이유, 곧 이 직무로 풀려는 문제를 쓴다.
4. 명시 요구로 업무, 필수와 우대, 기술과 도메인 제약, 협업, 되풀이되는 신호를 쓴다.
5. 추정 요구는 결과를 바꾸는 몇 가지만 근거, 이유, 신뢰도와 함께 쓴다.
6. 최근 맥락은 직무 해석을 바꾸는 날짜 있는 신호만 쓴다.
7. 열린 질문으로 모순, 빠진 정보, 멈춤과 질문 조건을 쓴다.

- 회사 연혁, 칭찬, 문화 짐작, 면접 질문 목록은 요청받았을 때만 쓴다. 최근 근거가 없으면 `JD 기반`으로 표시하고 실패한 확인을 적는다.
