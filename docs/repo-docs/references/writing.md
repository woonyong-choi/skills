# 문서 작성 규칙

저장소 문서의 절 구성, 문체, 문장, 용어, 서식을 정한다. 문서를 쓰거나 교정하기 전에 읽는다.

## 절 구성

1. 종류별 스킬의 절 목록이나 틀에서 필요한 절만 골라 그 순서대로 놓는다.
2. 필수 절은 종류별 스킬이 단계마다 정한다. 채울 사실이 없을 때의 처리는 [repo-docs 작성 절](../SKILL.md#작성)을 따른다.
3. 목록에 없는 절은 독자 질문에 필요할 때만 더한다. 같은 독자 질문의 하위 조건을 설명하는 절 바로 뒤에 둔다. 여러 저장소에서 되풀이되면 종류별 스킬 목록에 더한다.
4. 같은 내용의 절은 목록의 글자를 그대로 쓴다. 동의어를 쓰지 않는다.
5. 절 길이, 예시 수, 그림 수는 독자 질문에 필요한 정의, 조건, 예시, 예외를 모두 담는 만큼으로 하고 되풀이는 지운다.
6. 독자 질문에 맞게 문제, 근거, 판단, 결과, 한계를 잇는다. 앞뒤 문서와 겹치거나 끊기는 곳이 없는지 확인한다. 빈 절, 자리 채우기, 지어낸 내용을 쓰지 않는다.
7. 종류별 스킬의 코드 블록 예시는 절 구성과 문체를 보여 주는 표본이다. 글자를 그대로 베끼지 않는다.

## 문체

- 사람이 쓴 문서처럼 필요한 사실과 판단을 바로 전한다. 아래 신호는 교정 기준이고, 누가 썼는지 판정하는 근거로 쓰지 않는다.
- 한국어와 영어 문서, 커밋 메시지, PR과 이슈의 제목, 본문, 댓글에 적용한다. 인용, 코드, 명령 출력, 사용자가 확정한 문장은 원문을 지킨다.
- 작성 표시를 넣지 않는다. 작성 표시는 `Co-Authored-By`, `Generated with`, 로봇 이모지(`U+1F916`), 모델 이름을 붙인 작성 표시, 생성 문구, 세션 링크다. 작성자는 사용자 Git 설정을 그대로 쓴다.
- AI 티 나는 낱말, 과장, 꾸밈, 셋 맞추기, 뻔한 결론 같은 공통 패턴의 정본은 **unslop** 스킬이다. 이 절은 저장소 문서에만 더하는 규칙을 적는다.
- 커밋 본문, PR과 이슈 본문, 댓글의 끝말은 아래 한국어 문체 표의 개조식이 정본이다. **unslop**과 **technical-writing** 스킬의 서술어 규칙(완결된 문장, 능동태 서술)은 이 자리에 적용하지 않는다. unslop은 AI 티 낱말, 과장, 꾸밈을 지우는 데만 쓴다.

| 신호 | 저장소 문서 규칙 |
|---|---|
| 굵게 | 줄 첫머리 굵은 머리말 `**이름.**`에만 쓴다(unslop 16번). 문장 안 낱말을 굵게 하지 않는다 |
| 장식 | 이모지를 어디에도 쓰지 않는다. 제목과 글머리 기호 밖도 같다 |
| 줄표로 문장 잇기 | 한국어 글에서도 `—`(em dash)로 설명이나 문장을 잇지 않는다. 마침표로 나누거나 접속 관계를 문장에 밝힌다 |
| 안내 말 | `다음과 같습니다`, `살펴보겠습니다`, `Let's`, `In summary`, `It's worth noting`을 쓰지 않는다. 안내 없이 내용부터 쓴다 |
| 근거 없는 확신 | 확인한 범위를 넘어 단정하지 않는다. 주장에 근거와 적용 범위를 밝히고, 근거가 없으면 주장을 지우거나 미확인으로 표시한다 |

### 한국어 문체

| 문체 | 자리 | 문장 끝 | 예 |
|---|---|---|---|
| 합쇼 | 한국어 루트 README 문단 | `-ㅂ니다`, `-습니다`, `-입니다` | `입력한 내용을 저장합니다.` |
| 합쇼 요청 | 한국어 루트 README에서 독자에게 하라고 하는 문장 | `-세요` | `다음 명령으로 설치하세요.` |
| 평서 | 그 밖 한국어 문서의 문단과 절차 | `-다` | `엔진은 입력을 먼저 저장한다.` |
| 명사형 | 제목, 표 칸, 한 줄짜리 대등한 나열 목록 | 명사구. 종류별 제목 예외가 먼저고 끝에 마침표가 없다 | `- 입력 기록 보존` |
| 개조식 | 커밋 본문, PR과 이슈 본문, 이슈와 PR 댓글(결정, 범위 변경, 닫기) | 명사(`수정`, `추가`, `확인`, `결정`, `구현`, `대기`, `없음` 등). 한 줄에 사실 하나 | `- 재연결 뒤 중복 전송 수정` |

- 문서(README, docs)의 설명과 절차는 완결된 문장으로 쓴다. 번호 목록의 단계도 문장이다(`1. 엔진이 입력을 기록 저장소에 저장한다.`).
- 문서의 명사형은 표 칸과 한 줄짜리 대등한 나열에만 쓴다. 한 목록 안에 명사구와 문장을 섞지 않는다.
- 현재형으로 쓴다. 과거형은 끝난 일(실험 방법과 결과, 판단 기록)에만 쓴다.
- 다음 종결을 쓰지 않는다. `-해요`, `-십시오`, `-함`, `-음`, `-임`, `-ㄹ 것이다`, `-게 된다`, 합쇼 파일의 `-다`, 평서 파일의 `-니다`와 `-세요`, 개조식의 `-다`, `-니다`, `-요`.
- 질문문, 느낌표, 줄임표를 쓰지 않는다.

### 영어 문체

- 현재형과 능동태로 쓴다. 독자에게 하라고 하는 문장은 명령형으로 쓴다(`Run the following command.`).
- 제목은 첫 글자만 대문자로 쓴다(sentence case, `How it works`).
- 축약형을 쓰지 않는다(`do not`, `it is`).
- 다음 말을 쓰지 않는다. `blazing`, `powerful`, `seamless`, `simply`, `easy`, `easily`, `revolutionary`, `next-generation`, `cutting-edge`, `world-class`, `best-in-class`.
- 문장 첫머리에 `Additionally`, `Furthermore`, `In conclusion`, `Basically`를 쓰지 않는다.
- 질문문, 느낌표, 줄임표를 쓰지 않는다.

## 문장

- 한 문장에 사실 하나를 쓴다.
- 주어와 동작을 밝힌다. `최적화 수행` 대신 `캐시로 조회 수를 줄인다.`라고 쓴다.
- 형용사 대신 동작과 수치를 쓴다. `빠른 검색` 대신 `색인으로 검색한다.`라고 쓴다.
- 이유는 규칙 바로 뒤 한 문장으로 쓴다(`{규칙}. {막는 일}을 막기 위해서다.`).
- 기호와 변수는 처음 나오는 문장에서 정의한다(`활성 맥락 크기 A가 기준 T 이상이면 새 세션을 연다.`).
- 설계로 정한 수치에는 공개 결정 기록이나 실험 이슈 링크를 단다. 측정이 필요한데 실험이 없으면 `미해결`에 둔다.
- 사용자가 확정한 문장과 인용은 원문 그대로 둔다.

## 용어

- 기술 용어는 원어를 기본으로 쓴다. 저장소 용어집이 먼저고, 없으면 인용하는 공식 문서의 이름을 쓴다.
- 구매자와 실사용자가 다른 도메인에서는 고객과 사용자를 가른다. 코드 식별자는 원문 그대로 둔다.
- 번역어를 쓸 때는 처음 나오는 곳에 원어를 함께 적는다(`캐시(cache)`). 번역어와 원어 중 하나를 문서 전체에서 같게 쓴다.
- 구성 요소와 모듈 이름은 코드 식별자와 같은 글자로 쓴다(`core`, `engine`).
- 같은 대상은 저장소 전체에서 같은 이름으로 부른다. 기준은 `docs/glossary.md`이고, 없으면 `docs/architecture.md` 구성 요소 표다.
- 프로젝트 고유 용어는 `docs/glossary.md`에 둔다. 업계 일반 용어는 넣지 않는다.
- 업계에서 널리 쓰는 약어(API, CLI, JSON, TUI, HTTP)는 그대로 쓴다. 프로젝트가 만든 약어는 처음 나오는 곳에서 푼다.

| 쓰는 말 | 쓰지 않는 말 |
|---|---|
| 사용자 | 유저 |
| 절 | 섹션 |
| 저장소 | 레포, 리포지토리, 레포지토리 |
| 명령 | 커맨드 |
| 설정 | 컨피그 |
| 오류 | 에러(코드 식별자 제외) |
| 실행 | 구동 |
| 측정 전 | 미측정 |
| 합성 데이터 | 더미 데이터, 목업 데이터 |

- 다음 수식어를 쓰지 않는다. `강력한`, `혁신적`, `쉽게`, `손쉽게`, `간단히`, `간단하게`, `다양한`, `효율적`, `원활`, `최적의`, `완벽한`, `매끄러운`, `차세대`.
- 문장 첫머리에 `또한`, `이를 통해`, `이에 따라`, `결론적으로`, `요약하면`, `참고로`, `기본적으로`를 쓰지 않는다.
- 추측 표현 `~것 같다`, `~로 보인다`, `아마`, `TBD`, `TODO`를 쓰지 않는다.
- 문장 습관과 근거 범위는 문체 절을 따른다. 낱말만 바꿔 같은 과장이나 단정을 남기지 않는다.
- 명령, 경로, 파일 이름, 코드 식별자, 패키지와 crate 이름, 설정 키와 값, 메서드 이름은 인라인 코드로 쓴다(`cargo test`, `Cargo.toml`, `tokio`, `session/start`).
- 제품, 서비스, 언어, 운영체제, 표준 이름은 일반 글자로 쓴다.

## 서식

1. 제목은 문서당 `#` 하나다. README 머리는 정해진 HTML `h1`로 대신할 수 있다. 제목 단계를 건너뛰지 않고 제목 끝에 문장부호를 쓰지 않는다.
2. 블록 사이에 빈 줄 하나를 둔다. 빈 줄을 잇따라 두지 않고 줄 끝에 공백을 남기지 않는다. 파일 끝에는 줄바꿈 하나를 둔다.
3. 문단은 한 줄로 쓴다. 문장 중간에서 줄을 바꾸지 않는다.
4. 비순서 목록은 `- `, 순서 목록은 `1.`, `2.`처럼 실제 번호를 쓴다. 목록을 중첩하지 않는다. 예외는 `docs/README.md` 문서 목록의 하위 문서 한 단계와 repo-docs-design `references/index.md`다.
5. 표에는 머리 행과 `|---|` 구분 행을 반드시 둔다. 칸 앞뒤에 공백 하나를 두고 칸 안에서 줄을 바꾸지 않는다.
6. 값이 0개인 칸은 `없음`, 항목이 그 대상에 적용되지 않는 칸은 `해당 없음`으로 쓴다.
7. 코드 블록은 백틱 세 개와 언어 태그 `sh`, `text`, 또는 코드 언어 이름(`rust`, `toml`, `json`, `python`)으로 쓴다. 명령 앞에 `$`를 붙이지 않는다.
8. 그림은 이미지 한 줄 `![{대체 글}]({상대 경로})`로 넣는다. 다크 모드 그림이 따로 있으면 `<picture>` 블록을 쓴다. 그림 파일이 없으면 그 줄을 지운다(repo-docs-figures). mermaid와 텍스트 그림을 쓰지 않는다. 예외는 `docs/ui.md`와 `docs/design/`의 화면 배치 그림, repo-docs-figures의 `thinkflow` 원본 블록이다.
9. 저장소 안 링크는 상대 경로로 쓴다. 링크 글자는 문서 제목, 파일 이름, 문서 종류 이름(`결정 기록`) 중 하나로 쓴다. `여기`, `이 링크`, `here`를 쓰지 않는다.
10. 굵게와 이모지는 문체 절을 따른다. 기울임과 각주를 쓰지 않는다. 배지는 README 머리에만 둔다(repo-docs-readme). HTML은 `<picture>`, `<source>`, `<img>`, `<details>`, `<summary>`, PR 본문 캡처 표의 `<table>`, `<tr>`, `<th>`, `<td>`(git-pull-request 틀), README 머리의 `<p align="center">`, `<h1 align="center">`, `<a>`, `<br>`만 쓴다.
11. 인용 블록은 GitHub 알림 두 가지만 쓴다. `> [!NOTE]`는 알아 둘 사실, `> [!WARNING]`은 어기면 데이터나 동작을 잃는 규칙에 쓴다. 다음 줄에 `> {문장}` 한 줄을 둔다.
12. 숫자와 단위는 한국어에서 붙여 쓰고(`5초`, `2GB`) 영어에서 띄어 쓴다(`5 s`, `2 GB`). 날짜는 `YYYY-MM-DD`로 쓴다.
13. 조사는 영문과 코드 바로 뒤에 공백 없이 붙인다(`API를`, `store에`).
