# DiagramPlay 그림 품질

요청한 항목을 빠짐없이 담고, 가로형으로 읽히고, 무엇이 중요한지 바로 보이는 DiagramPlay 그림을 만든다. 문법과 정본 고르기는 [그림 작성](syntax.md), 명령은 [설치와 실행](execution.md)과 [검사](validation.md)가 맡는다. 편집 규칙은 [Diagram Design](https://github.com/cathrynlavery/diagram-design)(MIT)의 "더 뺄 것이 없을 때 끝난다", 종류 꼬리표, 초점 1~2개, 기술 글만 고정폭, 복잡도 상한을 DiagramPlay 문법으로 옮긴 것이다.

## 가로형 원칙

연결의 읽는 순서와 짧은 경로를 우선한다. 고정 본문 폭이나 비율에 맞추려고 구조를 접어 긴 우회를 만들지 않는다. 자연 배치를 가용 가로 폭에 맞춰 비례 축소하고 일반 보기에서 가로 스크롤이 생기지 않는지 확인한다. 세로 길이는 허용하며 전체화면 확대와 맞춤도 확인한다.

복잡한 설계는 요소·연결·포함 관계를 보존한다. 카드 개수나 면적 목표 때문에 내용을 지우지 않는다. 본문이나 인쇄에서 글자를 읽기 어려우면 전체 구조를 남기고 상세 보기를 추가한다. SVG를 손으로 고치거나 근거 없는 aspect 값으로 문제를 덮지 않는다. 클라우드 구성도는 [NHN Cloud 규칙](nhn-cloud.md)을 먼저 적용한다.

실제 표시 글자 크기는 원본 글자 크기에 표시 폭을 곱하고 SVG의 `viewBox` 폭으로 나누어 확인한다. 예를 들어 15px 글자가 있는 폭 1,400의 그림을 800px로 표시하면 글자는 약 8.6px이고, 폭 400의 그림을 같은 폭으로 표시하면 약 30px이다. 같은 토큰을 사용했어도 문서 안에서는 크기가 다르다.

대상 문서의 실제 본문 폭에서 그림들을 나란히 비교하고, 역할이 같은 글자와 선이 비슷한 크기로 읽히도록 맞춘다. 표시 폭을 지정해야 하면 repo-docs `references/writing.md`의 그림 서식을 따른다. 핵심 이름, 조건과 단위를 읽을 수 있어야 하며, 재생 중 바뀌는 문구 때문에 그림 전체가 불필요하게 넓어지지 않는지도 확인한다.

## 품질이 무너지는 원인

아래는 원본을 직접 그려 재현한 증상이다. 모두 `check --strict`를 통과했으므로 검사 통과만으로 품질을 판단하지 않는다. 고치는 법의 자세한 규칙은 가리킨 절에 있다.

| 증상 | 원인 | 고치는 법 |
|---|---|---|
| 모든 카드가 같아 무엇이 중요한지 안 보인다 | 종류, 기술 값, 초점이 글자로도 색으로도 드러나지 않는다 | 2절 편집 위계 |
| 세로로 긴 그림이 된다 | 읽는 순서와 표시 환경 대신 고정 폭·비율을 우선했다 | 전체 구조를 보존하고 실제 가로 맞춤과 상세 보기를 확인한다 |
| 그룹이 계단처럼 내려간다 | 그룹을 앞 그룹 마지막 카드에서 다음 그룹 첫 카드로 차례로 잇는다 | 4절 격자 만들기 |
| 선이 엉킨다 | 같은 역할 카드 여럿이 각자 같은 대상으로 선을 긋는다 | 4절 같은 역할 |
| 카드 폭이 들쭉날쭉하고 이름이 두 줄로 접힌다 | 이름과 선 글에 문장을 쓴다(카드 폭 169~186px) | 4절 이름 길이 |
| 요청한 메시지가 정지 이미지에 없다 | 순서 그림의 정지 SVG는 고른 장면 하나의 메시지만 그린다 | 한 장에 보일 메시지는 첫 장면에 두고 선택 경로는 `fragment` |
| 지표 카드가 흩어지고 순서가 바뀐다 | 선 없는 카드는 선언 순서와 다르게 쌓인다 | 지표는 카드 하나의 `value` 줄로 모은다. 값 이름은 한글 4자, 값은 6자 안팎 |
| 차트 합계가 뜻 없는 값이 된다 | 매출과 비용을 `stacked`로 쌓았다 | 3절 아래 줄 |
| 그래프 그림에 제목과 설명이 없다 | 구조, 상태, 순서 그림은 `title`을 그리지 않고 `subtitle`은 HTML에만 나온다 | 그림 안에 보일 말은 카드, 꼬리표, 선 글, 보기 라벨로 쓰고 나머지는 본문과 대체 글에 쓴다 |
| 같은 문서에서 한 그림만 글자와 선이 유난히 크거나 작다 | 서로 다른 `viewBox`의 그림을 같은 표시 폭으로 맞췄다 | 가로형 원칙에 따라 원본 배치와 삽입 폭을 함께 조정한다 |

## 1. 요구 항목 뽑기

1. 그릴지부터 정한다. 표나 문단 하나로 같은 것을 전할 수 있으면 그리지 않는다. 카드 하나뿐인 그림, 속성만 나열하는 그림은 문장이나 표로 쓴다.
2. 요청과 글에서 그릴 것을 다섯 종류로 나눠 목록을 만든다. 구성 요소(카드), 단계와 메시지(선, 순서), 상태와 전이, 관계(키, 호출, 소속), 수치(값, 계열, 단위)다.
3. 항목마다 원본 머리에 `require "표시 이름"` 한 줄을 적는다. 같은 뜻의 다른 이름은 `or`로 잇는다(`require "토큰 갱신" or "/refresh"`). "3대", "포함" 같은 수량과 조건도 항목으로 적는다. `--docs` 검사가 그림의 보이는 글(테이블 열, 차트 행 포함)에서 찾지 못한 항목을 그 줄에 `docs-15` 오류로 알린다. 원본에 남으므로 다음 수정 때도 다시 검사된다.
4. 항목마다 그림에서 맡을 자리를 정한다. 카드, 부제, 꼬리표, 선 글, 값 줄, 차트 행, 장면 가운데 하나다. 자리가 정해지지 않은 항목은 본문에 쓸 항목으로 따로 표시한다.
5. 한 그림의 양을 정한다. 요청한 전체 구조와 관계를 보존한다. 같은 역할의 실제 복제만 count로 합친다. 특정 개수를 강제하지 않고 실제 표시에서 읽기 어려울 때 전체와 상세 보기를 나눈다.
6. 장면을 나눌지 정한다. 장면은 같은 구조 위의 다른 경로나 변화를 보일 때만 나눈다. 정지 이미지 한 장에 모두 보여야 하는 항목은 첫 장면에 둔다.
7. 그리기 전에 답변에 한 줄로 계획을 적는다. 그림 종류, 쓰임(본문 단, Obsidian, 포트폴리오), 상한 때문에 빼거나 합칠 항목이다. 사용자가 있으면 고칠 기회를 주고, 없으면 그 줄을 가정으로 남기고 진행한다.

## 2. 편집 위계

그림은 "더 뺄 것이 없을 때" 끝난다. 카드는 서로 다른 생각 하나씩이고, 선은 배치만으로 알 수 없는 정보를 하나씩 싣는다. 그 위에 아래 다섯 가지로 위계를 세운다.

- **종류 꼬리표.** 종류가 이름이나 기본 도형만으로 구분되지 않을 때만 꼬리표를 단다. NHN 구성도의 서비스·리소스·그룹 종류는 공식 아이콘과 레이블을 우선한다. 프로세스 내부 컴포넌트도, 순서도, 상태도와 시퀀스에 같은 배지를 반복해 붙이지 않는다. 꼬리표는 이름이 아니라 종류를 말하므로 다섯 낱말 가운데서 고른다. `EXT`(우리가 운영하지 않는 바깥), `EDGE`(요청을 받아 넘기는 경계, 로드밸런서와 CDN), `APP`(우리 코드가 도는 서버와 서비스), `DATA`(DB, 캐시, 파일 같은 저장), `ASYNC`(큐 뒤의 워커와 배치)다. 같은 종류는 같은 글이다. 꼬리표 글이 범례 노릇을 하므로 흑백에서도 종류가 남는다. 같은 범위에서 같은 뜻으로 사용하되 모든 카드에 반복해 달지 않는다. `queue`는 꼬리표를 받지 않고 칸이 종류를 대신한다. `person`은 꼬리표를 받지만 사람 아이콘이 이미 종류를 말하므로 달지 않는다. 이름을 되풀이하는 꼬리표(`DB` 카드의 `DB`, `캐시` 카드의 `CACHE`)를 쓰지 않는다.
- **이름과 부제.** 이름은 사람이 읽는 명사(`Astro 오리진`)이고 일반 글꼴로 쓴다. 경로, 포트, 명령, 프로토콜 같은 기술 값은 부제에 백틱으로 쓴다(``"`src/content/*.mdx`"``). 백틱 구간만 고정폭으로 그려진다. 이름 전체를 백틱으로 감싸지 않는다.
- **초점.** 읽는 순서에 도움이 될 때만 강조한다. 원본 아이콘 색을 바꾸거나 모든 카드를 칠하지 않는다. 실제 동시 상태를 정해진 강조 개수에 맞춰 지우지 않는다. NHN 구성도의 성공과 실패는 공통 의미 역할과 글로 함께 표시한다.
- **경로 번호와 선 모양.** 처리 단계를 설명하는 그림은 주 경로의 선에 `no=1`부터 차례로 번호를 달아 정지 이미지에서도 순서가 읽히게 한다. 컴포넌트의 호출·의존 관계만 나타내는 그림에는 처리 순서처럼 보이는 번호를 달지 않는다. 주 경로와 보조 경로를 구분한다. 비동기라는 이유만으로 모든 주 흐름을 dashed로 바꾸지 않는다. 보조 경로와 상태 표현은 NHN Cloud 규칙을 따른다. 같은 선을 호출과 반환에 함께 쓰지 않으며, 반환을 생략하면 본문에 그 범위를 밝힌다. 배치만으로 뻔한 관계의 선과 선 글은 지운다.
- **경계.** 신뢰 경계·배포 단위·소유 범위의 실제 포함 관계를 group과 이름으로 표시한다. 클라우드 경계는 NHN Cloud 규칙을 따른다. 모든 그룹을 같은 점선이나 무테두리로 바꾸지 않는다.

DiagramPlay에는 구조 그림의 범례 띠, 카드 위 큰 단계 숫자, 그림 안 제목 글꼴 선택이 없다. 범례는 꼬리표로, 단계 숫자는 `no=`로, 제목은 본문 머리로 대신하고, 카드나 그룹을 꾸며 흉내 내지 않는다. 범례 카드를 따로 두면 선 없는 카드라서 흩어진다.

## 3. 그림 종류 고르기

| 전할 내용 | DiagramPlay 그림 | 주로 쓰는 문법 |
|---|---|---|
| 구성 요소와 요청이 지나는 길(아키텍처) | 구조 그림, 구성도 | `box`, `store`, `queue`, `external`, `group`, `badge=`, `icon=`, `count=`, `no=` |
| 처리 단계의 차례(순서도) | 구조 그림 | 갈래가 있으면 `decision`, 하위 단계가 있으면 단계 카드 안 `text` 줄 |
| 참여자 사이 메시지 차례(시퀀스) | 순서 그림 | `view sequence`, `dashed` 응답, `fragment alt`, `opt`, `loop`, `par`, `note` |
| 대상의 생애 주기 | 상태 그림 | `state`, `start`, `final`, 전이마다 사건 글, 예외 전이는 `dashed` |
| 테이블, 키, 참조 | 데이터 관계 그림 | `table`, `pk`, `fk=` |
| API 요청과 응답 칸 | 구조 그림의 API 카드 | `api`, `카드.칸` 연결 |
| 클래스와 인터페이스 | 구조 그림의 클래스 카드 | `class`, `interface`, `relation=` |
| 배열, 비트, 메모리, 스택 | 칸 격자 | `grid`, `item` |
| 측정한 시간 구간 | 시간 보기 | `trace`, `span`, `view time` |
| 큐와 병목 | 구조 그림의 흐름 장면 | `queue slots=N`, `track`, `every`, `wait`. 용량과 속도는 단위로 적는다(`8건/분`) |
| 항목별 값, 두 조건 비교 | 차트 | `bar`, `dumbbell`, `difference` |
| 구성과 비율 | 차트 | `stacked`, `percent`, `pie`, `donut` |
| 시간에 따른 변화 | 차트 | `line`, `step`, `area` |
| 분포 | 차트 | `histogram`, `box`, `ecdf` |
| 두 변수 관계, 교차표 | 차트 | `scatter`, `heatmap` |
| 증감이 합계에 주는 영향 | 차트 | `waterfall` |
| 구조와 핵심 수치 한 장 | 구조 그림 보기 둘 | `view graph "구조"`, `view graph "성과"`와 값 줄 카드 |

- 메시지 차례를 구조 그림의 번호 선으로 대신하지 않는다. 같은 두 참여자 사이를 여러 번 오가면 순서 그림을 쓴다.
- 합계가 뜻 없는 두 값을 `stacked`로 쌓지 않는다. 비교는 `bar`, 차이 자체가 결론이면 `difference`를 쓴다.
- 두 종류가 다 맞아 보이면 독자가 따라갈 축 하나(시간, 구성, 상태)로 고르고 나머지는 다른 그림으로 나눈다.

## 4. 배치 규칙

- **이름 길이.** 제품과 자원의 실제 이름을 쓴다. 설명은 부제나 본문으로 옮기고 측정한 줄바꿈과 연결선 자리를 확인한다. 고정 글자 수에 맞춰 제품명을 임의로 바꾸지 않는다.
- **방향.** 구성 요소의 층과 읽는 순서에 맞춰 지원하는 방향을 고른다. 방향이나 `width wide`를 바꿨다는 이유만으로 배치가 개선됐다고 판단하지 않고, 본문 폭에서 글자와 연결선을 다시 확인한다. `view graph`는 보기를 둘 이상 둘 때 이름과 함께 쓴다(`view graph "구조"`).
- **자연 배치.** 사슬을 정해진 칸 수나 본문 폭에 억지로 접지 않는다. 관계와 방향을 우선하고 긴 우회·꺾임·큰 빈 영역을 확인한다. 창 폭 변화는 표시 배율로 처리하며 요소나 연결을 버리지 않는다.
- **같은 역할.** 복제 서버나 워커는 `count=N` 카드 하나로 그리고 대상은 그룹으로 묶는다. 개별 서버마다 다른 선이나 값이 있을 때만 카드를 나눈다.
- **예외 경로.** 정상 경로는 실선으로 한 줄을 이루게 두고, 실패, 취소, 재시도는 `dashed`로 옆에 둔다. 분기 조건은 해당 선의 고유한 구간에 붙여 조건과 결과를 바로 짝지을 수 있게 한다. 가까이 겹치는 선을 끝까지 추적해야 하면 경로를 벌리거나 조건과 결과를 행별로 나눈다. 읽기 어려우면 전체 구조를 보존하고 상세 보기를 보완한다.

## 5. 쓰임별 기준

| 쓰임 | 넣는 방식 | 기준 |
|---|---|---|
| HTML로 넣는 블로그 글 | 본문의 `diagramplay` 블록을 빌드가 HTML 그림으로 넣는다 | 실제 본문 폭에서 가독성과 가로 넘침을 확인한다. 장면 탭을 쓸 수 있다. 삽입 빌드가 파일을 읽지 않으면 `data` 파일과 파일 아이콘 세트를 쓰지 않는다 |
| Markdown 노트, GitHub 문서 | `diagramplay` 블록과 `diagramplay md`가 넣는 SVG 이미지 줄([Markdown과 CI](markdown.md)) | 가로형 원칙대로 표시 크기를 확인한다. 둘째 장면부터 접는 도구에서는 요청한 표시 방식과 맞는지도 확인한다 |
| 포트폴리오 한 장 이미지 | `render --static` SVG를 2배 PNG로 바꾼다 | A4 폭에서 가장 작은 글이 읽히도록 카드를 줄이거나 그림을 나눈다. 장면 없이 읽혀야 한다. 모든 항목을 첫 장면에 담는다. 그래프 그림의 제목은 그려지지 않으므로 보기 라벨이나 포트폴리오 쪽 제목으로 보탠다. 수치는 값 줄 카드 하나로 모으고 짧게 쓴다. 인쇄용이라 라이트 PNG 한 장을 만든다(career `scripts/figures.py`) |

- 실제 표시는 넣을 환경에서 따로 확인한다. Markdown 앱이 SVG 안 움직임을 재생하는지는 확인하지 않았다.

## 6. 나쁜 예와 좋은 예

아래 짝은 모두 `check --strict`를 통과하고 Chromium으로 렌더해 눈으로 비교했다. 머리 한 줄만 보인 좋은 예는 나쁜 예 원본에 그 줄을 더한 것이고, `scene`으로 시작하는 예는 원본의 해당 장면만 보인다.

**위계 없는 구성도.** 나쁜 예는 카드 다섯이 모두 같은 모양이고, 이름에 기술 값이 섞여 `Astro 오리진 서버 SSR과 MDX`가 두 줄로 접히고, 응답이 요청과 같은 실선이다.

```text
diagramplay
title "블로그 요청 경로"
person reader "독자 브라우저"
box edge "Cloudflare Pages 캐시"
box origin "Astro 오리진 서버 SSR과 MDX"
box bundle "MDX 번들"
store cms "콘텐츠 CMS"
reader -> edge "HTTPS 요청"
edge -> reader "응답"
edge -> origin "SSR 요청"
origin -> bundle "MDX 읽기"
origin -> cms "조회"
```

좋은 예는 같은 카드 다섯에 꼬리표, 고정폭 부제, 초점 하나, 주 경로 번호, 점선 응답과 경계를 단다. 같은 관계와 이름을 유지하고, 꼬리표만 읽어도 바깥, 경계, 우리 서버, 저장이 구분된다.

```text
diagramplay
title "블로그 요청 경로"
external reader "독자" "브라우저" badge="EXT"
box edge "Cloudflare" "Pages · 캐시" badge="EDGE"
box origin "오리진" "Astro `SSR` + `MDX`" badge="APP" tone=blue appearance=filled
group content "콘텐츠" dashed direction=down {
  box bundle "MDX 번들" "`src/content/*.mdx`" badge="DATA"
  store cms "콘텐츠 CMS" "자산 · OG 이미지" badge="DATA"
}
reader -> edge "HTTPS" no=1
edge -> origin "SSR" no=2
origin -> bundle "MDX 읽기" no=3
origin -> cms "조회" no=4
edge -> reader "응답" dashed
```

**그룹으로 이은 단계 사슬의 이전 관측.** 나쁜 예는 9단계를 `진입`, `처리`, `뒷단` 그룹 셋으로 묶고 그룹끼리 차례로 이어 192x1011의 세로 한 줄이 된다. 이 수치는 이전 배치의 관측이다. 현재의 일반 해법으로 격자 접기를 지시하지 않고 관계와 포함 범위를 보존한 자연 배치를 확인한다.

```text
diagramplay
title "요청 처리 경로"
person user "사용자"
box dns "DNS"
box cdn "CDN"
box lb "로드밸런서"
box api "API 서버"
box cache "캐시"
store db "DB"
queue mq "메시지 큐" slots=4
box worker "워커"
user -> dns
dns -> cdn
cdn -> lb
lb -> api
api -> cache
cache -> db
db -> mq
mq -> worker
```

단계를 묶어 보이고 싶으면 그룹 대신 단계 카드 안 `text` 줄을 쓴다.

**같은 역할의 서버 여럿.** 나쁜 예는 `api1`, `api2`, `api3`를 따로 두고 각자 캐시, DB, 큐로 선 9개를 그어 선이 엉킨다. 좋은 예는 카드 하나와 그룹 둘로 선을 5개로 줄이고, 요청이 모이는 API 서버를 초점으로 칠한다.

```text
box lb "로드밸런서" badge="EDGE"
box api "API 서버" badge="APP" count=3 tone=blue appearance=filled
group data "데이터" direction=down {
  box cache "캐시" badge="DATA"
  store db "DB" badge="DATA"
}
group async "비동기 처리" direction=down {
  queue mq "메시지 큐" slots=4
  box worker "워커" badge="ASYNC"
}
lb -> api "분산"
api -> cache "조회"
api -> db "저장"
api -> mq "발행"
mq -> worker "소비"
```

**문장 이름.** 나쁜 예는 카드 이름과 선 글에 문장을 써 카드 폭이 169~186px로 갈리고 이름이 두 줄로 접힌다.

```text
box a "사용자가 웹 브라우저에서 주문 버튼을 누름"
box b "주문 API가 요청을 받아 검증함"
box c "주문 서비스가 재고를 확인하고 결제 요청을 보냄"
a -> b "HTTPS POST 요청으로 주문 내용을 전달"
b -> c "검증한 주문을 넘김"
```

좋은 예는 이름을 명사로 줄이고 기술 값은 부제로, 설명은 카드 안으로 옮긴다.

```text
person a "사용자"
box b "주문 API" "`POST /orders`" badge="APP"
box c "주문 서비스" badge="APP" {
  text "재고 확인 뒤 결제 요청"
}
a -> b "주문"
b -> c "검증 통과"
```

**두 장면으로 나눈 시퀀스.** 나쁜 예는 로그인과 토큰 갱신을 `scene` 둘로 나눠 정지 SVG에 토큰 갱신이 없다. 좋은 예는 한 장면 안에 `fragment opt`로 담는다.

```text
scene "로그인과 갱신"
  front -> browser "로그인 완료" dashed
  fragment opt "액세스 토큰 만료 시" run=on {
    front -> auth "POST /refresh"
    auth -> front "새 액세스 토큰" dashed
  }
```

**흩어진 지표 카드.** 나쁜 예는 선 없는 지표 카드 셋이 2+1로 쌓이고 순서가 바뀐다. 좋은 예는 값 줄 카드 하나를 둘째 보기에 둔다.

```text
box kpi "기존 대비" {
  value latency "p95 지연" from=-85%
  value throughput "처리량" from=5배
  value cost "월 비용" from=-40%
}
view graph "구조" {
  user api db jobs worker push
}
view graph "성과" {
  kpi
}
```

## 7. 완료 전 확인

1. 원본 검사와 정지 SVG, HTML 렌더는 [설치와 실행](execution.md)의 명령으로 한다. 기하 오류가 없고 종료 코드가 0이어야 한다.
2. 항목과 배치 위험은 DiagramPlay의 문서 품질 검사(`--docs`)가 대조한다. `render_figures.py`는 늘 `--strict --docs`로 부르므로 `docs-*` 진단이 하나라도 있으면 실패한다. 직접 실행할 때도 같은 옵션을 준다. 검사 항목과 기준 수치의 정본은 DiagramPlay [문서 품질 검사](https://github.com/woonyong-choi/diagramplay/blob/main/docs/design/figure-quality.md)다. NHN 구성도에서 가이드가 요구하지 않는 배지·초점 수·카드/선 수 상한과 넓은 표시 자체를 통과 조건으로 삼지 않는다. 원본 종류·자리, 요구 항목과 실제 본문 읽힘은 확인한다. 이 검사는 글과 배치로 잴 수 있는 위험(요구 항목, 꼬리표, 초점 수, 이름과 선 글 길이, 카드와 선 수, 접힌 사슬, 계단, 흩어진 카드, 순서 그림의 메시지와 장면 수, 680px 본문 단의 글 크기)만 보므로, 통과해도 4번과 5번을 건너뛰지 않는다.

   ```sh
   node <DiagramPlay 경로>/src/cli.js check <원본>.diagramplay --strict --docs
   ```

3. PNG로 찍어 직접 본다. DiagramPlay 소스 작업본의 `scripts/shoot.mjs`(npm 패키지에는 없다)는 Mac의 Chrome을 기본으로 쓰고, 다른 곳에서는 `CHROME_PATH`에 Chrome이나 Chromium 경로를 준다. 정지 SVG를 라이트와 다크로, HTML을 390px로 찍는다.

   ```sh
   node <DiagramPlay 경로>/scripts/shoot.mjs <출력 폴더>/<원본>.svg <이름>-light.png
   node <DiagramPlay 경로>/scripts/shoot.mjs <출력 폴더>/<원본>.svg <이름>-dark.png --dark
   node <DiagramPlay 경로>/scripts/shoot.mjs <출력 폴더>/<원본>.html <이름>-390.png --width 390
   ```

4. PNG에서 빼기 점검을 한다. 하나라도 "예"면 원본을 고치고 1번부터 다시 한다.
   - 지워도 독자가 이해하는 카드가 있는가.
   - 늘 함께 다니는 두 카드가 있는가. 있으면 하나로 합친다.
   - 배치만으로 뻔한 선이나 꼬리표와 같은 말을 되풀이하는 선 글이 있는가.
5. PNG에서 아래를 하나씩 확인한다. 하나라도 어긋나면 원본을 고치고 1번부터 다시 한다.
   - 카드가 줄과 열에 맞고 폭이 같은 역할끼리 같다.
   - 가로형이고(높이가 폭 이하) 세로 한 줄, 계단, 엉킨 선이 없다. 되돌아오는 선은 한 줄 3칸 이상으로 접힌 사슬의 줄 바꿈 선만 허용한다.
   - 글이 잘리거나 겹치지 않고 두 줄로 접힌 이름이 없다.
   - 불필요한 강조가 없고, 꼬리표는 필요한 경우에만 같은 의미로 쓰고 업무 카드의 장식을 반복하지 않는다.
   - 처리 단계 그림의 주 경로 번호가 차례대로 읽힌다. 컴포넌트의 호출·의존 관계에는 불필요한 순서 번호가 없으며 응답과 예외 경로는 점선이다.
   - `require` 줄의 모든 항목이 정지 이미지에 보인다. `--docs`는 모든 장면의 글을 보므로, 장면 탭에만 있는 항목은 여기서 빠진 것으로 본다.
   - 선택한 폭과 방향이 실제 본문에서 읽히며, 같은 문서의 다른 그림과 글자·선의 표시 크기가 어긋나지 않는다. 390px HTML에서 가로 스크롤 없이 첫 카드가 잘리지 않는다.
   - 라이트와 다크에서 글자, 선, 아이콘, 꼬리표가 면 위에 보인다.
