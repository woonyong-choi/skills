# Career

- 우선순위: 사용자 지시 → 저장소 규칙 → 이 스킬. 범위 밖은 명시한 소유 스킬 적용
- 범위: 지원 폴더, JD 분석, 경력 원본 읽기·고르기, 이력서·포트폴리오 작성·버전·확인, 교정 기록. 원본 추가·병합·수정·형식은 career-record
- 결과물: Typst로 만든 PDF만. HTML 결과물·HTML 미리보기 단계 없음
- 필요할 때만 읽기: 포트폴리오 그림 원본 작성 → repo-docs-figures `references/syntax.md` 필수 확인; 방향 제안·확인 결과·완료 보고 문장 → repo-docs `references/plain-language.md`(쉬운 설명 규칙과 낯선 말 목록)

## 입력

- 필수: 새 JD(URL, 본문, 파일)와 경력 원본(`<Vault>/career/`, career-record 형식). 단계별 읽기 범위·양식 대응: [경력 원본 사용](references/source.md) 필수 확인. 비공개 원본 주소의 스킬 내 기재 금지
- 원본 없음·옛 형식(master.md 프로젝트 절, `cases/`): career-record 초안 절차, 사용자 확인 전 사용 금지. 짧은 이력서·요약으로 원본 대체 금지
- 미완성 원본: 있는 내용만 사용, 빈 곳 보고
- 기본값: 이력서와 포트폴리오 둘 다, 한국어, 고정 양식(`assets/typst/`)

## 지원 폴더

쓰기 전 Vault 확인: 공고 폴더를 만들기 전 `python3 <이 스킬 폴더>/scripts/versions.py place <공고 폴더>`로 등록 Vault의 `career/` 아래인지 검사(확정 `confirm`도 같은 검사). 종료 0이 아니면 파일 0개로 중단. Vault 등록 절차: repo-docs `references/project-context.md`. 등록 뒤 `<Vault>/career/` 없으면 생성

```text
<Vault>/career/
  master.md, {소속}/[{팀}/]{프로젝트}/   # 경력 원본, career-record 소유
  {마감일}-{회사명}-{직군명}/
    jd.md
    전략.md
    career.typ
    figures/{프로젝트}-{그림}.thinkflow, .svg, .png
    이력서/
      이력서.typ, 이력서.pdf
      이력서-{NNNN}.typ, 이력서-{NNNN}.pdf
    포트폴리오/
      포트폴리오.typ, 포트폴리오.pdf
      포트폴리오-{NNNN}.typ, 포트폴리오-{NNNN}.pdf
```

- 공고 폴더: `{마감일}-{회사명}-{직군명}/`. `career.typ`(양식)와 `figures/`(그림)는 두 문서 공용
- 문서 폴더: `이력서/`, `포트폴리오/`. 작업 파일(`{문서}.typ`) 하나와 확정 버전(`{문서}-{NNNN}.typ`, 4자리)
- 문서 파일의 참조: 공고 폴더 기준 절대 경로. `#import "/career.typ": *`, `#diagram("/figures/{프로젝트}-{그림}.png", [...])`. `../`는 Typst가 양식 파일 기준으로 풀어 폴더 밖 오류
- 만들기: 공고 폴더에서 `typst compile --root . 이력서/이력서.typ`. `/`로 시작하는 경로의 기준이 공고 폴더가 되도록 `--root .` 필수
- `{마감일}`: JD 마감일 `YYYY-MM-DD`, 상시·미표기면 `상시`. `{회사명}`: JD 표기 그대로. `{직군명}`: 직군 이름만, 괄호·경력 조건 삭제. 공백은 `-`, `/` 삭제. 예 `2026-11-30-토스-백엔드-개발자`
- JD를 받으면 JD 원문 먼저 읽기 → 공고 폴더 생성 → `jd.md`부터 작성
- 같은 공고 재작업: 기존 공고 폴더. 다른 공고: 새 공고 폴더
- 경력 원본(공고 폴더 밖 전부) 수정 금지. 사용자가 원본 수정을 요청하면 career-record
- `전략.md` 절: `# 공고 분석`, `# 구성 계획`, `# 작성`, `# 확인`. 점수·선택 JSON·근거 순위표 금지

## 교정

사용자가 사실·선호·작업 방식을 교정하면 [교정 기록](references/corrections.md) 필수 확인. 이번 작업에만 즉시 반영, 이전 지원 폴더 재작업 금지

## 사실 경계

작성·확인 공통 정본. 작성 규칙·검증은 이 절 참조

- JD는 강조만 결정, 지원자 사실 생성 금지
- 신원·시기·회사·프로젝트 경계·담당 범위(주체)·수치 조건·공개 범위·현재 상태(상태) 보존
- 조사·제안·구현·빌드·배포·운영 관찰·기기·E2E 검증·지속 성과 구분. 채택 안 된 제안은 반응과 결과를 사실대로
- 팀 성과는 본인 기여가 분명할 때만. 진행 중은 진행 중, 없는 요구는 공백
- 수치는 원본 확인·결과 칸에 방법·범위가 있을 때만. 줄 길이 때문에 조건을 빼야 하면 수치 삭제
- `미확인` 칸의 제출 문서 기재 금지, 빈 곳 보고
- 근거 보강 제안은 `전략.md` 별도 절, 완료 경험처럼 쓰기 금지
- 공백·참고 등 메모는 `jd.md`·`전략.md`에만. 제출 문서에는 근거·범위·상태·결과만

## 흐름

확인 질문 없이 1~4 연속 실행. 출처 충돌, 핵심 주장의 담당·증명 범위 불명, 구조를 바꾸는 시각 요청, 원본 초안 확인일 때만 질문. 지원 방향은 2단계에서 사용자 선택

1. 공고 분석: [JD 분석](references/jd.md) 필수 확인 → JD 원문 확보·신원 확정 → `jd.md` 작성 → 경력 원본 읽기(모든 `이력서.md` 속성·줄). `전략.md` 공고 분석 절에 출처·캡처 시각, 채용 이유, 명시·추정 요구, 중심 포지셔닝 2~3개, 과장 금지 사실, 공백 기록. 사례 선택·순서 결정 금지
2. 구성 계획: 공고 분석과 원본을 한 번에 대조. 먼저 지원 방향 2~3개 제안(아래 방향 제안 절), 사용자 선택 뒤 이어서. 이력서 선두 성과(원본 줄), 포트폴리오 사례(고른 줄의 짝 묶음), 줄이기·빼기·합치기, 순서와 쪽 흐름, 근거 보강 제안 결정과 짧은 이유 기록. 고른 줄의 짝 묶음만 읽기. 원본 등급은 참고 값, 수치 점수·순위표·고정 사례 수 금지
3. 작성: [작성 규칙](references/writing.md) 필수 확인 → 양식 복사 → 작성 → 그림 생성 → 원본 재검토로 보강. 버전 규칙은 아래 버전 절
4. 확인: [검증](references/validation.md) 필수 확인 → 보내기 전과 수정 반영 뒤 두 번, 결과를 `전략.md` 확인 절에 기록
5. 완료 보고: 아래 완료 보고 절

## 고정 양식

- `assets/typst/career.typ`를 지원 폴더에 그대로 복사, 수정 금지(색·글꼴·크기·간격·helper 포함)
- `resume.typ`→`이력서/이력서.typ`, `portfolio.typ`→`포트폴리오/포트폴리오.typ`로 복사 후 `{}` 자리, 근거 없는 칸·줄 삭제, 절·항목·사례 반복 수만 변경. 새 helper·직접 스타일 금지
- 인쇄 문서 양식이라 design-tokens 적용 제외

## 그림

- 포트폴리오 아키텍처·흐름 그림: ThinkFlow 정지 그림, 실제 관계만. 장식 금지
- 가로 배치, 기본 캔버스, 짧은 선 이름. `width wide` 금지(A4에서 글자 축소). 세로 전환은 배치 폭 기준(repo-docs-figures 그림 작성): 생성 뒤 PNG 확인, 세로로 돌았으면 이름 축약·그림 분리
- 생성: `python3 <이 스킬 폴더>/scripts/figures.py <공고 폴더>/figures --thinkflow <ThinkFlow 경로>`. SVG·PNG는 원본 옆(`<공고 폴더>/figures/`)에 생성. Python 3.9+·Node.js·ThinkFlow 체크아웃·playwright-core Chrome 필요(`CHROME_PATH` 선택). 원본마다 SVG와 2배 PNG, 실패 종료 1
- 원본: 프로젝트 `figures/{그림}.thinkflow` → 공고 폴더 `figures/{프로젝트}-{그림}.thinkflow`로 복사 뒤 생성
- 삽입: `#diagram("/figures/{프로젝트}-{그림}.png", [{결론 한 문장}])`. SVG 직접 삽입 금지(Typst CSS 변수 미지원)

## 방향 제안

구성 계획 첫 단계. 공고 분석 뒤 지원 방향 2~3개 제안, 고정 1개 강제 금지

방향마다:

- 이력서 첫 줄(자기소개 문장) 실제 예시
- 이 방향이 증명하는 JD 요구 개수. 예: "필수 5개 중 4개"
- 증명 못 하는 요구

- 추천 1개와 이유 한 줄. 사용자 선택 뒤 작성 시작

## 버전

문서 폴더마다 작업 파일 하나만 유지. 이력서·포트폴리오 번호는 각각 독립

- 첫 작성: 작업 파일만 생성, 변경 표시 없음
- 수정 요청: 새 번호 파일 없이 작업 파일 갱신. 마지막 확정 버전 대비 바뀐 곳만 `added`·`changed`·`removed`로 표시. `#show:` 줄 바로 다음에 `#changes-legend([{문서} 작업본], [{문서}-{NNNN}])` 범례 블록
- 변경 표시: `#added[새 문장]` 초록 배경, `#changed[이전 문장][새 문장]` 파랑 배경과 아래 줄 회색 이전 문장, `#removed[지운 문장]` 빨간 취소선. 항목 배열 안에서는 `#` 없이 `added[...]`. 끄기: `--input changes=off`
- 확정: 사용자가 명시할 때만("킵하자", "버전 올려" 등). `python3 <이 스킬 폴더>/scripts/versions.py confirm <문서 폴더>` → 표시 반영 본문으로 정리, `{문서}-{NNNN}.typ`·`.pdf`(0001부터, 표시 끔) 저장, 작업 파일도 같은 깨끗한 상태로. 이후 수정은 이 번호 대비 표시
- 바뀐 곳 개수: `python3 <이 스킬 폴더>/scripts/versions.py marks <작업 파일>`
- 제출용: 가장 최근 확정 번호 PDF. 확정 없이 제출 요청이면 확정 여부 질문
