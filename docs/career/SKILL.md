# 이력서와 포트폴리오

JD를 분석하고 경력 원본에서 사실을 골라 고정 양식의 이력서와 포트폴리오 PDF를 지원 폴더에 만든다. 결과물은 Typst로 만든 PDF뿐이고 HTML 결과물이나 미리보기 단계는 없다.

## 언제 쓰나

- 지원 폴더, JD 분석, 경력 원본 읽기와 고르기, 이력서와 포트폴리오의 작성, 버전, 확인, 교정 기록에 쓴다.

## 쓰지 않을 때

- 자기소개서만 쓰는 일에는 쓰지 않는다.

## 입력

- JD(URL, 본문, 파일)와 경력 원본(Hanger closet의 `career/`)이 반드시 있어야 한다. 읽는 방법, 범위, 형식, 양식 대응은 [references/source.md](references/source.md)를 반드시 읽고 따른다. 비공개 원본 주소를 스킬에 적지 않는다.
- 원본이 없으면 빈 원본으로 보고하고 멈춘다. 짧은 이력서나 요약으로 원본을 대신하지 않는다.
- 원본이 덜 채워졌으면 있는 내용만 쓰고 빈 곳을 보고한다.
- 기본값은 이력서와 포트폴리오 둘 다, 한국어, 고정 양식(`assets/typst/`)이다.
- 방향 제안, 확인 결과, 완료 보고 문장을 쓰기 전에 repo-docs `references/plain-language.md`(쉬운 설명 규칙과 낯선 말 목록)를 읽는다.

## 지원 폴더

- 산출물 폴더(공고 폴더와 교정 기록을 두는 폴더, 아래 `<산출물 폴더>`)는 환경 변수 `CAREER_ROOT`이고, 없으면 `~/.config/skills/career.json`의 `root`다. `python3 <이 스킬 폴더>/scripts/versions.py root`로 확인한다. 종료 코드 1이면 사용자에게 한 번 묻고 `versions.py root --set <경로>`로 저장한다. `--set`은 있는 폴더만 저장하고, 없는 폴더면 아무것도 쓰지 않고 종료 코드 1로 끝난다.
- 공고 폴더를 만들기 전에 `versions.py place <공고 폴더>`로 산출물 폴더 아래인지 검사한다. 확정 `confirm`도 같은 검사를 한다. 종료 코드가 0이 아니면 파일을 하나도 만들지 않고 멈춘다.

```text
<산출물 폴더>/
  corrections/                 # 교정 기록
  {마감일}-{회사명}-{직군명}/
    jd.md
    전략.md
    career.typ
    figures/{프로젝트}-{그림}.diagramplay, .svg, .png
    이력서/
      이력서.typ, 이력서.pdf
      이력서-{NNNN}.typ, 이력서-{NNNN}.pdf
    포트폴리오/
      포트폴리오.typ, 포트폴리오.pdf
      포트폴리오-{NNNN}.typ, 포트폴리오-{NNNN}.pdf
```

- 공고 폴더는 `{마감일}-{회사명}-{직군명}/`이다. `career.typ`(양식)와 `figures/`(그림)는 두 문서가 함께 쓴다.
- 문서 폴더는 `이력서/`, `포트폴리오/`다. 작업 파일(`{문서}.typ`) 하나와 확정 버전(`{문서}-{NNNN}.typ`, 4자리)을 둔다.
- 문서 파일은 공고 폴더 기준 절대 경로로 참조한다(`#import "/career.typ": *`, `#diagram("/figures/{프로젝트}-{그림}.png", [...])`). `../`는 Typst가 양식 파일 기준으로 풀어 폴더 밖 오류가 나므로 쓰지 않는다.
- 공고 폴더에서 `typst compile --root . 이력서/이력서.typ`로 만든다. `/`로 시작하는 경로의 기준이 공고 폴더가 되도록 `--root .`를 반드시 붙인다.
- `{마감일}`은 JD 마감일 `YYYY-MM-DD`이고, 상시거나 적혀 있지 않으면 `상시`다. `{회사명}`은 JD 표기 그대로 쓴다. `{직군명}`은 직군 이름만 쓰고 괄호와 경력 조건은 지운다. 공백은 `-`로 바꾸고 `/`는 지운다(`2026-11-30-토스-백엔드-개발자`).
- JD를 받으면 원문을 먼저 읽고, 공고 폴더를 만들고, `jd.md`부터 쓴다.
- 같은 공고를 다시 작업하면 기존 공고 폴더를 쓴다. 다른 공고면 새 공고 폴더를 만든다.
- 경력 원본을 고치지 않는다. 파일에 직접 쓰는 것과 Hanger 변경 요청이 모두 해당한다.
- `전략.md`의 절은 `# 공고 분석`, `# 구성 계획`, `# 작성`, `# 확인`이다. 점수, 선택 JSON, 근거 순위표를 쓰지 않는다.

## 사실 경계

작성과 확인이 함께 쓰는 정본이다.

- JD는 무엇을 강조할지만 정한다. 지원자 사실을 만들어 내지 않는다.
- 신원, 시기, 회사, 프로젝트 경계, 담당 범위(주체), 수치 조건, 공개 범위, 현재 상태(상태)를 그대로 지킨다.
- 조사, 제안, 구현, 빌드, 배포, 운영 관찰, 기기 검증, E2E 검증, 지속 성과를 가른다. 채택되지 않은 제안은 반응과 결과를 사실대로 쓴다.
- 팀 성과는 본인 기여가 분명할 때만 쓴다. 진행 중인 일은 진행 중으로 쓰고, 없는 요구는 공백으로 둔다.
- 수치는 원본에서 확인했고 결과 칸에 방법과 범위가 있을 때만 쓴다. 줄 길이 때문에 조건을 빼야 하면 수치를 지운다.
- `미확인` 칸은 제출 문서에 쓰지 않고 빈 곳으로 보고한다.
- 근거 보강 제안은 `전략.md`의 별도 절에 쓰고 끝난 경험처럼 쓰지 않는다.
- 공백, 참고 같은 메모는 `jd.md`와 `전략.md`에만 둔다. 제출 문서에는 근거, 범위, 상태, 결과만 쓴다.

## 단계

확인 질문 없이 1~4를 이어서 실행한다. 출처가 부딪히거나, 핵심 주장의 담당이나 증명 범위가 불분명하거나, 구조를 바꾸는 시각 요청이 있거나, 산출물 폴더가 정해지지 않았을 때만 묻는다. 지원 방향은 2단계에서 사용자가 고른다.

1. **공고 분석.** [references/jd.md](references/jd.md)를 반드시 읽는다. JD 원문을 확보하고 신원을 확정한 뒤 `jd.md`를 쓴다. 경력 원본(모든 `이력서.md`의 속성과 줄)을 읽는다. `전략.md` 공고 분석 절에 출처와 캡처 시각, 채용 이유, 명시 요구와 추정 요구, 중심 포지셔닝 2~3개, 과장하면 안 되는 사실, 공백을 적는다. 이 단계에서는 사례를 고르거나 순서를 정하지 않는다.
2. **구성 계획.** 공고 분석과 원본을 한 번에 대조한다. 먼저 지원 방향 2~3개를 제안하고(방향 제안 절), 사용자가 고른 뒤 이어 간다. 이력서 선두 성과(원본 줄), 포트폴리오 사례(고른 줄의 짝 묶음), 줄이기와 빼기와 합치기, 순서와 쪽 흐름, 근거 보강 제안을 정하고 짧은 이유를 적는다. 고른 줄의 짝 묶음만 읽는다. 원본 등급은 참고 값이고, 수치 점수, 순위표, 고정 사례 수를 쓰지 않는다.
3. **작성.** [references/writing.md](references/writing.md)를 반드시 읽는다. 양식을 복사하고, 쓰고, 그림을 만들고, 원본을 다시 보며 보강한다. 버전 규칙은 버전 절을 따른다.
4. **확인.** [references/validation.md](references/validation.md)를 반드시 읽는다. 보내기 전과 수정을 반영한 뒤 두 번 확인하고 결과를 `전략.md` 확인 절에 적는다.
5. **완료 보고.** 답변 절을 따른다.

## 방향 제안

구성 계획의 첫 단계에서 지원 방향 2~3개를 제안한다. 하나로 고정해 강요하지 않는다. 방향마다 다음을 보인다.

- 이력서 첫 줄(자기소개 문장)의 실제 예시를 보인다.
- 이 방향이 증명하는 JD 요구 개수를 보인다(예: "필수 5개 중 4개").
- 증명하지 못하는 요구를 보인다.

추천 하나와 이유 한 줄을 붙인다. 사용자가 고른 뒤 작성을 시작한다.

## 고정 양식

- `assets/typst/career.typ`를 지원 폴더에 그대로 복사하고 고치지 않는다. 색, 글꼴, 크기, 간격, helper가 모두 해당한다.
- `resume.typ`는 `이력서/이력서.typ`로, `portfolio.typ`는 `포트폴리오/포트폴리오.typ`로 복사한다. 그 뒤 `{}` 자리를 채우고, 근거 없는 칸과 줄을 지우고, 절, 항목, 사례의 반복 수만 바꾼다. 새 helper나 직접 스타일을 쓰지 않는다.
- 인쇄 문서 양식이라 design-tokens를 적용하지 않는다.

## 그림

- 포트폴리오의 아키텍처와 흐름 그림은 DiagramPlay 정지 그림으로 실제 관계만 그린다. 장식을 넣지 않는다.
- 그림 원본을 쓰기 전에 **repo-docs-figures** 스킬 `references/diagramplay-quality.md`의 가로형 원칙, 쓰임별 기준의 포트폴리오 행, 완료 전 확인을 읽는다. A4 폭에서 가장 작은 글이 읽히도록 카드를 줄이거나 그림을 나눈다.
- `python3 <이 스킬 폴더>/scripts/figures.py <공고 폴더>/figures --diagramplay <DiagramPlay 경로>`로 만든다. SVG와 PNG는 원본 옆(`<공고 폴더>/figures/`)에 생긴다. Python 3.9 이상, Node.js, DiagramPlay 체크아웃, playwright-core Chrome이 필요하다(`CHROME_PATH`는 선택). 원본마다 SVG와 2배 PNG를 만들고 실패하면 종료 코드 1로 끝난다.
- 경력 원본 프로젝트의 `figures/{그림}.diagramplay`를 공고 폴더 `figures/{프로젝트}-{그림}.diagramplay`로 복사한 뒤 만든다. 복사 방법은 [references/source.md](references/source.md)를 따른다.
- `#diagram("/figures/{프로젝트}-{그림}.png", [{결론 한 문장}])`로 넣는다. Typst가 CSS 변수를 지원하지 않으므로 SVG를 직접 넣지 않는다.

## 버전

문서 폴더마다 작업 파일 하나만 둔다. 이력서와 포트폴리오의 번호는 따로 센다.

- 처음 쓸 때는 작업 파일만 만들고 변경 표시를 넣지 않는다.
- 수정 요청을 받으면 새 번호 파일 없이 작업 파일을 고친다. 마지막 확정 버전과 비교해 바뀐 곳만 `added`, `changed`, `removed`로 표시한다. `#show:` 줄 바로 다음에 `#changes-legend([{문서} 작업본], [{문서}-{NNNN}])` 범례 블록을 둔다.
- `#added[새 문장]`은 초록 배경, `#changed[이전 문장][새 문장]`은 파랑 배경과 아래 줄 회색 이전 문장, `#removed[지운 문장]`은 빨간 취소선이다. 항목 배열 안에서는 `#` 없이 `added[...]`로 쓴다. 표시는 `--input changes=off`로 끈다.
- 사용자가 명시할 때만 확정한다("킵하자", "버전 올려" 등). `python3 <이 스킬 폴더>/scripts/versions.py confirm <문서 폴더>`가 표시를 반영한 본문으로 정리하고, `{문서}-{NNNN}.typ`와 `.pdf`(0001부터, 표시 끔)를 저장하고, 작업 파일도 같은 깨끗한 상태로 만든다. 그 뒤 수정은 이 번호와 비교해 표시한다.
- 바뀐 곳 개수는 `python3 <이 스킬 폴더>/scripts/versions.py marks <작업 파일>`로 센다.
- 제출할 때는 가장 최근 확정 번호의 PDF를 쓴다. 확정 없이 제출을 요청하면 확정할지 묻는다.

## 교정

사용자가 사실, 선호, 작업 방식을 바로잡으면 [references/corrections.md](references/corrections.md)를 반드시 읽고 기록한다. 이번 작업에만 바로 반영하고 이전 지원 폴더를 다시 작업하지 않는다.

## 답변

**just-mode** 스킬 답변 절(맨 앞 할 일, 맨 끝 가정)을 따르고 다음을 넣는다.

- 공고 폴더 경로를 적는다.
- 문서별 작업 파일과 확정 버전 번호를 적는다.
- 이번에 바뀐 곳 개수(추가, 바뀜, 삭제)를 적는다.
- 남은 공백을 적는다.
- 다음에 할 일 하나를 적는다.

## 구분

- 경력 원본을 찾고 읽는 방법(Hanger MCP)과 원본에 사실을 더하거나 고치는 일은 [hanger](../hanger/SKILL.md)가 맡는다.
- 포트폴리오 그림 원본의 문법과 배치는 [repo-docs-figures](../repo-docs-figures/SKILL.md)가 맡는다.
