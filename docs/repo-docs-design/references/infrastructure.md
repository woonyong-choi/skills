# 구매 · 구축 · 인프라

적용: SaaS 도입·구매/구축·호스팅 선택과 변경. 먼저 현재 [스펙](requirements.md) 확인. 공급자 이름 대신 같은 사용자 과업을 완료하는 구성으로 비교한다.

후보 → 먼저 확인할 적합 조건 → 비교할 대가:

- 기존 SaaS 설정 → 필요한 업무·권한·데이터 입출력이 기본 기능으로 충족 → 변경 가능 범위·반출·종속
- SaaS + API 연동 → 필요한 차이를 확장·연동으로 충족 → API 한도·동기화·인증·중복/실패 처리
- 관리형 서비스 조합 → 고유 화면·업무 규칙을 구현하고 실행/DB/인증 등을 위탁 → 남는 개발·보안·운영 책임과 서비스별 한도
- 직접 구축·운영 → 계약·통제·운영상의 이점과 운영 가능 근거 존재 → 개발·배포·패치·관측·복구·인력·이전 책임

- 위 후보는 단계별 강제 통과 목록이 아닌 비교 후보. 현재 구성 재사용·혼합도 허용. 모두 미충족이면 제약 조정안을 설명하고 선택 전 구현 보류
- 클라우드 공급자 하나에도 관리형·직접 운영 구성이 공존. 공급자 이름과 SaaS라는 범주를 동등한 후보로 점수화 금지

## 후보 비교

확정할 것 → 후보마다 확인 → 탈락·보류 기준:

- 필요한 기능 → 같은 사용자 과업·권한·변경 자유도·연동·내보내기. 필요한 실행/DB/파일/인증/큐/관측의 포함 범위 → 미요청 기능을 필요로 만들어 후보 선정 금지
- 실행 계약 → 지원 언어·배경 작업·시간 제한·연결 수·영속성·리전·네트워크 → 필수 계약 위반은 근거와 제외. 미확인은 확인 전 확정 금지
- 운영 책임 → 설치·패치·배포·백업·복원·모니터링·장애 대응의 담당자·작업 시간 → 관리형도 남는 책임 명시. 담당자 미정을 운영 가능으로 간주 금지
- 보존·철수 → 내보내기 형식·이전 경로·인증/파일/DB 의존·중단 시간·나가는 트래픽 → 코드 교체만으로 데이터·권한 이전 완료 판정 금지

- 스펙에 맞는 실제 후보만 비교. 후보 수 채우기 금지. 필수 조건별 근거·충족/위반/미확인 대조, 미확인 조건이 남은 후보에 전체 통과 표시 금지
- 로컬/원격과 관리형/직접 운영은 별도 축. 특정 공급자에 관리형 서비스가 없다고 가정하는 비대칭 비교 금지
- 현재 버전·리전·서비스 등급의 공식 기능·한도·확인일 기록. 조회 불가면 후보와 확인 방법만 제시, 가능 여부 확정 금지
- 결론: 충족 스펙·남는 책임·추천이 바뀌는 조건. 시험 후보 추천과 운영 도입 분리
