# 스펙 확정

새 제품이나 기능을 만들거나 규모, 보장을 바꿀 때 스펙을 정한다. 기존 요청, 코드, 측정에서 뽑고, 없는 값은 미확인으로 둔다.

## 스펙 항목

- 스펙 한 항목은 대상과 입력 조건, 기대 결과와 허용 차이, 넘치거나 실패할 때의 동작, 검사로 이루어진다.
- 수치는 값, 단위, 집계 구간, 대상, 근거를 함께 적는다.
- 요구, 관측, 공식 제한, 가정을 가른다.
- 새 제약과 조건 충돌은 [요구 확인](../SKILL.md#요구-확인)을 따른다.

| 조건 | 반드시 할 일 | 통과와 차단 |
|---|---|---|
| 기능 | 사용자, 입력 예, 끝났을 때의 결과, 실패했을 때의 결과, 보존, 제외를 정한다 | 같은 입력의 기대 결과를 계산하거나 관측할 수 없으면 그 요구는 정해지지 않은 것이다. 관례적인 CRUD나 병합 정책을 요청하지 않은 기능이나 합격선으로 더하지 않는다 |
| 입력과 성장 | 필드, 형식, 건당 bytes, 허용 최대, 하루 증가량, 보관 기간을 확인한다 | 건수만으로 메모리나 디스크를 셈하지 않는다. 확인하지 않은 최대를 무제한 허용으로 구현하지 않는다 |
| 부하 | 초, 분, 하루 단위 요청 수, 최대 지속 시간, 읽기와 쓰기 비중, 입력 분포를 확인한다 | 건수만으로 부하나 용량이 충분하다고 주장하지 않는다. 하루 부하와 순간 부하, 동시 사용자와 동시 실행과 DB 연결을 가른다 |
| 응답과 자원 | 사용자가 견딜 수 있는 대기와 측정의 시작과 끝, 집계 조건을 정한다. CPU, 메모리, 디스크, 전송, 호출 상한은 요청, 프로세스, 전체 단위로 가른다 | 고정 상한, 백분위, 안전 배수를 마음대로 만들지 않는다. 상한을 넘을 때 거절할지, 기다릴지, 나눌지 고른다 |
| 저장과 정확성 | 저장이 끝나는 시점, 잃어도 되는 기간, 오래된 값 허용, 부분 성공, 같은 ID에 다른 내용, 순서가 뒤바뀐 경우의 결과를 정한다 | 정상 종료, 강제 종료, 기기 손실을 나눈다. "무손실", "최신", "한 번"이라는 말만으로 정하지 않는다 |
| 운영 | 실행 플랫폼, 리전, 운영자, 가용 시간, 멈춰도 되는 시간과 복구 시간을 확인한다 | 실행이 성공했다는 것만으로 운영할 수 있다고 판정하지 않는다 |

- 숫자나 정책이 다음 선택을 바꾸고, 되돌릴 수 없고, 해석이 둘 이상일 때만 사용자에게 확정을 묻는다(mode 질문 분류). 그 밖에는 가정으로 진행한다. 코드, 설정, 계측으로 확인할 수 있는 사실은 먼저 조사하고, 모르는 제품 의도는 사용자가 판단할 차이로 설명한다.
- 수치가 정해지지 않았으면 비교에 필요한 범위와 확인 방법을 보인다. 승인받지 않은 추정치를 합격선으로 쓰지 않는다. 그 선택과 상관없는 항목은 이유를 적고 뺀다.
- 넘치거나 실패하는 입력도 완료 검사에 잇는다. 예를 들어 같은 ID에 다른 본문이 오면 유지할지, 바꿀지, 거절할지 정해지지 않았으면 저장 구현을 미룬다. 이미 골랐으면 그 결과를 검사한다.

## 과잉·누락 설계 검사

1. 구성 요소와 제약마다 지금의 요구나 근거 있는 가까운 요구를 잇는다.
2. 빼거나, 기존 기능을 쓰거나, 더 단순하게 구성해도 같은 결과, 보존, 보안, 복구를 채우는지 비교한다.
3. 더해지는 코드, 자원, 배포 단위, 장애 지점, 운영과 이전 부담을 얻는 효과와 대조한다.
4. 효과 근거가 없으면 도입을 미룰 후보로 둔다. 다시 필요해지는 관측 조건을 적는다.

- 기술 이름만으로 과잉이라고 판정하지 않는다. 작은 서비스도 중복 효과, 권한 우회, 데이터 손실을 반드시 점검한다.
- 사용자가 한 명이어도 여러 탭, 자동 저장, 재전송 경로를 확인한다. 재고 음수, 부분 성공, 오래된 값 허용은 업무가 고를 일이다. 권장안을 필수 조건으로 올리지 않는다.
- 작은 규모에서 지금의 요구를 채우면 대규모 처리 기준은 미룬다. 건수가 작다는 이유만으로 큰 입력, 동시성, 장애 경로를 빼지 않는다.
- 앞으로의 성장만을 근거로 쓰지 않는 계층, 플러그인, 분산 구조를 더하지 않는다. 지금의 요구를 채우는 작은 구조와 바꿀 경계를 먼저 고른다.
