# 스펙 확정

적용: 신규 제품·기능, 규모·보장 변경. 기존 요청·코드·측정에서 추출하고 없는 값은 미확인으로 유지.

스펙 한 항목: `대상·입력 조건 → 기대 결과·허용 차이 → 초과·실패 동작 → 검사`. 수치는 `값·단위·집계 구간·대상·근거`로 기록. 요구/관측/공식 제한/가정 구분. 새 제약·조건 충돌: [요구 확인](../SKILL.md#요구-확인)

조건 → 필수 행동 → 통과·차단:

- 기능 → 사용자·입력 예·완료 결과·실패 결과·보존·제외 지정 → 같은 입력의 기대 결과를 계산·관측할 수 없으면 해당 요구 미확정. 관례적 CRUD·병합 정책을 미요청 기능·합격선으로 추가 금지
- 입력·성장 → 필드·형식·건당 bytes·허용 최대·일일 증가·보관 기간 확인 → 건수만으로 메모리·디스크 산정 금지. 미확인 최대를 무제한 허용으로 구현 금지
- 부하 → 초/분/일별 요청 수·최대 지속·읽기/쓰기 비중·입력 분포 확인 → 건수만으로 부하·용량 충분 주장 금지. 일일/순간 부하, 동시 사용자/실행/DB 연결 구분
- 응답·자원 → 사용자 대기 허용과 측정 시작/끝·집계 조건 지정. CPU/메모리/디스크/전송/호출 상한은 요청·프로세스·전체 단위 구분 → 고정 상한·백분위·안전 배수를 임의 생성 금지. 상한 초과의 거절/대기/분할 동작 선택
- 저장·정확성 → 저장 완료 시점·허용 손실 기간·오래된 값 허용·부분 성공·동일 ID/다른 내용·순서 역전의 결과 지정 → 정상 종료/강제 종료/기기 손실 분리. “무손실/최신/한 번”만으로 확정 금지
- 운영 → 실행 플랫폼·리전·운영자·가용 시간·중단/복구 허용 시간 확인 → 실행 성공만으로 운영 가능 판정 금지

- 숫자·정책이 다음 선택을 바꾸고 되돌릴 수 없으며 해석이 둘 이상일 때만 확정 질문(developer-thinking 진행 규칙), 그 밖은 가정으로 진행. 코드·설정·계측으로 확인 가능한 사실은 먼저 조사, 모르는 제품 의도는 사용자가 판단할 차이로 설명
- 수치 미정: 비교에 필요한 범위와 확인 방법 제시. 승인 없는 추정치를 합격선으로 사용 금지. 해당 선택에 무관한 항목은 이유와 함께 제외
- 초과·실패 입력도 완료 검사에 연결. 예: 같은 ID·다른 본문이 유지/교체/거절 중 미결정이면 저장 구현 보류, 이미 선택됐다면 그 결과를 검사

## 과잉·누락 설계 검사

1. 구성 요소·제약마다 현재 요구 또는 근거 있는 가까운 요구 연결
2. 생략·기존 기능·더 단순한 구성으로 같은 결과·보존·보안·복구 충족 여부 비교
3. 추가 코드·자원·배포 단위·장애 지점·운영·이전 부담과 얻는 효과 대조
4. 효과 근거가 없으면 도입 보류 후보. 다시 필요해지는 관측 조건 제시

- 기술 이름만으로 과잉 판정 금지. 작은 서비스도 중복 효과·권한 우회·데이터 손실 점검 필수
- 단일 사용자도 여러 탭·자동 저장·재전송 경로 확인. 재고 음수·부분 성공·오래된 값 허용은 업무 선택, 권장안을 필수 조건으로 승격 금지
- 작은 규모에서 현재 요구를 충족하면 대규모 처리 기준 도입 보류. 건수만 작다는 이유로 큰 입력·동시성·장애 경로 제외 금지
- 미래 성장만을 근거로 미사용 계층·플러그인·분산 구조 추가 금지. 현재 요구를 만족하는 작은 구조와 변경 경계 우선
