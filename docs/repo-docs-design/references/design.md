# design/{주제}.md

- 독자: 기여자와 검토자. 답할 질문: 왜 필요한가, 어떻게 동작하나, 무엇이 아직 미정인가
- 파일 이름: 기능 주제의 영어 소문자 kebab-case `input-handling.md`
- 주제: 사용자가 알아볼 수 있는 기능 단위. 관련 모듈의 설명은 상세 설계, 기능과 무관한 구조 설명은 architecture
- 머리: `# {주제 이름}`과 상태 표

```text
| 항목 | 값 |
|---|---|
| 상태 | 제안 |
| 관련 결정 | [{관련 결정}](../decisions/{결정 파일}.md) |
```

| 상태 | 뜻 |
|---|---|
| 제안 | 검토 중. 요구사항 표의 필수 동작에 미해결 질문 존재 |
| 결정 | 요구사항 표의 필수 동작 모두 승인 근거 존재. 구현 근거는 아직 미충족 |
| 구현 | 요구사항 표의 필수 동작 모두 repo-docs 사실 상태의 구현 근거 충족 |

- 사실 상태와 대응: 필수 동작 중 미정이 있으면 제안, 모두 승인됐지만 구현 근거 미충족이면 결정, 모두 구현 근거 충족이면 구현. 사용 가능은 별도의 실제 실행 근거 필수(repo-docs 사실 상태)

| 순서 | 한국어 절 | 영어 절 | 필수 | 내용 |
|---|---|---|---|---|
| 1 | `요약` | `Summary` | 필수 | 한 문단. 무엇을 하는 기능인지 |
| 2 | `동기` | `Motivation` | 필수 | 누가 어떤 상황에서 무엇이 어려운지, 이 기능이 없으면 생기는 일 |
| 3 | `예시` | `Examples` | 필수 | 요구사항별 동작 차이가 드러나는 사용 장면. 이미 있는 기능처럼 현재형으로 |
| 4 | `상세 설계` | `Design` | 필수 | 규칙, 상태, 흐름, 오류 처리, 요구사항 |
| 5 | `단점` | `Drawbacks` | 선택 | 이 설계가 치르는 비용 |
| 6 | `대안` | `Alternatives` | 선택 | 버린 선택지 한 줄씩과 결정 기록 링크 |
| 7 | `미해결 질문` | `Unresolved questions` | 미정이 있으면 필수 | 질문과 저장소 추적 링크 또는 내부 질문 식별자 |

| 자리 | 규칙 |
|---|---|
| 예시 | `###` 하나가 장면 하나. 번호 목록의 단계마다 한 문장. 사용자가 보는 것과 시스템이 하는 일 |
| 상세 설계 | `###`으로 나누기. 단계 목록은 문장. 수치의 근거 링크와 미해결 질문 기준(repo-docs references/writing.md 문장) |
| 상세 설계 상태 표 | 전이와 조건을 조회할 필요가 있는 대상. `상태`, `뜻`, `다음 상태` |
| 요구사항 표 | 상세 설계 마지막 `### 요구사항`. `요구사항`(문장), `검증 계획`(테스트나 실험이 확인할 내용). 테스트가 생기면 `검증 계획`을 `{파일 경로}`의 `{테스트 이름}`으로 교체 |
| 미해결 질문 | 추적기 사용 시 `- {질문} ([#{번호}]({이슈 URL}))`, 없으면 `- {질문 ID}: {질문} ({결정 근거 링크})`. 질문의 선택지 명시 |
| 기호 | 처음 나오는 문장에서 정의(repo-docs references/writing.md 문장) |

- 설정 값, 메시지 형식, 테이블 구조: 코드에 들어간 뒤 spec 문서로 옮기고 여기는 링크만
