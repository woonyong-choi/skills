# design/{주제}.md

- 독자: 기여자와 검토자. 답할 질문: 왜 필요한가, 어떻게 동작하나, 무엇이 아직 미정인가
- 파일 이름: 기능 주제의 영어 소문자 kebab-case `input-handling.md`
- 주제: 사용자가 알아볼 수 있는 기능 단위. 모듈 설명 배치: architecture.md 세부 분리

상태 → 뜻:

- 제안 → 검토 중. 요구사항 표의 필수 동작에 미해결 항목 존재
- 결정 → 요구사항 표의 필수 동작 모두 승인 근거 존재. 구현 근거는 아직 미충족
- 구현 → 요구사항 표의 필수 동작 모두 repo-docs 사실 상태의 구현 근거 충족

- 사용 가능은 별도의 실제 실행 근거 필수(repo-docs 사실 상태)

순서 → 한국어 절 → 영어 절 → 필수 → 내용:

- 1 → `요약` → `Summary` → 필수 → 한 문단. 무엇을 하는 기능인지. 아래에 `하지 않는 것`(영어 `Non-goals`) 목록, 해당 시
- 2 → `해결하는 문제` → `Motivation` → 필수 → 누가 어떤 상황에서 무엇이 어려운지, 이 기능이 없으면 생기는 일
- 3 → `사용 예` → `Examples` → 필수 → 요구사항별 동작 차이가 드러나는 사용 장면. 현재형
- 4 → `작동 방식` → `Design` → 필수 → 규칙, 상태, 흐름, 오류 처리, 요구사항
- 5 → `단점` → `Drawbacks` → 선택 → 이 설계가 치르는 비용
- 6 → `대안` → `Alternatives` → 선택 → 버린 방법 한 줄씩과 결정 기록 링크
- 7 → `미해결` → `Unresolved questions` → 미정이 있으면 필수 → 질문과 추적 링크

| 요구사항 | 검증 계획 |
|---|---|
| {요구사항 문장} | {테스트나 실험이 확인할 내용} |

## 대안

자리 → 규칙:

- 하지 않는 것 → 이 기능에 붙어 기대될 만한 일만, 최대 5개. 항목마다 이유 또는 옮긴 곳(설계 문서·이슈 링크) 필수. 해당 없으면 굵은 줄까지 생략. 대안·단점·미해결과 혼합 금지
- 사용 예 → `###` 하나가 장면 하나. 단계마다 한 문장
- 작동 방식 → `###`으로 나누기. 단계 목록은 문장. 수치 근거(repo-docs references/writing.md). 상태 전이가 있으면 `상태`, `뜻`, `다음 상태` 표
- 요구사항 → 작동 방식 마지막 `###`. 테스트가 생기면 검증 계획을 `{파일 경로}`의 `{테스트 이름}`으로 교체
- 미해결 → 추적기 없으면 `- {질문 ID}: {질문} ({결정 근거 링크})`
- 설정 값, 메시지 형식, 테이블 구조: 코드에 들어간 뒤 spec 문서로 옮기고 여기는 링크만
