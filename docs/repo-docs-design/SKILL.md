# 설계 문서

요구를 확인하고 구조, 동작, 운영의 선택지를 비교해 고른 뒤, 그 설계를 설계 문서에 쓰고 코드와 잇는다. 문서를 쓰거나 갱신할 때는 [repo-docs](../repo-docs/SKILL.md)와 이 스킬의 템플릿을 먼저 따른다.

## 적용

- 기능, 규모, 보장을 바꿀 때는 [references/requirements.md](references/requirements.md)를 반드시 읽는다.
- 구매, 구축, 호스팅을 고를 때는 [references/infrastructure.md](references/infrastructure.md)를 반드시 읽는다.

## 요구 확인

- 요청, 기존 결정, 코드, 측정에서 결과, 보존, 제외, 검사를 뽑는다. 사용자에게 양식을 채우라고 하지 않는다.
- 확인할 수 있는 사실은 조사하고, 정하지 않은 제품 의도는 대안을 비교한다. 조회에 실패한 것을 사용자 취향의 문제로 넘기지 않는다.
- 새 제약은 출처(요구, 관측, 공식 계약, 가정), 적용 조건, 어겼을 때의 피해를 확인한다. 가정을 필수 요구나 합격선으로 올리지 않고, 근거 없는 상한이나 정책을 구현하지 않는다.
- 조건이 부딪히면 함께 채울 수 없는 근거와 범위, 자원, 보장의 조정안을 보인다. 사용자가 고르기 전에는 기존 조건을 느슨하게 하거나 강하게 하지 않는다.

## 선택

1. 지금의 스펙에서 가능한 대안을 비교한다. 구현하지 않기, 기존 방식, 표준 기능, 구매, 구축 중 유효한 안만 넣는다.
2. 같은 입력, 보장, 환경, 기간에서 결과, 실패, 개발과 운영과 이전 부담을 대조한다. 필수 조건 위반을 다른 장점으로 메우지 않는다.
3. 추천 이유와 추천이 불리해지는 조건, 그 조건을 확인하는 방법을 보인다. 안들이 같으면 같다고 밝히고 고르는 기준을 적는다. 지금 결정과 상관없는 가상 반례는 조사하지 않는다.
4. 결과, 보존, 권한, 운영이 달라지는 미결정은 되돌릴 수 없고 해석이 둘 이상일 때만 사용자가 고르게 한다. 그 밖에는 추천안으로 진행하고 가정을 한 줄 적는다(mode 질문 분류).
5. 누가 무엇을 골랐는지, 그 범위, 남은 미확인을 기존 이슈와 결정 기록(**git-issue** 스킬의 과업 연결과 기록 절)에 넘긴다. 비교는 채팅에서 먼저 하고, 고르라는 요청만으로 새 문서를 만들지 않는다.

- 사소하고 되돌릴 수 있는 세부와 이미 고른 것, 위임받은 범위는 이유를 적고 진행한다. 명시된 값, 단위, 시점, 선택은 부딪히는 근거가 없으면 다시 해석하거나 다시 묻지 않는다.
- 가능한 안이 하나면 다른 안을 뺀 근거와 남은 제약을 설명한다. 승인 범위 안이면 진행한다.
- 확인하지 않은 후보를 불가능하다고 빼거나 비교 전에 최적안을 정하지 않는다. 이미 만든 구현으로 선택을 정당화하지 않는다.
- 코드베이스에 선례가 없는 UI 상호작용이나 아키텍처 결정은 **architect** 스킬과 **principle-exhaust-the-design-space** 스킬의 설계안 비교를 따른다. 그 밖에는 유효한 안만 두고 안 개수를 채우지 않는다.
- 고르기 전에는 조사, 비교, 꼭 필요한 최소 실험만 한다. 고른 안에 기대는 제품 구현은 하지 않는다. 남은 모든 대안에서 유효한 독립 승인 작업은 계속한다.
- 제품, 공급자, 프레임워크를 기본값으로 정하지 않는다. 이미 합의한 스택은 그 범위에서 다시 쓴다.
- 바뀔 수 있는 기능, 한도, 라이선스는 공식 버전, 리전, 서비스 등급, 확인일을 조회한다. 조회할 수 없으면 후보와 확인 방법만 보이고 가능 여부를 정하지 않는다. 조회와 실제 호환, 복구 검증을 나눈다.
- 수치 판단에는 적용 버전, 단위, 기준값, 예외, 실행 비용을 잇는다. 측정하지 않은 값을 추정으로 확정하지 않는다. 성능이나 호환성이 선택을 바꾸면 대표 입력으로 최소 실행을 해 확인하고 결과를 기존 기록에 넘긴다. 문서로 남기는 조건은 [repo-docs-note](../repo-docs-note/SKILL.md)와 [repo-docs-experiment](../repo-docs-experiment/SKILL.md)의 대상을 따른다. 요청하지 않은 기능을 고르는 근거로 더하지 않는다.
- 위임받은 범위나 이미 고른 범위를 넓히지 않는다. 저장 위치를 고르는 일과 제품을 고르는 일, 구현을 맡는 일과 보존 방식을 바꿀 권한을 나눈다.

## 설명과 조사

- 대안은 같은 실제 입력의 처리, 저장, 외부 효과, 응답과 실패 뒤 상태로 설명한다.
- 경계마다 실행 주체, 입출력 단위, 상태 소유자, 책임을 확인한다. 추상 상자를 늘어놓는 것으로 설명을 대신하지 않는다.
- 이해가 막힌 곳은 그 결정에 필요한 개념만 예제, 도식, 최소 코드로 설명한다.
- 같은 값, 단위, 시점에서 조건 하나를 바꿨을 때의 결과와 이유를 확인한다. 비유나 모델의 동의를 정확성의 증거로 쓰지 않는다.
- 사용자가 한 설명과 대신 써 준 답변을 가른다. 사용자가 제약을 다르게 이해했으면 그 차이를 바로잡고 선택과 잇는다. 무응답을 선택, 이해, 무지로 짐작하지 않고, 일상 작업마다 이해 시험을 시키지 않는다.
- 새 자료는 기존 기준과 다른 주장과 조건부터 고른다. 받아들일 내용은 원문, 적용 범위, 반례를 확인한다.
- 배우려고 하는 실험과 제품 반영을 나눈다. 실행이 성공했다는 것만으로 이해나 제품 검증이 끝났다고 판정하지 않는다.
- 새 근거는 기존 전제와 대조해 영향을 받는 선택만 다시 검토한다. 근거 없는 해석을 확정하지 않고, 과거 선택의 이유, 의도, 발견한 사람을 지어내지 않는다.

## 구조 경계

- 요구를 상태, API, 데이터로, 그것을 컴포넌트로, 컴포넌트를 검사로 잇는다.
- 표현, 업무 계산, 데이터 접근을 가르고 정본, 파생 화면, 캐시의 책임과 의존 방향을 가른다. 지금 바뀌는 이유, 계약, 검사 책임이 다를 때만 나누거나 새 계층을 검토한다.
- 제품, 배치, 기능을 가른다. 로컬과 원격, 내장과 별도 프로세스, 관리형과 직접 운영은 서로 다른 축이다. 인터넷을 쓰는지만으로 서버 구조나 로컬 우선 구조를 단정하지 않는다.
- 무언가를 교체할 때는 읽기와 쓰기 소비자, 기존 데이터, 혼합 버전, 배포 순서, 역변환을 확인한다. 코드 롤백과 데이터 복구를 나눈다.

## 새 기능을 넣는 자리

| 새로 정할 것 | 넣는 자리 |
|---|---|
| 기능의 목적, 동작, 요구사항 표 | `design/{주제}.md` |
| 구성 요소와 경계, 깨면 안 되는 조건 | `architecture.md` |
| 프로젝트 고유 용어 | `glossary.md` 표의 행 |
| 코드에 들어간 메시지, 명령, 키, 테이블, 설정 키, 오류 코드 | [repo-docs-spec](../repo-docs-spec/SKILL.md) 문서 |
| 선택지 중 하나를 고른 이유 | `decisions/{날짜}-{주제}.md`([repo-docs-decision](../repo-docs-decision/SKILL.md)) |
| 측정이 필요한 값 | `experiments/{실험}/`([repo-docs-experiment](../repo-docs-experiment/SKILL.md)). 그 전에는 `미해결` |
| 구조와 흐름 그림 | [repo-docs-figures](../repo-docs-figures/SKILL.md)의 도구와 파일 |

## 공통 규칙

- 설계 문서는 설계한 동작을 현재형으로 쓴다. 진행 상황, 날짜, 담당자를 쓰지 않는다. 상태는 상태 표 한 칸에만 쓴다.
- 지금의 설계만 쓴다. 바뀐 이력과 옛 설계를 쓰지 않는다. 버린 선택지는 `대안` 절에 쓴다.
- 정하지 않은 것은 `미해결` 절(design.md 형식)에 쓰고 본문에 확정된 것처럼 쓰지 않는다.
- 파일을 나눌 때는 각 문서가 다른 독자 질문에 답하는지, 한쪽 설명을 바꿔도 다른 쪽을 함께 바꿀 필요가 없는지 따진다. 줄 수만으로 나누지 않는다.

## 요구사항

- 요구는 요구 확인 절에서 뽑은 결과, 보존, 제외, 검사를 다시 쓴다. 작업 요구는 이슈(**git-issue** 스킬)에, 설계 문서 요구는 요구사항 표(design.md)에 적는다.
- 문서의 요구 범위와 검증 범위를 맞춘다.
- 자동 생성한 문서나 표는 원본 요구 설명이 정확한지와 생성물이 원본과 같은지를 따로 확인한다.
- 기능을 더할 때는 그 기능을 빼도 기존 의미가 그대로인 사례를 정한다.

## 코드로 옮기기

| 내용 | 계약이 코드에 들어가기 전 | 들어간 뒤 |
|---|---|---|
| 목적, 흐름, 규칙과 이유 | 설계 문서 | 설계 문서 |
| 타입으로 드러나는 함수와 타입의 입출력 | 설계 문서 작동 방식 | 코드의 타입 정의. 설계 문서에는 요약과 링크 |
| 타입으로 드러나지 않는 실패 조건, 제약 | 설계 문서 작동 방식 | 시험과 설계 문서. 공개 API면 그 API 문서 주석에도 쓴다(**mode** 스킬의 주석 절) |
| 메시지, 명령, 설정, 테이블, 오류 코드 | 설계 문서 작동 방식 | spec 문서 |
| 할 일 | 이슈 | 이슈와 `TODO(#{번호})` |
| 동작 예시와 완료 조건 | 설계 문서 예시, 이슈 | 시험. 요구사항 표의 `검증 계획`을 바꾼다 |

## 답변

- 비교한 대안, 추천과 그 이유, 추천이 불리해지는 조건을 적는다.
- 사용자가 골라야 하는 미결정이 있으면 맨 앞에 적는다.
- 문서를 썼으면 쓰거나 고친 파일 경로와 남은 `미해결` 항목을 적는다.

## 구분

- 코드에 들어간 인터페이스 문서(프로토콜, 명령, 화면, 데이터, 설정, 오류)는 [repo-docs-spec](../repo-docs-spec/SKILL.md)이 맡는다.
- 코드 주석으로 남겨도 되는 범위는 **mode** 스킬의 주석 절이 맡는다.
- 맥락, 구성 요소, 순서, 상태 그림은 [repo-docs-figures](../repo-docs-figures/SKILL.md)가 맡는다.
- 대안을 고른 근거의 공개 기록은 [repo-docs-decision](../repo-docs-decision/SKILL.md)이 맡는다.
- 설계 값 측정은 [repo-docs-experiment](../repo-docs-experiment/SKILL.md)가 맡는다.
- PR의 문서 동반 확인은 **git-pull-request** 스킬의 문서 동반 절이 맡는다.
