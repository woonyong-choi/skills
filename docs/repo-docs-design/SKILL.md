# Repo Docs Design

- 우선순위: 사용자 지시 → 저장소 규칙 → 이 스킬. 범위 밖은 명시한 소유 스킬 적용
- 기반: repo-docs 먼저 적용(문서 작성·갱신 때만, 해당 템플릿 포함). 이 스킬 범위: 제품 요구·구조·동작·운영 선택과 설계 문서 구성·코드 연결
- 필요할 때만 읽기: 코드에 들어간 인터페이스 문서(프로토콜, 명령, 화면, 데이터, 설정, 오류) → repo-docs-spec; 타입으로 드러나지 않는 실패 조건·제약을 코드 주석으로 옮길 때 → code-style; 맥락, 구성 요소, 순서, 상태 그림 → repo-docs-figures; 대안 선택 근거 기록 → repo-docs-decision; 설계 값 측정 → repo-docs-experiment; 문서 동반 확인 → git-pull-request의 문서 동반 절

## 적용

- 기능·규모·보장 변경은 [requirements.md](references/requirements.md) 필수 확인
- 구매·구축·호스팅 선택은 [infrastructure.md](references/infrastructure.md) 필수 확인

## 요구 확인

- 요청·기존 결정·코드·측정에서 결과·보존·제외·검사 추출. 사용자에게 양식 작성 요구 금지
- 확인 가능한 사실은 조사, 제품 의도의 미결정은 대안 비교. 조회 실패를 사용자 취향으로 전가 금지
- 새 제약은 출처(요구/관측/공식 계약/가정)·적용 조건·위반 피해 확인. 가정을 필수 요구나 합격선으로 승격, 근거 없는 상한·정책 구현 금지
- 조건 충돌은 함께 충족할 수 없는 근거와 범위·자원·보장의 조정안 제시. 사용자 선택 없이 기존 조건 완화·강화 금지

## 선택

1. 현재 스펙에서 가능한 대안 비교. 구현 생략·기존 방식·표준 기능·구매·구축 중 유효한 안만 포함
2. 같은 입력·보장·환경·기간에서 결과·실패·개발/운영/이전 부담 대조. 필수 위반을 다른 장점으로 상쇄 금지
3. 추천 이유와 추천이 불리해지는 조건·확인 방법 제시. 동등하면 동등함과 선택 기준 명시. 현재 결정과 무관한 가상 반례 조사 제외
4. 결과·보존·권한·운영이 달라지는 미결정: 되돌릴 수 없고 해석이 둘 이상이면 사용자 선택, 그 밖은 추천안으로 진행하고 가정 한 줄(developer-thinking 진행 규칙)
5. 선택 주체·범위와 남은 미확인을 기존 이슈·Continuity 기록(git-issue)에 전달. 비교는 채팅 우선, 선택 요청만으로 새 문서 생성 금지

- 사소하고 가역적인 세부, 기존 선택·위임 범위는 이유와 함께 진행. 명시된 값·단위·시점·선택은 충돌 근거 없이 재해석·재질문 금지
- 가능한 안이 하나면 배제 근거·남은 제약 설명. 승인 범위 안이면 진행
- 미확인 후보를 불가능으로 제외하거나 비교 전 최적안 확정 금지. 안 개수 채우기·이미 만든 구현으로 선택 정당화 금지
- 선택 전 조사·비교·필요한 최소 실험만 수행. 종속 제품 구현 금지, 남은 모든 대안에서 유효한 독립 승인 작업 계속
- 제품·공급자·프레임워크 기본값 금지. 기존 합의 스택은 해당 범위에서 재사용
- 변할 수 있는 기능·한도·라이선스는 공식 버전·리전·서비스 등급·확인일 조회. 조회 불가면 후보와 확인 방법만 제시, 가능 여부 확정 금지. 조회와 실제 호환·복구 검증 구분
- 수치 판단은 적용 버전·단위·기준값·예외·실행 비용 연결, 미측정값 추정 확정 금지. 성능·호환성이 선택을 바꾸면 대표 입력의 최소 실행으로 확인, 결과는 기존 기록에 전달(문서 기록 조건: repo-docs-note·repo-docs-experiment 대상). 미요청 기능을 선정 근거로 추가 금지
- 위임·기존 선택 범위 확대 금지. 저장 위치 선택은 제품 선택과, 구현 위임은 보존 변경 권한과 구분

## 설명과 조사

- 대안은 같은 실제 입력의 처리·저장·외부 효과·응답과 실패 후 상태로 설명
- 각 경계의 실행 주체·입출력 단위·상태 소유자·책임 확인. 추상 상자 나열로 설명 대체 금지
- 이해가 막힌 부분은 해당 결정에 필요한 개념만 예제·도식·최소 코드로 설명
- 같은 값·단위·시점에서 조건 하나 변경 시 결과와 이유 확인. 비유나 모델 동의를 정확성 증거로 사용 금지
- 사용자 설명과 대신 작성한 답변 구분. 제약을 다르게 이해했다면 차이를 바로잡고 선택 연결. 무응답을 선택·이해·무지로 추정하거나 일상 작업마다 이해 시험 강제 금지
- 새 자료는 기존 기준과 다른 주장·조건부터 선별. 채택할 내용은 원문·적용 범위·반례 확인
- 학습용 실험과 제품 반영 구분. 실행 성공만으로 이해·제품 검증 완료 판정 금지
- 새 근거는 기존 전제와 대조하여 영향받는 선택만 재검토. 근거 없는 해석 확정·과거 선택 이유·의도·발견 주체 창작 금지

## 구조 경계

- 요구 → 상태·API·데이터 → 컴포넌트 → 검사 연결
- 표현·업무 계산·데이터 접근과 정본·파생 화면·캐시의 책임·의존 방향 구별. 현재 변경 이유·계약·검사 책임이 다를 때만 분리·새 계층 검토
- 제품·배치·기능을 구별. 로컬/원격, 내장/별도 프로세스, 관리형/직접 운영은 서로 다른 축. 인터넷 사용 여부로 서버·로컬 우선 구조 단정 금지
- 교체 시 읽기/쓰기 소비자·기존 데이터·혼합 버전·배포 순서·역변환 확인. 코드 롤백과 데이터 복구 구분

## 새 기능을 넣는 자리

새로 정할 것 → 넣는 자리:

- 기능의 목적, 동작, 요구사항 표 → `design/{주제}.md`
- 구성 요소와 경계, 깨면 안 되는 조건 → `architecture.md`
- 프로젝트 고유 용어 → `glossary.md` 표의 행
- 코드에 들어간 메시지, 명령, 키, 테이블, 설정 키, 오류 코드 → repo-docs-spec 문서
- 선택지 중 하나를 고른 이유 → `decisions/{날짜}-{주제}.md` (repo-docs-decision)
- 측정이 필요한 값 → `experiments/{실험}/` (repo-docs-experiment), 그 전에는 `미해결`
- 구조와 흐름 그림 → repo-docs-figures 도구와 파일

## 공통 규칙

- 설계 문서: 설계한 동작을 현재형으로. 진행 상황, 날짜, 담당자 금지. 상태는 상태 표 한 칸에만
- 현재 설계만. 바뀐 이력, 옛 설계 금지. 버린 선택지는 `대안` 절
- 정해지지 않은 것: `미해결` 절(design.md 형식). 본문에 확정처럼 쓰기 금지
- 파일 분리: 각 문서가 다른 독자 질문에 답하고, 한쪽의 설명을 바꿔도 다른 쪽 설명을 함께 바꿀 필요가 없는지 검토. 줄 수만으로 분할 금지

## 요구사항

- 요구는 요구 확인의 결과·보존·제외·검사 재사용. 작업 요구 기록은 이슈(git-issue), 설계 문서는 요구사항 표(design.md)
- 문서의 요구 범위와 검증 범위 일치
- 자동 생성 문서·표: 원본의 요구 설명 정확성과 생성물·원본 일치를 각각 확인
- 추가 기능: 생략 시 기존 의미를 유지하는 사례 지정

## 코드로 옮기기

내용 → 계약이 코드에 들어가기 전 → 들어간 뒤:

- 목적, 흐름, 규칙과 이유 → 설계 문서 → 설계 문서
- 타입으로 드러나는 함수와 타입의 입출력 → 설계 문서 작동 방식 → 코드의 타입 정의. 설계 문서는 요약과 링크
- 타입으로 드러나지 않는 실패 조건, 제약 → 설계 문서 작동 방식 → 코드 문서 주석 (code-style 공개 범위와 주석)
- 메시지, 명령, 설정, 테이블, 오류 코드 → 설계 문서 작동 방식 → spec 문서
- 할 일 → 이슈 → 이슈와 `TODO(#{번호})`
- 동작 예시와 완료 조건 → 설계 문서 예시, 이슈 → 테스트. 요구사항 표 `검증 계획` 교체
