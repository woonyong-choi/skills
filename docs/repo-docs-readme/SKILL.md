# README 작성

처음 온 사람이 무엇인지, 왜 필요한지, 지금 쓸 수 있는지 바로 알도록 루트 `README.md`와 `README.en.md`를 쓴다. 공통 규칙은 [repo-docs](../repo-docs/SKILL.md)를 먼저 따르고, 이 스킬은 README의 종류, 절 구성과 절 규칙, 이미지를 맡는다.

## 원칙

- 독자와 답할 질문은 repo-docs 문서 목록을, 언어는 repo-docs 언어 절을 따른다. 영어판은 아래 영어판 절을 따른다.
- 필수 정보와 핵심 사용 흐름은 남기고, 따로 찾아보는 세부는 `docs/`로 링크한다.
- 그 절의 질문에 답하는 그림만 넣는다. 같은 정보를 되풀이하는 그림은 넣지 않는다.

## 종류

- **오픈소스형**은 남이 설치해 쓰는 저장소다.
- **포트폴리오형**은 내가 한 일을 보여 주는 저장소다. 절은 경력 원본 `포트폴리오.md` 묶음 절에 대응한다(해결한 문제는 문제와 제약, 그 밖은 설계 결정, 구현, 결과). 원본 문장을 베끼지 않고, 확인된 사실로 공개용 문장을 새로 쓴다(repo-docs 비공개 작업 파일 절).
- [references/template.md](references/template.md)에서 종류 하나의 틀을 고른다. 절 이름과 순서는 그대로 쓰고, 아래 조건이 맞지 않는 절은 뺀다.

## 입력

쓰기 전에 다음 입력을 읽는다. 없는 파일은 건너뛴다. GitHub 명령은 GitHub 저장소에서만 쓰고, 다른 환경은 대응하는 근거를 쓴다.

| 입력 | 쓰는 곳 |
|---|---|
| GitHub 저장소 설명 `gh repo view --json description` | 한 줄 소개 |
| `docs/design/`의 요약과 예시 절, `docs/architecture.md` | 작동 방식, 구현 |
| 공개 결정 기록과 `design` 이슈 | 해결하는 문제, 설계 결정 |
| 열린 상위 이슈 | 상태의 다음 할 것 |
| 판정과 한계를 확인한 실험 보고서 | 상태의 측정 결과, 결과 |
| GitHub 릴리스 목록 `gh release list` | 단계 |
| 실제로 실행한 명령과 출력 | 빠른 시작, 실행 |
| `docs/README.md` 목록 | 문서 |
| CI 설정과 저장소 검사 스크립트 | 개발 |
| `LICENSE`, `.github/CONTRIBUTING.md` | 라이선스, 개발 |

## 단계

위에서부터 처음 맞는 단계 하나를 고른다.

| 단계 | 조건 |
|---|---|
| 배포 | GitHub 릴리스나 패키지 저장소 배포가 하나 이상 있다 |
| 실행 가능 | 저장소에서 확인한 기본 브랜치 빌드로 빠른 시작의 명령이 실제로 동작한다 |
| 개발 중 | 구현 상태 기능이 하나 이상 있다 |
| 설계 | 그 밖의 경우 |

## 목차

두 종류 모두 키워드 트리 형식의 `## 목차` 절을 둔다.

- 머리, 데모, 단계 알림 다음, 첫 본문 절 앞에 둔다.
- 글머리 목록 링크로 쓴다. `##` 절이 1단, 그 아래 `###` 소절이 2단(공백 2칸 들여쓰기), `####`가 3단이다. 4단 이상과 목차 절 자신은 넣지 않는다.
- 링크 글자는 절 제목 그대로 쓴다. 앵커는 GitHub 규칙을 따른다. 소문자로 바꾸고, 공백은 `-`로 바꾸고, 마침표, 괄호, 쌍점 같은 기호는 지우고, 한글은 그대로 둔다. 같은 제목이 두 번 나오면 뒤쪽에 `-1`을 붙인다.
- 실제로 있는 절만 넣는다. 뺀 절과 다른 문서로 가는 링크는 넣지 않는다.
- 절을 더하거나 이름을 바꾸는 PR에서 목차도 고친다.

## 오픈소스형 절 규칙

- **머리.** 로고는 파일이 있을 때만 넣는다. 한 줄 소개는 저장소 설명과 같은 글자로 쓰고 마침표는 뺀다. 뱃지는 license, CI, 배포 버전 중 있는 것만 단다. 언어 전환 줄은 영어판이 있을 때만 둔다(영어판 절).
- **데모 GIF.** 실행되는 제품이 있을 때만 머리 바로 아래에 둔다.
- **단계 알림.** `> [!NOTE]`와 아래 표의 고정 문장을 쓴다. 배포 단계면 뺀다.
- **빠른 시작.** 실행 가능과 배포 단계에만 둔다. 실제로 실행해 확인한 설치와 첫 실행 명령만 쓴다.
- **해결하는 문제.** 프로젝트 고유 용어는 같은 문장에서 푼다. 대신 쓸 도구를 깎아내리지 않고, 그 도구가 더 나은 경우만 쓴다.
- **작동 방식.** 입력부터 결과까지 번호 목록, 흐름 그림 한 장, 설계 문서 링크를 둔다. 설계와 개발 중 단계에서는 첫 문장을 `아래는 설계한 동작입니다.`(영어판 `The following is the designed behavior.`)로 쓴다.
- **상태.** 있는 것, 아직 없는 것, 다음 할 것(상위 이슈 링크), 측정 결과(있을 때)를 쓴다. 측정 수치는 보고서 `results/summary.json`의 값과 조건을 그대로 쓰고, 유리한 판정만 고르지 않는다. 호환 약속을 한 문장 쓴다(예: `1.0 전에는 형식과 명령이 예고 없이 바뀔 수 있습니다.`). 설계 단계에서는 있는 것이 공개 설계 문서와 공개 결정 기록뿐이라고 밝힌다.
- **문서.** `docs/README.md`가 있을 때만 둔다. 그 목록의 시작 분류 문서 줄을 같은 제목, 같은 설명 그대로 쓰고 끝에 전체 문서 목록 링크를 단다. 작업 언어가 한국어이면 영어판 문서 절 첫 문장을 `The design documents are written in Korean.`으로 쓴다. `README.md`에는 이 문장이 없다.
- **개발.** CI와 검사 스크립트에 있는 명령만 빌드, 시험, 린트, 포맷 순서로 쓴다. `.github/CONTRIBUTING.md`가 있으면 링크한다.
- **라이선스.** `[{SPDX 식별자}](LICENSE)` 한 줄로 쓴다. 라이선스가 둘이면 `{A} 또는 {B}`로 쓴다.

| 단계 | 알림 | 영어판 알림 |
|---|---|---|
| 설계 | `설계 단계입니다. 실행할 수 있는 코드는 아직 없습니다.` | `Design stage. There is no runnable code yet.` |
| 개발 중 | `개발 중입니다. 실행할 수 있는 명령은 아직 없습니다.` | `In development. There is no runnable command yet.` |
| 실행 가능 | `개발 중입니다. 배포판은 없고 소스에서 빌드해 실행합니다.` | `In development. There are no releases; build from source.` |

## 포트폴리오형 절 규칙

- **머리.** 한 줄 소개는 무엇을 하는 시스템인지와 규모 숫자 하나로 쓴다. 뱃지는 실제로 쓴 핵심 기술 4~6개의 이름과 버전으로 단다.
- **결과.** 측정하지 않은 값을 쓰지 않는다.
- **실행.** 실제로 돌아가는 명령을 쓴다. 비공개 의존이 있으면 이유를 한 문장 쓴다.
- 기간, 역할, 인원 요약 표를 두지 않는다.

## 이미지와 아이콘

두 종류 모두 적용한다. 형식, 위치, 크기, 용량은 [repo-docs-figures](../repo-docs-figures/SKILL.md) 규격 절을 따른다.

| 종류 | 넣는 자리 |
|---|---|
| 로고 | 로고 파일이 있을 때 머리. `<picture>`로 테마마다 다르게 |
| 데모 GIF | 실행되는 화면이 있을 때 머리 바로 아래 |
| 스크린샷 | GIF가 필요 없는 정지 화면. 라이트와 다크 `<picture>`(repo-docs-figures 스크린샷) |
| 흐름이나 구조 그림 | 작동 방식이나 구현 절에 한 장 |

- 대체 글은 repo-docs-figures 대체 글 절을 따른다. 모형이나 합성 화면이면 대체 글과 캡션에 `모형`을 붙인다(repo-docs 자리표시).
- 아이콘은 shields.io 뱃지의 공식 로고(`logo=` 값)에만 쓴다. 절 제목, 목록, 본문에 아이콘과 이모지를 쓰지 않는다.

## 영어판

- `README.en.md`는 `README.md`와 절 순서, 내용, 이미지, 뱃지가 같다. 절 이름은 아래 대응표를 쓴다.
- 언어 전환 줄은 `README.md`에서 `한국어 | [English](README.en.md)`, `README.en.md`에서 `[한국어](README.md) | English`다. 가운데 정렬 블록 안이라 `<a href>` 형식으로 쓴다.
- `README.md`를 바꾸는 PR에서 `README.en.md`도 고친다. 한쪽만 바꾼 PR을 만들지 않는다.
- `README.md`는 합쇼체, `README.en.md`는 평이한 영어 현재형으로 쓴다.
- 두 판을 대조할 때 주체, 동작, 조건, 부정, 수치를 그대로 지킨다. 대체 글과 목차의 링크 글자, 앵커는 각 언어를 기준으로 쓴다.

| 한국어 절 | 영어 절 |
|---|---|
| 목차 | Contents |
| 빠른 시작 | Quick start |
| 해결하는 문제 | Why |
| 작동 방식 | How it works |
| 상태 | Status |
| 문서 | Documentation |
| 개발 | Development |
| 라이선스 | License |
| 문제와 제약 | Problem and constraints |
| 설계 결정 | Design decisions |
| 구현 | Implementation |
| 결과 | Results |
| 실행 | Running |

## 갱신

다음 일이 생기면 입력을 다시 읽고 `README.md`와 영어판을 함께 고친다. 뒤이어 `llms.txt`는 [repo-docs-llms](../repo-docs-llms/SKILL.md)의 갱신 절을 따른다.

- 단계가 바뀌었다.
- 기능을 처음 구현했거나, 정했거나, 없앴다.
- 상위 이슈가 바뀌었다.
- 사용자 판단에 필요한 실험 보고서, 판정, 한계가 바뀌었다.
- 구성 요소, 설치 명령, 사용 명령, 문서 목록이 바뀌었다.

## 답변

- 고른 종류와 단계, 고친 파일을 적는다.
- 근거가 없어 뺀 절이 있으면 그 절과 이유를 적는다.

## 구분

- 흐름과 구조 그림, 데모 GIF 제작은 [repo-docs-figures](../repo-docs-figures/SKILL.md)가 맡는다.
- README를 고친 뒤 `llms.txt` 재생성은 [repo-docs-llms](../repo-docs-llms/SKILL.md)가 맡는다.
