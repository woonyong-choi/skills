# 서브에이전트

서브에이전트를 띄우고, 모델과 추론 수준을 고르고, 결과를 받는 방법을 정한다.

## 언제 읽나

- 서브에이전트를 띄우기 전에 읽는다. 플레이북 단계 안의 위임, 검증자, 담당자, 감시자 모두 해당한다.
- 띄우는 도구 이름과 호스트별 차이는 [호스트 대응표](hosts.md), 역할별 모델 값은 [역할별 모델](models.md)을 본다.

## 누구를 띄우나

1. 플레이북 단계 안에서 띄우는 서브에이전트는 모두 `just-agent`로 띄운다. 코드 작성 위임과 그때그때 필요한 도우미가 여기에 든다. 정의가 설치되지 않은 호스트에서는 같은 지시를 프롬프트 첫머리에 넣는다([호스트 대응표](hosts.md#서브에이전트-공통-규칙)).
2. `just-agent`에게 주는 프롬프트에는 just-mode SKILL.md의 절대 경로를 넣는다. 함께 설치된 스킬은 그 파일 기준 `../<이름>/SKILL.md`에 있다.
3. 플레이북은 `/just-mode`를 받은 대화가 직접 실행한다. 플레이북 자체를 실행하라고 `just-agent`를 띄우지 않는다.
4. `how`, `why`, `interrogate`, `reflect`, `swarm`은 여러 모델로 검토하려고 서브에이전트 종류와 역할을 직접 정한다. 그 스킬이 정한 대로 두고 `just-agent`로 바꾸지 않는다.

## 기본값

- 백그라운드로 띄워 동시에 돌린다.
- 쓰기 작업이면 읽기 전용으로 띄우지 않는다. 쓰기 작업마다 별도 git 워크트리를 준다.
- 내용을 프롬프트에 붙여 넣지 않고 파일 경로를 넘긴다.
- 역할을 밝혀 모델을 고른다. 코드 작성은 `code`, 글과 판단은 `judgment`다.
- 코드 위임은 난이도로 나눈다. 가장 어려운 변경(여러 모듈에 걸친 설계, 까다로운 동시성, 미묘한 알고리즘)은 `judgment`로 보낸다. 모호한 의도를 판단하는 일이든, 정해진 단계를 그대로 실행하는 일이든 같다. 사소한 기계적 수정은 `code`로 보낸다.
- `/just-setup`이 만든 설정 파일의 역할 값은 이 기본값보다, 그리고 `how`, `why`, `arena`, `swarm`, `architect`, `interrogate`, `reflect`의 모델 선택보다 우선한다. 설정에 없는 역할은 기본값을 쓴다.

## 추론 수준과 속도 고르기

1. 띄울 때마다 그 역할의 설정 값이나 기본값에서 출발한다. `/just-setup` 예산이 역할마다 시작 추론 수준을 정한다.
2. 가장 어렵거나 미묘한 일은 한 단계 올린다(최대 수준까지). 판단은 한 단계, 일상적인 일은 두 단계 이상 내린다.
3. 호스트에 빠른 실행 옵션이 있으면 급할 때만 쓴다. 급하다는 것은 CI나 trunk가 실패 중이거나, 사람이 그 결과를 기다리며 멈춰 있다는 뜻이다. 그 밖에는 표준 속도를 쓴다.
4. 실사용 검증자(변경을 사용자처럼 실행해 `PASS`나 `FAIL` 판정을 남기는 에이전트)는 예외로 `code` 역할과 그 속도를 그대로 쓴다. 다른 회사 모델은 리뷰(**interrogate**)에 쓴다.
5. 추론 수준과 빠른 실행 여부만 바꾸고 역할이 정한 모델 계열은 유지한다. 그래야 여러 모델로 꾸린 검토단이 다양하게 남는다.
6. 조정한 모델이나 수준이 거부되면 다른 값을 추측해 넣지 않는다. [역할별 모델](models.md#고르는-규칙)의 규칙대로 진행하고 답변에 알린다.

## 결과 받기

- 서브에이전트가 한 일은 전부 내 책임이다. diff를 직접 보고 요약은 내가 쓴다. 서브에이전트의 말을 그대로 전달하지 않는다.
- 두 번째 의견은 같은 프롬프트를 다른 모델에 보내 얻는다. 둘이 일치하면 믿을 만하다는 강한 신호다.
- 리뷰 지적의 반영 확인은 그 코드를 쓴 에이전트가 아닌 다른 에이전트가 한다.

## 새로 띄우기와 재개

1. 새 일은 합친 범위를 넘긴 새 서브에이전트에 준다. 합친 범위란 처음 지시, 그 뒤의 모든 지시, 이전 에이전트의 보고와 브랜치다. 수정 라운드, 후속 작업, 재시도, 대기열의 다음 항목도 모두 새로 띄운다.
2. 기존 서브에이전트를 재개하거나 메시지를 보내는 것은 새 일이 그 에이전트 안에만 있고 옮기기 비싼 상태를 꼭 필요로 할 때뿐이다. 로컬 체크아웃, 커밋하지 않은 변경, 아직 돌고 있는 프로세스(개발 서버, 시뮬레이터, PR 감시자 등)가 그런 상태다.
3. 돌고 있는 에이전트에 멈춤이나 대기 지시를 보내는 것은 재사용이 아니다.
4. PR 담당 같은 역할은 에이전트보다 오래 간다. 그 에이전트가 끝나서 돌아오면 그 역할의 다음 라운드는 새 에이전트가 맡는다.
5. 중단과 재개를 이어 가며 일을 시키면 중간 지시가 모르는 사이에 빠진다. "완료" 요약을 믿지 말고 합친 범위로 새 서브에이전트를 띄운다.
6. 문맥 사용량이 80%에 가까우면 결정 기록에 지금까지를 적고 새 서브에이전트에 인계한다.
