# 공격적 검토

설정한 모델마다 검토자 하나를 띄워 코드 변경을 공격적으로 검토한다. 날카로운 반론은 검토자에게 역할을 정해 주는 데서가 아니라 서로 다른 모델을 쓰는 데서 나온다. 결과물은 종합한 판정이다. 변경을 자동으로 적용하지 않는다.

## 1. 범위

맥락에서 검토할 대상을 찾는다.

- 사용자가 특정 파일이나 diff를 가리키면 그것을 쓴다.
- 기능 브랜치에 있으면 `git diff origin/HEAD...HEAD`(PR의 기준 브랜치가 다르면 그 브랜치)로 전체 변경을 얻는다.
- 사용자 메시지가 최근 작업을 가리키면 관련 파일을 모은다.

diff나 파일 내용에, 검토자가 코드를 이해하는 데 필요한 주변 맥락 파일을 함께 묶는다.

## 2. 의도

검토자를 띄우기 전에 의도를 분명한 한 문단으로 적는다. 근거는 사용자 메시지, 커밋 메시지, PR 설명(있으면), 코드다. 의도가 확실하지 않으면 이슈 본문을 읽는다. 그래도 모르면 가장 그럴듯한 의도를 가정으로 적고 진행한다. 의도를 잘못 읽으면 결과가 크게 달라지고 되돌릴 수 없는 결정이 걸린 경우에만 사람에게 묻는다(**principle-never-block-on-the-human** 원칙 스킬).

## 3. 검토자 띄우기

모든 검토자를 한 메시지에서 동시에 서브에이전트로 띄운다([호스트 대응표](../just-mode/references/hosts.md)). 검토자는 [역할별 모델](../just-mode/references/models.md)의 `review` 역할에 적힌 모델마다 하나씩 두고, 개수에 맞춰 검토자 A, B처럼 이름을 붙인다. 미설정·빈값과 실행 불가 대체도 역할별 모델을 따른다. 모델 문제로 검토를 생략하지 않는다.

현재 호스트와 다른 회사 모델은 호스트 대응표의 "다른 회사 모델로 검토" 방법으로 실행한다. 모든 검토자는 읽기 전용으로 실행한다. 코드 작성자가 아닌 검토자의 독립 실행 검증 겸임은 [서브에이전트](../just-mode/references/subagents.md#결과-받기)를 따른다.

`references/reviewer-prompt.md`를 읽고 모든 검토자에게 같은 템플릿을 채워 준다. 채울 내용은 적어 둔 의도, diff나 파일 내용, `references/rubric.md`의 채점 기준, `references/code-quality-review.md`의 코드 품질 관점이다. 각 서브에이전트의 추론 수준은 일에 맞게 고른다([서브에이전트](../just-mode/references/subagents.md#추론-수준과-속도-고르기)).

## 4. 종합

결과가 오는 대로 전체 그림을 하나로 정리한다. 모든 검토자의 지적을 읽는다. 같은 문제를 다르게 적은 지적은 합치고, 각 지적을 어느 모델이 냈는지 적는다. 두 모델 이상이 독립적으로 낸 지적이 가장 강한 신호다. 한 모델만 낸 지적도 읽되 그만큼 가볍게 본다. 의견이 갈린 곳을 적는다. 한 모델이 문제를 짚고 다른 모델이 분명히 반대로 말하면 그것도 판정할 때 고려할 맥락이다.

## 5. 주 검토자 판단

나는 중립적인 집계자가 아니라 주 검토자이고, 실용적인 시니어 엔지니어다. 전체 기준은 `references/lead-judgment.md`를 읽는다. 모든 지적에 등급 `P1`~`P5`(**git-pull-request** 스킬 `references/review.md`의 등급 표)를 매기고, 네 갈래 중 하나에 넣고, 낸 모델과 한 줄 근거를 붙인다.

- **반영.** 실제 목표에 비춰 정확성, 보안, 유지보수성에 영향을 주는 실제 문제다. 실제 PR이라면 머지를 막는다.
- **검토.** 타당하지만 지금 고치는 비용을 들일 만큼인지 확실하지 않은 문제다. 사용자가 볼 가치가 있다.
- **참고.** 기술적으로는 맞지만 지금 할 일은 없는 지적이다. 맥락에 따라 다르거나, 섣부른 최적화이거나, 지금 단계에서 영향이 작다.
- **기각.** 틀렸거나, 사소하거나, 맥락을 놓친 지적이다. 짧은 이유를 붙인다.

## 답변

- **git-pull-request** 스킬 `references/review.md`의 공개 피드백 형식을 반드시 읽고 따른다. 검토만 했으면 실제 발견을 첫 문단에 쓰고 실행 통과로 판정하지 않는다.
- 집계와 지적의 표시 조건은 공개 피드백 형식을 따른다. 지적이 있으면 `## 발견 사항` 아래에 등급과 반영·검토·참고·기각 판단을 남긴다. 기각 이유와 모델 간 의견 일치·차이도 해당 지적에 붙인다. 끝 고리의 머지 조건은 남은 P1과 P2를 센다.
- `## 확인한 내용`에 의도, 검토 범위와 검토자별 모델·지적 수를 적는다. 공개 댓글에는 지적과 근거를 요약한다.
- `## 한계와 미확인 사항`에 검토하지 못한 범위와 실패한 검토자 실행을 적는다. 없는 절은 지운다.
