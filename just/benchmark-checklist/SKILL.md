# 벤치마크 체크리스트

성능 숫자를 낼 때 쓴다. PR의 전후 비교, 회귀 주장, 힐클라이밍 측정 도구, 라이브러리나 설정 선택 같은 경우다. 각 질문에 코드에 대한 추측이 아니라 실행에서 얻은 증거로 답한다.

사용자가 대략적인 값만 요청했으면 한 번 실행으로 충분하다. 그래도 질문 4와 7은 확인하고, 한 번 실행이라고 밝힌다. 그 실행이 이상해 보이지 않으면 나머지는 건너뛴다. 여러 선택지 중 하나를 고르는 일은 대략적인 값으로 끝내지 않는다.

## 실행하기 전에

- 하게 될 주장을 보고에 그대로 쓸 문장으로 적어 둔다("60k행 데이터셋에서 내보내기가 p50 기준 30% 빠르다"). 아래 질문들은 그 문장이 맞는지 따진다.
- 측정 스크립트를 읽는다. 무엇을 재고, 세고, 무시하는지 적는다.
- `uptime`으로 부하 평균을, `nproc`로 코어 수를 확인한다. 머신이 바쁘면 무엇이 돌고 있는지 알아낸다. 그것을 멈출 수 없으면 양쪽을 번갈아 돌려 같은 잡음을 받게 하고, 보고에 그렇게 밝힌다.

## 질문

1. **왜 두 배가 아닌가?** 병목이 무엇인지 밝힌다. 프로파일러와 트레이서는 작업을 느리게 하므로 보고하지 않을 실행에서 프로파일링한다. 프로세스별 CPU(`top`, `pidstat`), 런타임 프로파일러(`node --cpu-prof`, `py-spy`, `perf`), I/O 대기, 시스템 호출 수(Linux에서 `strace -c`)를 쓰고, 핫스팟이 소스의 어디인지 찾는다. 부하 생성기도 지켜본다. 부하 생성기가 먼저 포화되면 부하 생성기를 잰 것이다. 변경했는데 숫자가 그대로면 그 이유는 병목에 있으므로, 변경이 쓸모없다고 하기 전에 병목부터 찾는다.
2. **튜닝했는가?** 모든 쪽을 프로덕션이 돌리는 방식대로 돌린다. 릴리스 빌드, 프로덕션 플래그와 환경 변수, 배치와 트랜잭션 설정, 연결 풀, 프로덕션과 같은 상태(웜 또는 콜드)의 캐시, 같은 버전과 데이터다. 한쪽이 기본값으로 돌면 구현이 아니라 설정을 비교한 것이다. 병목이 설정(행마다 커밋, 디버그 빌드, 빠진 인덱스)이면 그쪽은 튜닝되지 않은 것이다. 승자를 고르기 전에 튜닝하고 다시 잰다. 튜닝할 수 없으면 그 실행으로 승자를 고르지 않는다. 사용자가 무엇을 도입할지 고르는 중이라면, 주장을 "오늘 배포된 코드 기준"으로 좁혀도 이 문제는 풀리지 않는다. 사용자는 오늘의 설정이 아니라 그 선택지를 도입하기 때문이다.
3. **한계를 넘었는가?** 직접 계산해 본다. 초당 바이트는 디스크·네트워크 대역폭과 비교한다. 초당 작업 수 × 작업당 비용은 코어 수와 비교한다. 아낀 시간은 바뀐 부분이 원래 걸린 시간과 비교한다. 실행의 10%를 차지하는 부분을 없애도 실행은 최대 약 11%만 빨라진다. 한계를 넘는 결과가 나왔다면 실제 작업이 아닌 다른 것을 잰 것이다. 캐시, 아무것도 안 하는 동작, 버그 같은 것이다.
4. **오류가 났는가?** 실패와 성공이 아닌 응답을 세고, 출력이 있기만 한 게 아니라 올바른지 확인한다. 요청 거부는 대개 빠르고, 시간 초과와 재시도는 느리다. 스크립트가 오류를 세지 않으면 세는 코드를 더한다.
5. **재현되는가?** 각 쪽을 최소 5번, 번갈아(A, B, A, B 식으로) 돌려 예열, 지연 초기화, 캐시, 시간에 따른 성능 변화(drift)가 어느 쪽에도 유리하지 않게 한다. 중앙값과 범위를 보고한다. 실행 간 변동보다 작은 차이는 측정 가능한 차이가 아니다. 판정이 아슬아슬하면 순위합 검정이나 측정 도구 자체의 통계를 쓴다.
6. **중요한가?** 마이크로벤치마크 결과를 낼 때는 사용자가 실제로 기다리는 엔드투엔드 경로도 현실적인 데이터 크기와 동시성으로 재고, 마이크로벤치마크 결과를 전체에서 차지하는 비율로 보고한다. 요청의 1%를 차지하는 헬퍼는 아무리 빨라져도 요청을 최대 1%만 빠르게 한다.
7. **작업이 실제로 일어났는가?** 측정 구간 안에서 작업이 실제로 돌았는지 확인한다. 요청이 서버에 닿았고, 행이 쓰였고, 바이트를 읽었고, 코드가 결과를 썼는지다. 지연 실행 코드(아무도 순회하지 않는 제너레이터, 아무도 기다리지 않는 프로미스, JIT가 버릴 수 있는 결과)와 시간 초과는 실제로 하지 않은 작업의 숫자를 만들어 낸다.

## 보고

- 판정을 먼저 쓴다. 빨라짐, 느려짐, 측정 가능한 차이 없음, 판정 불가.
- 단위를 붙인 숫자, 실행 횟수, 범위, 병목을 준다. 예: "p50 41 ms → 33 ms, 양쪽 각 7회 실행의 중앙값, 변경 후 범위 32~35 ms, 코어 하나의 JSON 파싱이 병목."
- 차이를 주장하는데 병목을 밝히지 못하거나, 한쪽이 튜닝 없이 돌았거나, 질문 4와 7을 확인하지 못했으면 판정 불가라고 한다. 무엇을 확인하지 못했는지 적는다.
- PR 본문에는 대표 숫자 하나만 둔다(PR 열기 플레이북, `../mode/playbooks/opening-a-pr.md`). 실행 기록, 범위, 병목 증거는 링크한 산출물이나 메모 파일에 둔다.

## 다른 성능 자료

- 성능 문제 플레이북(`../mode/playbooks/perf-issue.md`)이 기준선으로 계획을 세우기 전에 그 기준선을 검증하고, 그 뒤의 모든 숫자도 검증한다.
- 힐클라이밍 플레이북(`../mode/playbooks/hillclimb.md`)의 측정 도구를 고정하기 전에 검증한다. 고정한 측정 도구는 오류 수와 작업량을 출력하므로, 변경을 유지할지 되돌릴지 정할 때마다 질문 4와 7이 따로 품을 들이지 않고 확인된다.
