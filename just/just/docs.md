# just docs

독자가 가져갈 답에 맞는 유형을 고르고, 확인한 경험과 근거로 작성자의 생각이 이어지는 글을 쓴다.

## 켜기와 끄기

- `/just docs`나 `/just docs on`(Codex는 `$just docs on`)으로 불리면 이 세션의 글쓰기에 이 기준을 적용한다. 처음 켤 때 `docs 켜짐`을 짧게 알리고, 글 유형을 이미 골랐으면 함께 알린다.
- 켜진 동안 작성과 교정마다 공통 규칙과 선택한 유형을 적용한다. 이미 읽은 파일은 바뀌거나 유형이 달라질 때만 다시 읽는다.
- `/just docs off`(Codex는 `$just docs off`)나, 켜진 뒤의 `docs off`는 적용을 끝낸다. 단독 명령이면 `docs 꺼짐`으로 답한다. 함께 온 다른 요청은 글쓰기 기준을 끈 뒤 처리한다.
- 새 세션은 꺼진 상태다. 같은 세션을 요약해 이어가면 활성 여부, 유형, 확인한 판단과 남은 질문을 기존 인계에 보존한다. 상태 파일을 따로 만들지 않는다.
- 이는 대화 지시의 적용 범위다. 도구 훅, 전역 설정, 쓰기 권한을 바꾸지 않는다. `just dev`의 편집 전 규칙 확인과도 따로 켜고 끈다.

## 단계

1. 대상 원고와 관련 대화, 당시 자료를 읽는다. 독자와 가져갈 답, 작성자가 정한 흐름을 확인한다.
2. [유형 카탈로그](references/docs/catalog.md)로 주 유형 하나를 고르고 이유를 한 문장으로 알린다. 코드나 수치의 유무만으로 고르지 않는다. 맞는 유형이 없거나 근거가 부족하면 독자가 가져갈 답과 결과물부터 묻는다. 두 유형의 목적이 겹치면 어느 답이 중심인지 묻는다.
3. 선택한 유형의 파일만 읽는다. 빈 파일이면 기준이 준비되지 않았다고 알리고 사용자의 예시와 첫 원고로 함께 채운다. 다른 유형의 틀로 대신 쓰거나 나머지 빈 파일까지 채우지 않는다.
4. 의도와 경험이 없거나 모호하면 [질문 절차](references/docs/questions.md)를 읽고 해당 부분을 확인한다. 코드가 보여 주는 동작과 작성자가 기억하는 이유를 구분한다.
5. 독자가 앞 문단을 읽고 다음에 궁금해할 내용을 잇는다. 사용자가 준 전개와 확정 문장을 보존하고, 아래 원고 규칙과 유형 기준으로 쓴다.
6. 독자, 기술 검토자, 편집자의 눈으로 전체를 다시 읽는다. 사실이 맞는지, 독자가 이해한 내용이 작성자의 의도와 같은지, 이 사람만 쓸 수 있는 글인지([아래 절](#이-사람만-쓸-수-있는-글))를 따로 본다. 근거 없는 주장, 빠진 설명, 앞서 나온 결론, 중복, 문장 리듬, 그림 위치를 고친다. 실제 검토를 받지 않았으면 전문가가 평가했다고 말하지 않는다.
7. 저장을 요청받았으면 해당 저장 도구로 반영하고 다시 읽는다. 화면을 확인해야 하는 변경은 독자가 실제로 보는 화면에서도 확인한다. 초안, 저장, 검증, 발행을 구분한다.

## 원고 규칙

- 원고는 사용자가 정한 문체와 확정한 표현을 따른다. 한국어 기술 블로그의 기본은 합쇼체다. 스킬 문서 자체의 평서체와 섞지 않는다.
- 독자가 알아야 할 필요가 생긴 자리에 개념을 소개한다. 작성자가 준비한 용어와 구성 요소의 순서로 나열하지 않는다.
- 관심을 끄는 방식과 전개는 선택한 유형을 따른다. 실제 목적과 장면을 쓰고, 모든 글에 장애나 반전, 제약부터 선택으로 이어지는 서사를 강제하지 않는다.
- 설명을 더하기 전에 기존 문단의 순서를 바꾸거나 합친다. 필요한 원리와 비용은 남기고 같은 역할의 예고, 요약, 정의를 걷어 낸다. 짧음보다 이해에 필요한 내용이 빠지지 않는지가 먼저다.
- 같은 길이의 문장을 같은 종결로 끊지 않는다. 인과나 조건으로 연결되는 문장은 함께 쓰고, 대상이나 논점이 바뀌면 나눈다. 종결어미만 피하려고 접속어를 붙이거나 긴 문장으로 합치지 않는다.
- 비유는 낯선 관계를 실제로 이해시키는지 확인한다. 대응 관계를 설명하느라 글이 더 길어지면 실제 값의 변화나 그림으로 바꾼다.
- 작성자가 만든 자료가 아닌 링크는 요청받지 않았으면 원고에 넣지 않는다. 사실 확인에 쓴 외부 자료와 상세 검증 기록은 원고와 따로 두는 근거 기록이 있으면 그곳에 두고, 없으면 답변에서 알린다. 이 규칙은 스킬끼리의 참조 링크에 적용하지 않는다.

## 이 사람만 쓸 수 있는 글

독자가 "누군가 원리를 정리한 글"이 아니라 "이 사람이 궁금해서 직접 해 본 글"로 읽게 한다. 원리 정리는 누구나 같은 문장으로 쓸 수 있지만, 무엇이 궁금했고 무엇을 골랐고 무엇을 확인했는지는 작성자만 쓸 수 있다. 새 생각을 더 받아 내는 일이 아니라, 작성자가 이미 말한 생각을 설명 안에 살리는 일이다.

- 문단마다 묻는다. 작성자 이름을 지워도 다른 사람이 똑같이 쓸 수 있는 문단인가. 원리 설명 문단은 그래도 된다. 선택과 결과를 말하는 문단이 그렇다면 작성자의 궁금증, 판단, 흔적이 빠진 것이다.
- 작성자의 생각은 세 가지에서 나온다. 무엇이 궁금해서 직접 해 봤는지, 여러 조건 가운데 무엇을 중요하게 여겼는지, 결과에서 무엇을 확인했는지다.
- 그 생각은 선택이 생기는 자리에 둔다. 원리를 설명한 뒤 "그래서 무엇을 하려고 어디에 적용했는지"까지 잇는다. 원리와 동작 자체는 담백하게 쓴다.
- 작성자만의 구체적인 흔적을 그 값이 쓰이는 설명 안에 넣는다. 실제 환경에서 읽은 값, 처음 정한 목표, 써 본 도구와의 비교가 그런 흔적이다. 흔적만 따로 소개하는 문단은 만들지 않는다.
- 구성 요소부터 소개하지 않는다. 그 구조가 필요해지는 부담부터 독자가 따라오게 쓴다.
- 이미 판단이 들어 있는 문단은 그대로 둔다. 감정이나 일화로 다시 꾸미지 않는다.
- "저는"을 반복하거나 이름을 더하는 것으로 대신하지 않는다. 없는 감정, 실패, 대화를 보태지 않고, 모든 문단에 개인 이야기를 넣지 않는다.
- 작성자가 말하지 않은 생각, 짐작, 미리 한 예상이나 계산을 만들어 넣지 않는다. 작성자의 목소리가 필요한 자리인데 확인된 말이 없으면 그 부분을 묻고, 답을 받기 전에는 확인된 동작과 결과만 쓴다.

## 증거와 그림

- 중요한 동작과 결과는 독자가 본문 안에서 확인하게 한다. 저장소 링크만으로 대신하지 않는다. 실제 화면, 코드, 측정 자료와 설명용 모형을 구분한다.
- 증거를 나란히 견주는 이미지는 연달아 둘 수 있다. 설명용 그림은 그 그림이 필요해지는 맥락 뒤에 두고, 그림 뒤에는 해석이나 다음 궁금증을 잇는다. 같은 내용을 글과 그림에서 되풀이하지 않는다.
- 코드를 설명할 때는 그림보다 읽을 수 있는 코드 블록을 먼저 쓴다. 발췌한 코드의 정렬 공백, 들여쓰기, 주석 위치만 다듬었어도 토큰, 문자열, 주석 내용이 원문과 같은지 대조한다. 보기 좋게 하려고 실제 구현이나 공통 스타일을 바꾸지 않는다.
- 그림을 아직 만들지 않은 초안에는 그림 자리에 위치, 입력, 상태 변화, 강조할 관계를 적은 `text` 코드 블록을 두고 앞뒤에 빈 줄을 둔다. 이 자리 표시를 완성한 그림으로 보고하지 않는다.
- 그림 제작과 화면 증거 검증은 **repo-docs-figures** 스킬을 쓴다. 자세한 수치와 반복 계산은 그림이나 표로 옮기되 해석에 필요한 조건은 본문에 남긴다.

## 답변

- 원고 요청에는 원고를 보여 준다. 분석 요청에는 실제로 달라질 문단과 이유를 보여 주고 같은 진단을 반복하지 않는다.
- 부족한 사실과 확인이 필요한 질문만 묻는다. 확인된 답은 다음 교정에도 유지하고 다시 묻지 않는다.
- 저장했으면 대상과 반영 결과, 확인한 범위와 남은 작업을 짧게 알린다. 발행은 별도 요청으로 다룬다.

## 구분

- 저장소 문서의 언어와 위치, 형식은 **repo-docs** 스킬이 맡는다. 문장 명료성과 군더더기는 **technical-writing**, **unslop** 스킬을 쓴다. just docs는 작성자 경험을 확인하고 독자 질문으로 전개하는 일을 맡는다.
- 등록 Vault의 노트를 읽거나 고치는 일은 **markdown-notes-agent** 스킬이 맡는다. 채용 공고별 이력서와 포트폴리오는 **career** 스킬이 맡는다.
