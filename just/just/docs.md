# just docs

독자가 가져갈 답에 맞는 유형을 고르고, 확인한 경험과 근거로 작성자의 생각이 이어지는 글을 쓴다.

## 켜기와 끄기

- `/just docs`나 `/just docs on`(Codex는 `$just docs on`)으로 불리면 이 세션의 글쓰기에 이 기준을 적용한다. 처음 켤 때 `docs 켜짐`을 짧게 알리고, 글 유형을 이미 골랐으면 함께 알린다.
- 켜진 동안 작성과 교정마다 공통 규칙과 선택한 유형을 적용한다. 이미 읽은 파일은 바뀌거나 유형이 달라질 때만 다시 읽는다.
- `/just docs off`(Codex는 `$just docs off`)나, 켜진 뒤의 `docs off`는 적용을 끝낸다. 단독 명령이면 `docs 꺼짐`으로 답한다. 함께 온 다른 요청은 글쓰기 기준을 끈 뒤 처리한다.
- 새 세션은 꺼진 상태다. 같은 세션을 요약해 이어가면 활성 여부, 유형, 확인한 판단과 남은 질문을 기존 인계에 보존한다. 상태 파일을 따로 만들지 않는다.
- 이는 대화 지시의 적용 범위다. 도구 훅, 전역 설정, 쓰기 권한을 바꾸지 않는다. `just dev`의 편집 전 규칙 확인과도 따로 켜고 끈다.

## 단계

1. 대상 원고와 관련 대화, 당시 자료를 읽는다. 독자와 가져갈 답, 작성자가 정한 흐름을 확인한다.
2. [유형 카탈로그](references/docs/catalog.md)로 주 유형 하나를 고르고 이유를 한 문장으로 알린다. 코드나 수치의 유무만으로 고르지 않는다. 맞는 유형이 없거나 근거가 부족하면 독자가 가져갈 답과 결과물부터 묻는다. 두 유형의 목적이 겹치면 어느 답이 중심인지 묻는다.
3. 선택한 유형의 파일만 읽는다. 빈 파일이면 기준이 준비되지 않았다고 알리고 사용자의 예시와 첫 원고로 함께 채운다. 다른 유형의 틀로 대신 쓰거나 나머지 빈 파일까지 채우지 않는다.
4. 의도와 경험이 없거나 모호하면 [질문 절차](references/docs/questions.md)를 읽고 해당 부분을 확인한다. 코드가 보여 주는 동작과 작성자가 기억하는 이유를 구분한다.
5. 독자가 앞 문단을 읽고 다음에 궁금해할 내용을 잇는다. 사용자가 준 전개와 확정 문장을 보존하고, 아래 원고 규칙과 유형 기준으로 쓴다.
6. 아래 [완성 검수](#완성-검수)를 반드시 거친다. 독자, 기술 검토자, 편집자의 관점으로 각각 읽고, 실제 문장과 문단 사이의 관계로 판정한다. 항목이 들어 있다는 확인만으로 통과시키지 않는다. 전체 원고를 쓰거나 전개·결론을 고칠 때는 아래 독립 검토도 거친다. 실제 검토를 받지 않았으면 전문가가 평가했다고 말하지 않는다.
7. 저장을 요청받았으면 해당 저장 도구로 반영하고 다시 읽는다. 화면을 확인해야 하는 변경은 독자가 실제로 보는 화면에서도 확인한다. 초안, 저장, 검증, 발행을 구분한다.

## 원고 규칙

- 원고는 사용자가 정한 문체와 확정한 표현을 따른다. 한국어 기술 블로그의 기본은 합쇼체다. 스킬 문서 자체의 평서체와 섞지 않는다.
- 독자가 알아야 할 필요가 생긴 자리에 개념을 소개한다. 작성자가 준비한 용어와 구성 요소의 순서로 나열하지 않는다.
- 관심을 끄는 방식과 전개는 선택한 유형을 따른다. 실제 목적과 장면을 쓰고, 모든 글에 장애나 반전, 제약부터 선택으로 이어지는 서사를 강제하지 않는다.
- 설명을 더하기 전에 기존 문단의 순서를 바꾸거나 합친다. 필요한 원리와 비용은 남기고 같은 역할의 예고, 요약, 정의를 걷어 낸다. 짧음보다 이해에 필요한 내용이 빠지지 않는지가 먼저다.
- 비유는 낯선 관계를 실제로 이해시키는지 확인한다. 대응 관계를 설명하느라 글이 더 길어지면 실제 값의 변화나 그림으로 바꾼다.
- 작성자가 만든 자료가 아닌 링크는 요청받지 않았으면 원고에 넣지 않는다. 사실 확인에 쓴 외부 자료와 상세 검증 기록은 원고와 따로 두는 근거 기록이 있으면 그곳에 두고, 없으면 답변에서 알린다. 이 규칙은 스킬끼리의 참조 링크에 적용하지 않는다.

## 이 사람만 쓸 수 있는 글

독자가 작성자의 궁금증과 판단을 따라가게 한다. 작성자에게서 확인한 생각을 그 생각이 필요한 설명 안에 살린다. 개인 이야기를 많이 넣는 것으로 이 기준을 채우지 않는다.

- 원리 자체는 담백하게 설명한다. 선택과 결과를 다루는 자리에는 무엇을 하려 했고, 어떤 조건을 중요하게 여겼으며, 무엇을 확인했는지 잇는다. 이를 별도 소개나 회고 문단으로 반복하지 않는다.
- 함수명, 구성 요소, 환경값만으로 판단을 대신하지 않는다. 그 사실이 앞선 선택에서 왜 필요해졌고 무엇을 가능하게 했는지 확인한다.
- 작성자가 말하지 않은 감정, 실패, 대화, 예상이나 계산을 만들지 않는다. 당시의 판단과 지금의 해석을 구분한다. 선택의 이유가 원고와 자료에 없으면 질문 절차로 확인하고, 그동안 나머지 교정은 이어 간다.
- 원리 설명이나 이미 판단이 드러나는 문단은 억지로 개인 서술로 바꾸지 않는다. 이름이나 "저는"을 더해 목소리를 꾸미지 않는다.

## 완성 검수

교정 전에는 확정한 표현과 사실, 의도, 조건, 원고 분량을 확인한다. 초안의 주장과 수치 중 확인 자료로 뒷받침되지 않는 것부터 찾는다. 원고에 적혀 있다는 이유만으로 사실로 남기지 않고, 빼거나 확인되지 않았다고 표시한다. 사용자가 확정한 표현은 지우지 않고 사실만 확인한다. 교정한 뒤에는 앞 절부터 이어 읽으며 아래 순서로 판정한다. 검수 메모를 원고에 덧붙이지 않는다.

1. 문단의 첫 문장이 앞 문단에서 생긴 필요나 궁금증을 받는지 확인한다. 독자가 그 지점에서 왜 이 설명을 읽는지 말할 수 없다면 나열로 판정한다. 기존 이유를 선택 앞으로 옮기거나, 실제로 주고받는 값과 동작으로 잇는다. "이 과정", "이 글에서는" 같은 말이나 예고, 수사적 질문만 더한 것은 연결로 보지 않는다.
2. 관계가 있는 문장을 소리 내어 읽듯 이어 본다. 조건, 판단, 동작, 결과가 같은 어미로 한 문장씩 끊겨 있으면 논점이 같은 문장끼리 합친다. 대상이나 논점이 바뀌면 나눈다. 어미만 바꾸거나 접속어로 늘이지 않는다. 합치면서 측정 대상의 정의를 관측 결과의 원인처럼 쓰지 않는다. 합친 뒤 주체와 인과가 흐려지면 다시 쓴다.
3. 결과 문단이 독자에게 남기는 답을 확인한다. 수치만 늘어놓거나 주의사항, "어느 쪽이 낫다고 할 수 없다"로 끝나면 관측한 차이가 무엇을 뜻하는지 기존 근거 안에서 잇는다. 해석에 필요한 한계는 남긴다. 결론은 도입의 궁금증에 대해 무엇을 확인했는지 답한다. 마지막 문장만 따로 읽어도 그 답이 남는지 본다. 주의사항이 그 답을 끊으면 위치를 옮기거나 결과와 합친다. 확인할 수 없었다는 것 자체가 결과면 그 사실과 남은 질문을 밝히고, 억지로 교훈을 붙이지 않는다.
4. 원문과 대조해 같은 역할의 설명을 걷어 낸다. 새 사실이나 의도를 넣지 않았는지, 사용자 표현과 필요한 조건을 잃지 않았는지 확인한다. 분량을 늘리지 말라는 요청이 있으면 필요한 연결도 기존 중복을 줄여 그 안에 쓴다. 그런 제한이 없을 때만 이해에 꼭 필요한 누락을 보충한다. 원문이 같은 사실을 이미 자연스럽게 전하는 문단은 고치지 않는다.

- 분량 제한이 있으면 고치기 전과 후의 원고를 사용자가 정한 단위로 도구를 써서 세어 비교한다. 단위를 정하지 않았으면 글자 수로 센다. 답변의 보고나 스킬 켜짐 알림은 원고 분량에 넣지 않는다. 분량을 맞췄다는 것만으로 사실 보존과 문단 연결을 통과시키지 않는다.
- 하나라도 통과하지 못하면 그 부분을 다시 고치고 앞뒤 문단과 마지막 문장을 재검수한다. "짧게"라는 요청을 받았을 때도 같은 설명을 되풀이해 늘이지 않았는지 확인한다. 원고만 요청했으면 교정 보고가 붙지 않았는지도 보여 주기 전에 확인한다.
- 문단 연결과, 결론이 처음 목적에 답하는지는 선택한 유형에 맞춰 판정한다. 절차, 안내, 표와 나열 자체가 목적이면 서사를 강요하지 않는다. 모든 문단에 이유와 결과를 갖추게 하거나 질문으로 시작하게 하지 않는다.
- 독립 검토자에게 사용자 요청, 확인 자료, 원문과 수정본을 함께 주고 독자가 이해한 답, 끊긴 관계, 중복, 불필요한 교정을 실제 문단을 근거로 찾게 한다. 작성자의 자기평가나 원하는 판정은 넘기지 않는다. 지적을 자료와 대조해 고친 뒤 바뀐 부분과 앞뒤 관계를 다시 검토받는다. "규칙을 지켰다" 같은 총평이나 작성자 의도를 되풀이한 답은 통과로 보지 않는다. 독립 검토자를 쓸 수 없으면 혼자 다시 읽고 그 한계를 알리며, 독립 검토를 마쳤다고 보고하지 않는다.

## 증거와 그림

- 중요한 동작과 결과는 독자가 본문 안에서 확인하게 한다. 저장소 링크만으로 대신하지 않는다. 실제 화면, 코드, 측정 자료와 설명용 모형을 구분한다.
- 그림과 이를 해석하는 글을 한 묶음으로 둔다. 사용자가 배치 순서를 정했으면 따르고, 정하지 않았으면 그림이 필요한 맥락 뒤에 그림과 해석을 둔다. 증거를 견주는 이미지는 연달아 둘 수 있다. 같은 내용을 글과 그림에서 되풀이하지 않는다.
- 코드를 설명할 때는 그림보다 읽을 수 있는 코드 블록을 먼저 쓴다. 발췌한 코드의 정렬 공백, 들여쓰기, 주석 위치만 다듬었어도 토큰, 문자열, 주석 내용이 원문과 같은지 대조한다. 보기 좋게 하려고 실제 구현이나 공통 스타일을 바꾸지 않는다.
- 그림을 아직 만들지 않은 초안에는 그림 자리에 위치, 입력, 상태 변화, 강조할 관계를 적은 `text` 코드 블록을 두고 앞뒤에 빈 줄을 둔다. 이 자리 표시를 완성한 그림으로 보고하지 않는다.
- 그림 제작과 화면 증거 검증은 **repo-docs-figures** 스킬을 쓴다. 자세한 수치와 반복 계산은 그림이나 표로 옮기되 해석에 필요한 조건은 본문에 남긴다.

## 답변

- 원고만 요청하면 원고만 보여 준다. 교정 이유와 검수 보고를 덧붙이지 않는다. 분석 요청에는 실제로 달라질 문단과 이유를 보여 주고 같은 진단을 반복하지 않는다.
- 부족한 사실과 확인이 필요한 질문만 묻는다. 확인된 답은 다음 교정에도 유지하고 다시 묻지 않는다.
- 저장했으면 대상과 반영 결과, 확인한 범위와 남은 작업을 짧게 알린다. 발행은 별도 요청으로 다룬다.

## 구분

- 저장소 문서의 언어와 위치, 형식은 **repo-docs** 스킬이 맡는다. 문장 명료성과 군더더기는 **technical-writing**, **unslop** 스킬을 쓴다. just docs는 작성자 경험을 확인하고 독자 질문으로 전개하는 일을 맡는다.
- 등록 Vault의 노트를 읽거나 고치는 일은 **markdown-notes-agent** 스킬이 맡는다. 채용 공고별 이력서와 포트폴리오는 **career** 스킬이 맡는다.
