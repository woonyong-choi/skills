# 학습 구현

궁금했던 원리가 실제 코드와 저장·실행 과정에서 어떻게 이어졌는지 같은 예제로 설명한다.

## 시작 전 확인

- 학습의 출발점과 구현해 연결하려던 동작을 작성자에게 확인한다. 과제나 팀 소개부터 시작하도록 강제하지 않는다.
- 당시 자료의 버전과 본인 역할, 처음 구현한 범위와 후속 확장을 구분한다. 코드만으로 개인의 선택 이유를 확정하지 않는다.
- 독자가 이미 아는 입력과 마지막에 확인할 결과를 고른다. 글 전체에서 같은 값과 대상을 유지한다.

## 전개

1. 출발점과 구현한 대상을 짧게 잇는다. 같은 목적을 도입, 범위 설명, 예고에서 반복하지 않는다.
2. 익숙한 입력이 처리되는 전체 경로를 보여 준다. 비교할 실제 시스템이 있으면 같은 단계를 맞춰 구현 범위를 드러내되, 다른 구조를 같은 파이프라인으로 단정하지 않는다.
3. 다음 처리를 이해하는 데 필요한 원리를 설명한다. 그 원리로 어떤 문제가 생기고 무엇이 필요해지는지 연결한 뒤 구현의 선택과 감수한 비용을 쓴다.
4. 선택한 구조를 실제 코드, 저장 형식, 상태 변화로 확인한다. 정의와 장단점을 따로 늘리지 말고 해당 동작 안에서 설명한다.
5. 처음의 입력을 끝까지 따라가며 단계나 계층마다 주고받는 값과 표현이 어떻게 바뀌는지 확인한다. 실제 실행 증거는 그 설명을 검증하는 자리에 둔다.
6. 비교 실험이 있으면 실행 조건과 결과가 허용하는 해석만 남긴다. 처음 연결하려던 원리가 구현에서 어떻게 이어졌는지 구체적인 결과로 마친다. 다음 글 예고나 막연한 성장 소감으로 결론을 대신하지 않는다.

## 문단 고치기

- 공통 [완성 검수](../../docs.md#완성-검수)를 따른다. 원리를 이미 설명했으면 설계 절에서는 적용한 판단만 남긴다. 같은 대상이라도 새 동작을 따라가는 사례는 중복으로 지우지 않는다.
- 같은 입력이 단계나 계층마다 어떤 값과 표현으로 바뀌는지 잇는다. 함수 목록이나 장점보다 앞 동작이 다음 정보를 필요로 하는 이유를 보여 준다.
- 배운 내용을 구현 중인 실습처럼 쓰지 않는다. 앞에서 설명한 기준이 다음 설계에 어떻게 쓰였는지 연결한다.

## 근거 확인

- 설계 의도, 코드가 하는 일, 관측한 효과를 따로 대조한다. 기대한 효과나 이론상 수치를 측정한 성과로 쓰지 않는다.
- 당시 측정과 이후 확장, 정상 실행과 장애 복구, 코드의 호출과 그 호출이 실제로 일으킨 일을 구분한다. 결과 해석이 달라지는 조건은 남기고 검증 일지는 본문에 나열하지 않는다.
- 직접 단 카운터, 로그, 타이머로 센 값은 그것이 무엇을 센 것인지 본문의 결과 옆에 밝힌다. 코드가 요청한 횟수인지 실제로 일어난 횟수인지처럼, 독자가 다르게 읽을 수 있는 차이를 한 문장으로 구분한다.
- 코드 블록은 기준 버전과 대조한다. 발췌를 짧게 만들려고 오류 처리나 자원 해제를 지워 의미를 바꾸지 않는다. 생략이 필요하면 범위를 밝히고 원문과 구분한다.
- 그림은 수치의 긴 나열 대신 배치와 변화, 탐색 경로를 보여 준다. 설명용 예시와 실제 실행의 값을 섞지 않는다.

## 검토

- 독자의 다음 질문이 생기기 전에 결론이나 전문 용어가 튀어나오는지 확인한다.
- 작성자의 판단을 코드 설명만으로 대신한 곳과 근거 없이 의도를 보탠 곳을 찾는다.
- 기능 목록을 읽은 느낌인지, 하나의 입력이 저장과 실행을 거쳐 결과로 돌아오는 흐름을 읽은 느낌인지 확인한다.
- 목적을 회수하는 결론과 필요한 비용은 남긴다. 바로 앞 문장의 요약, 같은 원리의 재정의, 과장된 후킹을 지운다.
