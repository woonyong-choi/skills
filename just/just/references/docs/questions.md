# 판단과 경험 확인

문장을 자연스럽게 만들기 전에 작성자가 실제로 겪고 판단한 내용을 확인한다.

## 단계

1. 원고와 관련 대화, 당시 코드, 문서, 커밋, 실행 자료에서 답을 먼저 찾는다. 기록에서 추론한 이유는 작성자의 당시 생각으로 확정하지 않는다. 현재 구현을 당시 선택의 근거로 대신 쓰지 않는다.
2. 글의 목적, 독자, 당시 궁금했던 것, 제약, 선택 이유, 본인 기여, 확인한 동작 중 전개를 바꾸는 빈칸을 찾는다. 한꺼번에 설문하지 않고 다음 문단에 필요한 질문부터 묻는다.
3. 답이 추상적이면 그 답으로 어떤 선택을 설명할 수 있는지 대조한다. 설명할 수 없으면 무엇이 부족한지 짚고 구체적인 상황이나 대안을 묻는다.
4. 기억이 흐리거나 개념을 모르면 자료에서 가능한 후보를 찾아 차이와 비용을 설명한다. 후보를 당시 경험처럼 제시하지 않고, 해당 없음과 기억 안 남도 답할 수 있게 한다.
5. 답을 당시 의도, 당시 관측, 현재 해석 중 맞는 자리에 요약해 확인한다. 후보에 동의한 것만으로 실제로 비교하거나 측정했다는 뜻으로 넓히지 않는다.
6. 확인된 답과 근거를 해당 문단에 반영한다. 모르면 그 부분의 인과 주장은 보류하고 확인 가능한 동작만 쓴다. 나머지 원고와 증거 확인은 계속한다.

## 질문을 좁히는 법

- 구현 유무와 결과는 자료로 확인하고, 자료에 없는 개인의 의도는 작성자에게 묻는다. 구현에서 추론한 이유는 후보로 제시하고 확인 전 사실로 쓰지 않는다.
- "성능 때문에"라는 답에는 읽는 양, 호출 횟수, 메모리 사용 중 무엇을 줄이려 했는지 묻는다. 측정한 효과인지 기대한 효과인지도 가른다.
- "환경의 기본값"이라는 답에는 직접 고정한 값인지 실행 환경에서 읽은 값인지 확인한다. 관측한 값을 설계 의도로 바꾸지 않는다.
- "여러 대안을 비교했다"라는 답에는 실제로 실행한 대안과 자료로만 살펴본 대안을 구분한다. 시도하지 않은 대안을 실패 경험으로 쓰지 않는다.
- 후보를 설명할 때는 "당시 이런 제약이 있었는가", "A와 B는 이 점이 다른데 어느 쪽이 목표였는가"처럼 기억을 돕는다. 선택을 유도하거나 후보를 골라야만 진행할 수 있게 하지 않는다.
- 답이 앞선 코드나 기록과 다르면 어느 버전과 시점인지 먼저 맞춘다. 설명에 맞추려고 증거를 고치지 않는다.
