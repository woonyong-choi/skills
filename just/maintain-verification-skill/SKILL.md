# 검증 스킬 유지보수

기능 맵은 앱이 바뀌는 순간부터 실제와 어긋나기 시작한다. 이 스킬은 `create-verification-skill` 스킬이 만든 스킬(또는 기능 맵이 있는 어떤 프로젝트 전용 검증 스킬)의 유지보수 루프다. 꼼꼼히 확인하는 단위는 문장 하나하나가 아니라 기능이다. 모든 기능 파일을 소스와 대조하고 모든 기능을 라이브로 써 보되, 항목 하나하나를 터미널에서 확인하지는 않는다.

## 결과

하나를 고르고 무엇인지 말한다.

- **clean.** 모든 기능이 소스와 라이브로 확인됐고 반영할 만한 수정이 없다. 브랜치도 PR도 없다.
- **changed.** PR 하나로 증명된 문서, 조작 도구, 맵 수정을 반영한다.
- **blocked.** 점검을 끝내지 못했거나 증명된 수정을 안전하게 반영하지 못했다. 무엇이 막았는지 정확히 말한다.

## 수정 범위

검증 스킬 자기 폴더(SKILL.md, features/, 그 스킬이 소유한 조작 스크립트)만 고친다. 실행 중에 제품 코드를 고치지 않는다. 맵이 설명하는데 앱이 더는 하지 않는 동작은 문서 어긋남(맵을 고친다)이거나 제품 회귀(보고하고, 문서로 덮지 않는다)다.

## 점검

0. **대상 찾기.** 유지보수할 검증 스킬을 찾는다. 본문에 실행·조작 절과 기능 맵이 있는 프로젝트 전용 스킬이다(대개 `.agents/skills/verify-*/`. 프로젝트 전용 스킬 위치는 [호스트 대응표](../just-mode/references/hosts.md)). 후보가 여럿이면 사용자에게 어느 것인지 묻는다. 없으면 대상을 지어내지 말고 멈춘 뒤 `create-verification-skill` 스킬을 알려 준다.

1. **색인 정리.** 기능 맵 README를 읽고 같은 폴더의 파일을 glob으로 찾는다. 빠진 항목, 남는 항목, 중복 항목, 깨진 항목을 고친다. 가볍게 한다. 목록을 따로 생성하지 않는다.

2. **소스 웨이브.** 기능 파일마다 읽기 전용 서브에이전트 하나를 동시에 띄운다(호스트 대응표). 각 서브에이전트는 "이 사용자 대상 기능은 어떻게 동작하는가?"를 소스로 설명하고, 문서 어긋남으로 보이는 것을 인용과 함께 짚고, 간결한 라이브 검증 방법 하나를 돌려준다. 서브에이전트는 앱을 조작하지 않고 파일을 고치지 않는다. 돌려주는 항목은 기능 요약, 소스 진입점, 어긋남으로 보이는 것(없으면 없음), 검증 방법 하나다.

3. **맞추기.** 모든 기능 파일에 대해 요약이 돌아왔는지 확인한다. 겹치는 검증 방법을 될 수 있는 한 적은 앱 상태로 합친다. 인용된 어긋남은 일부를 골라 확인한다. 문제없다는 결과는 다시 증명하지 않는다. 최근 변경을 훑어 맵에 빠진 사용자 대상 화면을 찾는다. 빠졌다고 하려면 구체적인 소스 경로가 있어야 한다.

4. **라이브 점검.** 소스가 깨끗해 보여도 반드시 한다. 조율자가 모든 조작을 맡는다. 검증 스킬 자신의 실행 모델을 따른다. 서버와 UI는 계속 띄워 두는 인스턴스 하나를 순서대로 조작하고, 금방 끝나는 CLI는 조작마다 격리된 새 세션을 쓴다(이 스킬이 아니라 검증 스킬의 실행 절이 정한다). 모든 기능을 최소 한 번 써 보고, 어떤 실패가 나든 점검 내내 불변 조건 셋을 지킨다. (1) 인스턴스가 예상 밖의 동작을 했다면 상태를 다시 확인하기 전에는 조작하지 않는다. 첫 조작 전에 진단하고, 세션이 단위인 곳에서는 새 세션마다 진단하고, 실패한 조작 뒤에 다시 진단한다. 진단으로 잡히지 않는 실패(프로세스는 정상인데 UI가 멈춘 상태)라면 저절로 풀리길 기대하지 말고 알려진 상태로 되돌리거나 다시 띄운다. (2) 지금까지 남긴 증거는 어떤 정리 뒤에도 남아 있어야 한다. 남아 있으리라 가정하지 말고 정해 둔 위치에서 확인한다. (3) 조작이 띄운 것은 그 조작에 더는 필요 없어지면 남겨 두지 않는다. 실패한 시도가 남긴 찌꺼기는 세션이 멈췄든, 종료됐든, 공유 중이든 치운다(공유 인스턴스라면 인스턴스가 아니라 찌꺼기를 치운다). 진단이 실패한 원인이 스킬 문서와 실제의 어긋남이면 그것도 어긋남으로 다룬다. 수정 범위 안에서 고치고 한 번 다시 시도한다. 수정이 무효로 만든 것만 다시 띄우고 그 이상은 하지 않는다. 그다음에야 점검을 `blocked`라고 한다. 들어갈 수 없는 기능은 구체적인 전제 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 있을 때만 `verified-unreachable`이다. 맵이 그 전제 조건을 빠뜨렸으면 그것은 어긋남이다. 분류 단계에서 나온 조작 도구 수정은 반영 전에 라이브로 다시 조작해 확인한다. 마지막 정리는 그 재증명까지 포함한 이번 실행의 마지막 조작 뒤에 한다. 그래서 이번 실행이 띄운 것은 실행이 끝나면 하나도 남지 않는다(증거는 스킬에 따라 남는다).

5. **분류.** 사용자 관점 설명이 틀렸거나 빠졌으면 문서 어긋남이고, 고친다. 동작은 하는데 조작 도구가 조작하지 못하면 조작 도구 빈틈이고, 고친다. 조작 도구 수정은 생성 때와 같은 헬퍼 규칙을 따른다(스크립트는 실행 가능, 호출 방법은 스킬 본문에 문서화). 앱 동작이 정말 망가졌으면 제품 빈틈이다. 사용자에게 알리도록 기록하고 이번 PR에는 넣지 않는다.

6. **반영하거나 멈추기.** changed라면 증명된 수정의 PR 하나를 만들고, 먼저 바뀐 파일을 모두 다시 읽는다. clean이나 blocked라면 PR 없이 결과와 점검 범위를 정직하게 보고한다.

간결한 실행 메모(다룬 기능, 들어갈 수 없게 만든 전제 조건, 확인된 어긋남, 결과)는 저장소 `.local/runs/verify-<이름>/`에 두고 커밋하지 않는다.
