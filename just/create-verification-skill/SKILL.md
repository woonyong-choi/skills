# 검증 스킬 만들기

제대로 된 프로젝트라면 실제 앱을 조작해 동작을 증명하는 스크립트가 필요하다. 앱을 띄우고, 사용자처럼 기능을 써 보고, 증거를 남기는 방법이다. 이 스킬은 그것을 저장소에 맞춘 프로젝트 전용 스킬로 만든다. 만든 스킬은 `.agents/skills/verify-<app>/`에 쓰고 `.claude/skills/verify-<app>`에 같은 내용을 링크한다(`ln -s ../../.agents/skills/verify-<app> .claude/skills/verify-<app>`, [호스트 대응표](../just/references/hosts.md)의 프로젝트 전용 스킬 위치). 생성 결과는 사람이 아니라 다음 에이전트를 위해 쓴다. 앱을 한 번도 본 적 없는 에이전트가 작업 도중에 사전 지식 없이 읽게 된다.

## 1. 사용자가 아니라 저장소에서 답을 찾는다

다음 질문에 코드베이스로 답하고, 관찰할 수 없는 것만 사용자에게 묻는다.

- **화면.** 사용자가 실제로 무엇을 쓰는가? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에 여럿이 있을 수 있다. 주된 것 하나를 고르고 나머지는 적어 둔다.
- **실행.** 앱을 로컬에서 어떻게 띄우는가? 저장소가 문서로 둔 개발 명령(패키지 스크립트, Makefile, README 빠른 시작)을 우선 쓴다. 포트, 환경 변수, 시드 데이터, 인증을 적는다.
- **조작.** 에이전트가 코드로 앱을 어떻게 조작할 수 있는가? 기존 테스트 도구가 먼저다. Playwright/Cypress 스펙, expect 스크립트, PTY 헬퍼, curl로 부를 수 있는 엔드포인트, 디버그 포트다. 그다음에야 범용 방법을 고른다. 웹과 Electron은 브라우저/CDP, CLI/TUI는 tmux/PTY 도구, 서비스는 일반 HTTP 요청이다.
- **관찰.** 어떤 증거를 남길 수 있는가? 스크린샷, 터미널 기록, 응답 본문, 로그, 종료 코드, DB 상태다.
- **격리.** 인스턴스 둘을 나란히 돌릴 수 있는가(포트, 데이터 폴더, 프로필)? 안 된다면 만든 스킬에 그렇게 적는다. 여럿이 쓰는 인스턴스를 동시에 조작하지 않는 편이 사용자의 세션을 망가뜨리는 것보다 낫다.

체크아웃한 코드가 그대로는 빌드되지 않거나 실행되지 않으면 스킬을 만들기 전에 먼저 고친다(또는 정확히 보고한다). 제대로 돌지 않는 코드를 기준으로 쓴 스킬은 틀린 단계를 알려 준다. 검증과 상관없는 파일이 빠져서 앱이 시작되지 않으면(API가 한 번도 서빙하지 않는 정적 폴더, 예제 설정), 만든 스킬이 그것을 검증용 임시 파일이라고 분명히 표시해 만들고 정리 단계에서 지울 수 있다.

## 2. 스킬 만들기

`.agents/skills/verify-<app>/SKILL.md`를 YAML frontmatter와 함께 쓴다. frontmatter에는 `name: verify-<app>`과 앱, 화면, 언제 쓰는지를 말하는 `description`을 둔다. frontmatter가 없으면 스킬이 등록되지 않는다. 다음 절을 두고, 각 절은 인터뷰에서 실제로 찾은 것에 근거한다(자리 표시자를 남기지 않는다).

- **실행.** 검증을 위해 앱을 띄우는 정확한 명령과 준비됐음을 아는 방법(로그 한 줄, 프롬프트). 빈 데이터 폴더에서 시작해 마이그레이션과 시드 데이터까지 마치고 쓸 수 있는 상태가 되어야 한다. 준비됐다는 것은 프로세스가 응답하는 것만이 아니라 실제로 쓸 수 있다는 뜻이다. 데이터베이스 상태 확인은 초기화 스크립트가 아직 도는 중에도 통과할 수 있다. 종료 방법도 넣는다. 금방 끝나는 CLI나 TUI에는 계속 띄워 둘 서버가 없다. 이때 실행이란 바이너리를 한 번 빌드(또는 의존성 설치)하고, 조작할 때마다 격리된 PTY나 tmux 세션을 새로 여는 것이다.
- **진단.** "이 인스턴스를 조작해도 되는가?"에 답하는 읽기 전용 확인 하나. 프로세스가 떠 있고, 버전·빌드가 맞고, 포트를 우리 프로세스가 쓰고 있고, 인증이 유효한지 본다. 무엇이든 이상해 보이면 에이전트가 이것부터 돌린다.
- **조작.** 예시가 아니라 이 저장소의 실제 선택자·명령을 쓴 조작 방법. 좌표와 탭 순서보다 잘 바뀌지 않는 식별자(ARIA 라벨, data 속성, 프롬프트 문자열, 라우트 경로)를 택한다.
- **증거.** 증명을 위해 무엇을 남기고 어디에 두는지. 증명 기준을 적는다. 내부 setter나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로로 조작한다. 마지막 화면만이 아니라 동작과 그 결과 상태를 남긴다. 보이는 것과 함께 부수 효과(쓴 파일, 넣은 행, 보낸 메시지)를 확인한다. 목(mock)은 프로덕션 코드에서도 이미 외부 시스템과 경계가 나뉜 곳에서만 쓴다. 안전한 경로가 dry-run이나 테스트 모드라면 이름을 믿지 말고 실제로 무엇을 건너뛰는지 관찰로 확인한다(파일, 네트워크, git ref). 어떤 dry-run은 여전히 네트워크를 건드리거나 브라우저를 연다.
- **정리.** 실행이 만든 인스턴스를 내리는 방법. 프로세스 이름으로 종료하지 않는다. 내가 띄운 것만 종료한다. 정리는 인스턴스와 임시 상태를 지우되 증거는 지우지 않는다. 증명 산출물은 스킬에 적어 둔 위치에 남아 정리 뒤에도 지워지지 않는다.
- **헬퍼.** 스킬에 딸린 스크립트는 실행 가능해야 하고 호출 방법이 스킬 본문에 보여야 한다. 읽는 사람이 역설계해야 하는 헬퍼는 헬퍼가 아니다.

## 3. 기능 맵 초안을 만든다

`.agents/skills/verify-<app>/features/README.md`와 찾을 수 있는 사용자 대상 기능마다 파일 하나를 만든다(라우트, 명령, 메뉴, 문서에서 상위 3~5개로 시작한다). [`references/feature-map-example/`](references/feature-map-example/)의 형식을 따라 README 색인과 기능마다 파일 하나를 둔다. 각 파일은 사용자 관점에서 답한다. 기능이 무엇인지, 어떻게 들어가는지, 조작 도구로 어떻게 조작하는지, 동작함을 증명하는 관찰 가능한 최종 상태가 무엇인지다. H2 넷은 `하위 기능`, `들어가는 방법(사용자 관점)`, `<harness>로 조작하기`, `주의할 점`이다. 시나리오에 필요한 전제 조건이 시드 데이터에 없으면 그 시나리오는 실패로 보고하고, 이유는 그 기능의 `주의할 점`에 적는다. 통과시키려고 시나리오를 느슨하게 바꾸지 않는다. 기능 맵은 저장소가 관리하는 검증 정본이다. 맵에 다른 진입점도 있는데 편한 진입점 하나만 조작했다면 그 증명은 불완전하다.

## 4. 넘기기 전에 만든 스킬을 증명한다

스킬 자신의 지시를 처음부터 끝까지 한 번 돌린다. 실행, 진단, 맵에 있는 기능 하나 조작(하나면 충분하다. 나머지는 나중 실행이 맵을 보고 다룬다), 증거 남기기, 정리다. 정리 뒤에 증거가 정해 둔 위치에 아직 있는지 확인한다. 증거까지 지워 버리는 정리 단계는 여기서 실패로 본다. 실패한 것을 고치고, 시도가 실패할 때마다 만든 정리 단계도 돌려서 깨진 시도가 프로세스와 포트를 남기지 않게 한다. 한 번도 실행하지 않은 생성 스킬은 결과물이 아니라 초안이다. 실제 대상 대신 대체 환경(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택)에서 증명했다면, 대체 환경에서는 했지만 실제 대상에서는 하지 않을 준비 단계를 모두 적는다. 그 단계들은 실제 대상에서 돌려 확인할 때까지 검증되지 않은 상태로 남는다.

## 5. 유지보수 루프를 제안한다

앱이 바뀌어도 맵이 실제와 맞게 유지되도록 사용자에게 `maintain-verification-skill` 스킬을 알려 준다. 주기는 사용자가 물을 때만 제안한다.
