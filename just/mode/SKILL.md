# mode

요청에 맞는 순서표를 골라 시작 고리, 순서표, 끝 고리 순으로 끝까지 진행한다. 오타나 문구 한 줄 수정은 고리 없이 해도 된다. 함께 설치된 스킬은 이 파일 기준 `../<이름>/SKILL.md`에 있다. 호스트마다 다른 동작(스킬 부르기, 서브에이전트, 다시 깨우기, 규칙 파일)은 [호스트 대응표](references/hosts.md)를 따른다.

## 반드시 지킬 것

| 상황 | 할 일 |
|---|---|
| 사소하지 않은 변경, 아키텍처 결정, "확실해?" | **how** 스킬을 쓴다 |
| 사용자에게 묻고 싶은 갈림길 | 아래 질문 방식 절을 따른다 |
| 모든 코드 | 데이터 모양을 먼저 적고, 담을 구조는 **principle-model-the-domain**으로 고른다 |
| 함수 경계를 넘는 코드 | 구현 전에 **architect**로 여러 설계를 병렬로 탐색한다 |
| 병렬 분배(빠짐없이 나누기, 경주, 차례 검증, 탐색 나누기) | **swarm**을 쓴다. 여러 안을 겨뤄 기준안을 고르고 좋은 부분을 옮길 때는 **arena**를 쓴다 |
| 사소하지 않은 여러 단계 작업 | 처리량 점검을 적는다(기능 개발 플레이북 3단계) |
| 모든 글(답변 포함) | **unslop**을 적용하고, 답변은 답변 절을 따른다. 스킬 문서는 **skill-sync** 스킬 `references/authoring.md`를 따른다 |
| 문서, RFC, README, PR 설명, 커밋 메시지 | 문체·용어·서식은 **repo-docs** 스킬 `references/writing.md`, 갈래와 문장 명료성은 **technical-writing**으로 쓴다 |
| 커밋 전 | **unslop**과 **no-comments**를 돌린다 |
| UI나 CLI 배포 | 프로젝트 검증 스킬(`verify-<앱>`)로 확인한다. 버그 수정이면 같은 화면에서 직접 먼저 재현한다. 사용자에게 넘기는 것은 버그 수정 1단계의 좁은 예외뿐이다 |
| 벤치마크, 직접 잰 속도·회귀 보고 | 그 숫자로 보고하거나 행동하기 전에 **benchmark-checklist**를 돌린다 |
| PR 상태 요청("PR X 확인해 줘", "CI 통과시켜 줘", "봇 지적 처리해 줘") | `playbooks/babysit.md`를 따른다. PR을 열었다는 사실만으로 시작하지 않는다. 예외는 끝 고리 4단계다. 폴링 전에 모드를 밝힌다. 단계 에이전트 안에서 `drive`를 쓰면 그 에이전트가 턴을 끝내지 못한다 |
| CI를 통과한 스택의 머지·배포 요청 | `playbooks/shipping.md`를 따른다. CI 통과는 안전하다는 뜻이 아니다. PR마다 검증 판정이 나오기 전에는 자동 머지를 걸지 않는다 |
| PR 생성, 수정, 보기, 감시, 머지 | GitHub CLI(`gh`)로 한다. Graphite(`gt`)를 요구하지 않는다. 내장 PR 도구가 있을 때의 규칙은 `playbooks/opening-a-pr.md`에 있다 |
| 리뷰 봇이나 자동 보안 리뷰의 지적 | 의심하며 하나씩 따진다. 분류는 `references/bugbot-triage.md`를 따른다 |
| 스킬 지시가 틀렸거나 스크립트가 안 돎 | 하던 일은 계속하고 스킬은 별도 PR로 고친다. 말없이 건너뛰지 않고 보고에 적는다 |
| 길거나, 자율이거나, 사용자가 자리를 비운 작업 | **show-me-your-work**로 결정 기록을 남긴다(시작 고리 6단계) |
| 서브에이전트를 띄우기 전 | [서브에이전트](references/subagents.md)를 읽고 역할, 추론 수준, 속도(빠른 실행 여부)를 고른다. 플레이북의 모든 위임, 검증자, 담당자, 감시자에 적용한다 |

## 질문 방식

1. 묻기 전에 질문을 분류한다.
2. 실행해서 관찰할 수 있는 사실이면(동작, 시간, 레이아웃, 출력, 성능, 평가가 두 안을 가르는지) `playbooks/prototype.md`로 스케치를 만들어 결과로 정한다.
3. 읽어서 알 수 있는 사실이면 조사를 계속하고 근거로 답한다. 읽기 전용 조사에서는 스케치를 만들지 않는다.
4. 되돌릴 수 없고 해석이 둘 이상인 결정만 묻는다. 어떤 실험으로도 정할 수 없는 제품·취향 결정이 여기에 든다.
5. 나머지는 합리적으로 가정하고 진행한다. 가정은 답변 끝 "가정" 줄에 적는다.
6. 자율 권한을 받았으면 그 안의 결정은 직접 내리고, 실행하고, 보고한다. 사용자가 답할 말을 정해 주거나 "~할까요?" 같은 제안을 덧붙이지 않는다. 사용자만 내릴 수 있는 결정이면 안전한 기본값을 적용하고, 결정 기록에 phase `결정 필요`로 적고, 다른 일을 계속한다. 보고에는 이유와 사용자가 대신 지시할 수 있는 내용을 쉬운 말로 적는다.
7. 사용자는 자기 말로 답한다. 그대로 입력해 돌려보낼 약어를 주지 않는다.

## 자율

- **그냥 한다.** MCP 도구는 무엇이든 쓴다. 되돌릴 수 있는 작업과 외부 행동(팀 채팅, 티켓 갱신, 평가 시작)은 묻지 않고 진행한다. 기존 문서 수정도 묻지 않는다.
- **항상 멈춘다.** 되돌릴 수 없는 쓰기 앞에서는 멈추고 확인받는다. 공유 브랜치 강제 푸시, 운영 배포, 데이터 삭제, 고객에게 보내는 메시지가 여기에 든다. 끝 고리의 PR 머지는 여기에 들지 않는다. 자율 실행 중에도 같다. 공유 브랜치는 기본 브랜치와 다른 사람이 쓰는 브랜치다. 그 브랜치의 이력 재작성(rebase, amend 뒤 push)도 여기에 든다.
- **자기 브랜치는 다시 쓴다.** 내가 만들어 혼자 쓰는 작업 브랜치에서는 순서표대로 rebase, amend, `git push --force-with-lease`를 묻지 않고 한다. 기본 브랜치의 변경은 리베이스로 받는다.
- **새 공개 문서는 승인 기준을 따른다.** 승인할 대상과 자율 실행 중 처리는 **repo-docs** 스킬의 새 문서 절이 정한다.
- **사용자의 게이트는 사용자가 정한다.** 사용자가 지정한 검사와 위 멈춤 목록은 자율 권한 아래에서도 바꾸지 않는다.
- **요청 범위를 지킨다.** 설계 요청은 설계와 필요한 설계 문서까지만 끝낸다. 자율 실행도 임의로 구현까지 넓히지 않는다. 구현까지 허용한 요청은 구현한다.
- **멈추지 않는다.** "멈추지 마", "자러 간다", "끝날 때까지 돌려", "완전히 자율로 해"는 자율 실행(`playbooks/autonomous-run.md`)으로 간다. "자율 멈춰"나 "자동 모드 멈춰"를 들을 때까지 계속한다.
- **아니라는 답도 괜찮다.** 제안이나 범위 확장을 받으면 자기 판단을 말한다. 맞다면 거절하고 반박한다. 추천은 판단이지 맞장구가 아니다. 동의는 기본값이 아니다.

## 작업 흐름

코드를 바꾸는 순서표는 시작 고리, 순서표 단계, 끝 고리 순으로 간다. 읽기 전용 순서표(아래 표에서 "코드 변경"이 아님)는 두 고리를 건너뛴다. 읽기 전용 조사에 이슈를 연결할지는 **git-issue** 스킬의 과업 연결과 기록 절이 정한다.

### 시작 고리

1. **이슈 연결.** 같은 일의 이슈가 있으면 재사용하고, 없으면 **git-issue** 스킬의 제목·본문 틀로 만든다. 목표, 제약, 완료 조건은 이슈 본문에 둔다. 진행 로그 댓글은 달지 않는다.
2. **시작 전 확인.** **git-branch** 스킬의 시작 전 확인 절대로 같은 이슈의 브랜치, PR, 워크트리와 담당자를 확인한다.
3. **브랜치와 워크트리.** **git-branch** 스킬의 이름 절과 작업 중 절대로 만든다.
4. **과업 연결.** 브랜치를 만든 뒤 `python3 <이 스킬 폴더>/scripts/hooks/task.py bind --session-id <세션 ID> --task <과업> --issue <이슈 URL>`을 실행한다. 세션 ID는 세션 시작 안내에 나오고, Codex는 생략하면 `CODEX_THREAD_ID`를 쓴다. `--task`는 그 브랜치의 과업 이름이다.
5. **판 상태.** 이슈를 "진행"으로 옮긴다. 들어가는 조건은 **git-issue** 스킬 `references/project-status.md`의 상태표가 정하고, 판이 없으면 같은 문서의 새 저장소 절차로 만든다.
6. **결정 기록 시작.** 작업용 파일은 모두 `.local/` 아래에 둔다(**repo-docs** 스킬의 비공개 작업 파일 절). `bash <show-me-your-work 폴더>/scripts/log.sh .local/decisions/<과업>.tsv start <decision> <why> <evidence> <result>`로 첫 줄을 쓴다. 과업 이름 규칙은 **show-me-your-work** 스킬의 기록을 두는 곳 절이 정한다.

순서표 단계를 진행하는 동안 단계 경계마다 결정 기록에 한 줄을 남긴다.

### 끝 고리

판 상태 이동은 **git-issue** 스킬 `references/project-status.md`의 상태표를 따른다. 진행에서 검토로 가는 것은 `Closes`로 이은 PR뿐이다.

1. **PR 열기.** `playbooks/opening-a-pr.md`를 따른다. 이슈를 잇는 표기(`Closes`, `Refs`)는 **git-issue** 스킬의 닫기 절을 따른다.
2. **리뷰.** **interrogate**로 [역할별 모델](references/models.md)에 따라 검토하고 지적마다 `P1`~`P5`를 붙인다. 판정과 P1·P2 지적을 PR 댓글로 올린다. 공개 형식은 **git-pull-request** 스킬 `references/review.md`의 공개 피드백 형식을 따른다. 반영 확인은 그 코드를 쓴 에이전트가 아닌 다른 에이전트가 하고, 반영 뒤 남은 P1·P2 수를 다시 센다.
3. **검증 판정.** PR이 하나여도 코드를 쓰지 않은 검증자가 PR head에서 변경을 사용자처럼 실행하고 그 PR에 검증 판정을 남긴다. 검토자의 겸임과 유효한 기존 시험 재사용은 [서브에이전트](references/subagents.md#결과-받기)를 따른다. 공개 형식은 **git-pull-request** 스킬 `references/review.md`의 공개 피드백 형식을 따른다. 방법은 `playbooks/shipping.md` 1단계를 따른다.
4. **머지 조건.** 조건의 정본은 **git-pull-request** 스킬의 머지 조건 절이다. `READY` 판정은 `watch-pr`를 drive 모드로 돌려 기다린다(`playbooks/babysit.md`). 끝 고리에서는 요청이 없어도 이렇게 돌린다. 머지 조건이 막혀 사용자 결정이 필요하면 결정 기록에 phase `결정 필요`로 적고, 이슈를 "보류"로 옮기고, 다음 일로 간다.
5. **squash 머지.** squash 메시지와 머지 명령은 **git-branch** 스킬의 머지 절을 따른다.
6. **정리.** 이 작업에서 만든 워크트리와 브랜치만 **git-branch** 스킬의 정리 절을 따라 지운다.
7. **성과 확인.** 머지 뒤 훅 안내를 따른다. 자율 실행 중에는 사용자에게 묻지 않고 결정 기록에 phase `경력 후보` 줄로 남긴다.

## 주석

주석 규칙의 정본은 **code-style** 스킬 `references/structure.md`의 공개 범위와 주석 절이고, 코드 파일을 고치기 전에 훅이 그 절을 넘긴다. 정리는 커밋 전에 **no-comments**로 한다.

## 순서표 고르기

할 일 목록을 만들고, 작업별 할 일보다 앞에 고른 순서표의 단계를 그대로 옮긴다. 하지 않을 단계도 남기고 `skip: <이유>`를 단다. 크거나 여러 곳에 걸친 일, 사용자가 자리를 비우고 나중에 믿고 볼 일, 맞는 순서표가 없는 일은 **figure-it-out**으로 보낸다. 여러 날, 많이 쌓인 PR, 조정자 하나 아래 여러 서브에이전트인 프로그램은 오케스트레이션으로 보낸다.

| 순서표 | 언제 | 코드 변경 |
|---|---|---|
| 조사(`playbooks/investigation.md`) | 읽기 전용 질문. X는 어떻게 동작하나, 왜 이렇게 만들었나, 무엇을 해야 하나 | 아님 |
| 버그 수정(`playbooks/bug-fix.md`) | 보고된 결함을 재현하고 근본 원인을 고친다 | 맞음 |
| 성능 문제(`playbooks/perf-issue.md`) | 측정으로 확인된 느림을 한 번 고친다 | 맞음 |
| 힐클라이밍(`playbooks/hillclimb.md`) | 지표 하나를 가설과 측정 반복으로 꾸준히 올린다 | 맞음 |
| 실행 중 포렌식(`playbooks/runtime-forensics.md`) | 살아 있는 프로세스를 계측해 누수, 헛도는 CPU, 글리치를 진단한다 | 아님 |
| 트레이스 포렌식(`playbooks/trace-forensics.md`) | 넘겨받은 프로파일·트레이스·스냅샷으로 진단한다 | 아님 |
| 기능 개발(`playbooks/feature.md`) | 정해 둔 데이터 모양에서 새 동작을 만들거나 바꾼다 | 맞음 |
| 리팩터링(`playbooks/refactoring.md`) | 동작은 지키고 구조를 바꾼다 | 맞음 |
| 프로토타입(`playbooks/prototype.md`) | 버릴 스케치로 설계·동작 갈림길을 관찰로 정한다("목업 만들어 줘", "스케치해서 정하자") | 아님 |
| 화면 동등성(`playbooks/visual-parity.md`) | 두 구현이나 스타일 체계를 픽셀 단위로 맞춘다 | 맞음 |
| 스킬 작성·수정(`playbooks/authoring-a-skill.md`) | SKILL.md를 쓰거나 고친다 | 맞음 |
| 평가(`playbooks/eval.md`) | 스킬·구조·프롬프트 변경이 에이전트 동작에 주는 영향을 확인한다 | 아님 |
| PR 돌보기(`playbooks/babysit.md`) | PR이나 스택을 머지 준비까지 끌고 간다 | 기존 PR |
| 배포(`playbooks/shipping.md`) | CI를 통과한 스택을 따로 검증하고 아래부터 머지한다 | 기존 PR |
| 자율 실행(`playbooks/autonomous-run.md`) | "끝날 때까지 돌려", "자율로 해". 멈추라고 할 때까지 판의 일을 계속 처리한다 | 맞음 |
| 오케스트레이션(`playbooks/orchestrate.md`) | 여러 날, 수십 개 PR과 서브에이전트에 걸친 프로그램. 에이전트 하나가 세션 예산 안에 끝낼 일은 맞는 순서표로 종료 조건까지 혼자 진행한다(단일 과업) | 맞음 |

## 답변

- **맨 앞 "할 일" 줄.** 사용자만 할 수 있는 일을 적는다. 없으면 "할 일: 없음"이라고 쓴다. 결정 필요 목록을 물으면 그 목록을 맨 앞에 둔다.
- **맨 끝 "가정" 줄.** 확인하지 않고 정한 가정을 한 줄로 적는다.
- **원칙 인용.** 결정에 영향을 준 원칙마다 이름과 그 원칙 때문에 바뀐 선택을 적는다. 이번 세션에 그 원칙 SKILL.md를 직접 읽었을 때만 인용한다.
- **짧은 평서문.** 한 문장에 생각 하나를 담고 마침표로 끝낸다. 초안부터 깨끗하게 쓴다.
- **엠 대시와 문장 중간 콜론을 쓰지 않는다**(unslop 규칙 13, 14). 목록 앞의 콜론은 괜찮다. 파일 목록과 굵은 절 제목도 문장으로 쓴다("**검증.** CDP로 처음부터 끝까지 확인했다").
- **짧게 쓴다고 내용을 빼지 않는다.** 플레이북이 요구하는 절(세부, 절충, 선택, 열린 결정)은 모두 남긴다. 각 플레이북의 답변 절에는 그 플레이북에만 있는 내용만 적는다.
- **쓰는 사람과 이어받을 사람의 영향을 먼저 적는다.** 이 일이 누구를 위한 것이고 그들에게 무엇이 바뀌는지, 다음 엔지니어가 무엇을 물려받는지 먼저 적는다. 둘 다 말할 수 없으면 일이나 설명이 잘못된 것이다.
- **지어내지 않는다.** 이번 세션에 직접 만들거나 읽은 것만 링크한다. PR 링크는 `https://github.com/<owner>/<repo>/pull/<number>` 형식이다.
- **주장마다 근거나 표시를 단다.** 같은 문장 안에 근거를 달거나 측정, 추론, 추측 중 하나로 표시한다. 내가 돌릴 수 있는 확인을 사람에게 넘기지 않는다.
