# 실행 중 포렌식

진단을 맡는다. 소스에서 추리하지 않고 살아 있는 프로세스를 계측한다. 결과물은 수정이 아니라 근거를 단 진단이다.

## 단계

1. 맞는 화면에서 살아 있는 신호를 잡는다. 프로젝트 검증 스킬(`verify-<앱>`)이나, 없으면 Playwright로 Chrome DevTools Protocol(CDP)에 붙는다. CPU를 계속 쓰며 헛도는 프로세스면 CPU 프로파일을, 누수면 힙 스냅샷을, 화면 결함이면 CDP 트레이스를 잡는다. 추측이 아니라 실제 결과물이어야 한다. 결과물은 `.local/runs/trace-<이름>/`에 둔다.
2. 결과물을 결정적 증거로 줄인다. 핫 패스 위의 함수, 누수된 객체에서 GC 루트까지의 리테이너 체인(retainer chain), 입력 없이 도는 루프가 그런 증거다. 큰 결과물은 서브에이전트에서 파싱하고(**principle-guard-the-context-window** 원칙 스킬), 줄인 발견만 주 대화에 둔다.
3. 믿기 전에 메커니즘을 증명한다. 돌고 있는 프로세스에 CDP eval로 계측을 넣거나, 다시 로드하지 않고 실행 중인 코드를 바로 고쳐 가설을 싸게 확인한다.
4. 발견을 소스로 되짚는다. 파일, 심볼, 메모리를 할당하거나 작업을 예약(schedule)하는 줄을 찾는다.
5. 처리량 점검은 한 줄로 둔다. `처리량 점검: 해당 없음, 읽기 전용 진단`.

## 답변

- 잡은 신호, 줄인 발견, 메커니즘을 증명한 방법, 소스 위치, 결과물 경로를 적는다.
- 요청이 없으면 수정하지 않는다. 원인을 알면 버그 수정(`playbooks/bug-fix.md`)이나 성능 문제(`playbooks/perf-issue.md`)로 넘긴다.
