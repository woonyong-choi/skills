# 영향 범위

배포 전에 변경이 다른 곳에서 무엇을 깨뜨리는지 찾는다. "X의 영향 범위", "이거 뭐 깨질 수 있어?", 아직 믿기 어려운 작은 diff를 검토할 때 쓴다.

`how`, `why`와 짝을 이룬다. `how`는 코드가 무엇을 하는지 알려 준다. `why`는 왜 그런 구조인지 알려 준다. 영향 범위는 다른 곳에서 무엇을 깨뜨리는지 알려 준다.

호출부를 나열하는 것은 이 스킬의 일이 아니다. 그건 에이전트가 grep으로 1초면 한다. 할 일은 grep으로는 보이지 않는 깨짐을 찾는 것이다.

## 내가 쓴 글을 믿지 않는다

그럴듯하게 들리는 영향 범위 분석 글은 가치가 없다. 참이든 아니든 설득력 있게 읽힌다. 그러니 글로 끝내지 않는다. 분석 전체가 기대고 있는 사실 한두 개를 찾아 코드를 돌려 증명한다.

### 얼마나 확실한가

변경이 안전하다는 근거가 되는 사실마다, 비용이 크지 않은 선에서 이 목록의 되도록 아래 단계까지 확인하고, 어느 단계에서 멈췄는지 밝힌다.

1. 내가 그렇다고 말했다. 그것만으로는 가치가 없다.
2. 해당 줄을 가리켰다. 실제 `file:line`, 또는 라이브러리 자체 소스.
3. 나쁜 경우가 일어날 수 없음을 보였다. 실패 경로를 단계별로 따라가 보니 거기까지 이어지지 않는다.
4. 돌려 봤다. 실제 코드를 호출하고 내가 틀리면 눈에 띄게 실패하는 스크립트나 테스트.
5. 실행 중인 앱에서 재현했다.

4단계는 보통 앱에 실제로 들어가는 것과 같은 라이브러리를 가져와 걱정되는 바로 그 함수를 호출하는 작은 스크립트 하나다.

## 단계

1. 변경을 읽는다. diff, 추가·변경·삭제한 심볼, 그리고 이제 무엇을 다르게 하는지. diff가 드러내지 않는 부분도 포함한다. PR과 커밋은 `why` 2단계로 가져온다.
2. 안전의 근거가 되는 사실 하나를 찾는다. 위험해 보이는 변경 대부분은 사실 하나 덕분에 안전하다. "이 호출은 이미 쓸모없어진 캐시 항목만 지우고 다른 일은 하지 않는다" 같은 것이다. 그 사실을 찾는다. 그것이 성립하면 위험해 보이는 경우 대부분이 한 번에 정리된다. '혹시 이럴 수도' 하는 목록을 길게 늘어놓지 말고 여기에 시간을 쓴다.
3. grep으로 찾을 수 없는 곳을 본다. 호출하는 라이브러리의 소스를 읽고, 고정된 버전과 로컬 패치를 확인한다. 언제 실행되는지 따져 본다. 마이크로태스크, 언마운트와 정리, Solid와 React의 차이. 심볼 검색이 놓치는 것을 따라간다. API가 돌려주는 JSON, DB 열, 와이어 형식, 같은 바이트를 읽는 다른 언어, 기능 플래그, 호출을 세 번 거친 하위 코드.
4. 위험마다 정직하게 따진다. 실제로 일어날 확률과 일어났을 때의 실제 비용을 매긴다. 확인된 위험은 남긴다. 확인해 보니 문제없는 것은 따로 나열한다. 규칙은 `why`와 같다. 실제 `file:line`을 인용하고, 아무것도 찾지 못한 검색도 답이며, 호출부나 API를 절대 지어내지 않는다.
5. 사실 하나를 증명한다. 실제 코드를 돌리는 스크립트나 테스트를 쓰고, 돌리고, 실제 결과를 붙인다.
6. 크거나 넓은 변경은 `arena`로 돌린다. 같은 질문을 여러 모델에 묻고 답을 합친다. 모델마다 잡는 실제 버그가 다르다.

## 돌려줄 것

- **무엇을 하나.** 무엇이 바뀌었는지. 뻔하지 않은 부분도 포함한다.
- **안전의 근거가 되는 사실 하나.** 밝히고, 몇 단계까지 갔는지 말하고, 증명을 보여 준다. 증명하지 못했으면 미증명이라고 쓴다.
- **위험.** 각각 어떻게 깨지는지, `file:line`, 얼마나 일어나기 쉽고 얼마나 나쁜지, 어떻게 확인하는지 적는다. 중요한 것은 증명을 붙인다.
- **문제없음.** 확인한 것과 괜찮은 이유.
- **머지 전에.** 실제 버그를 잡는 가장 적은 비용의 테스트나 재현. 직접 쓴 스크립트도 포함한다.

`unslop`을 거쳐 쓰고, 실제 코드를 인용하고, 공개된 곳에 올리기 전에 비공개 내용을 지운다.

**답변:** 위의 분석 글. 안전의 근거가 되는 사실 하나는 증명됐거나 미증명으로 표시돼 있어야 한다.
