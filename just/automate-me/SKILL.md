# Automate me

사용자의 작업 관례를 에이전트가 따를 스킬로 만드는 단계별 흐름이다. 결과물은 사용자에게 맞춘 `-mode` 스킬 하나다(예: `jay-mode`, `priya-mode`).

이 스킬은 다른 셋을 조율한다. 본문 안의 캐내기 단계(1단계), 작성용 `skill-creator` 스킬(없으면 SKILL.md 형식을 직접 작성), 글 다듬기용 **unslop** 스킬이다. 순서를 정할 뿐, 그것들을 대신하지 않는다.

## 흐름

### 0. 기존 스킬 확인

프로젝트 전용 스킬 위치([호스트 대응표](../just-mode/references/hosts.md))와 현재 호스트의 사용자 스킬 설치 폴더에서 사용자 핸들과 맞는 `**/*-mode/SKILL.md`를 재귀로 찾는다. mode 스킬은 맨 위뿐 아니라 개인 범주 폴더(`<스킬 위치>/<handle>/`)에 있을 수 있다. 있으면 사용자에게 질문해 의도를 확인한다(이미 "내 스킬 고쳐 줘" 같은 말을 했으면 묻지 않는다).

- 기존 스킬 고치기(다시 실행할 때 기본)
- 새로 시작하기(드물다. 하기 전에 이유를 묻는다)

고치기 모드에서는 나머지 흐름이 이렇게 바뀐다.

- 1단계는 스킬을 마지막으로 고친 뒤의 기록만 캐낸다(`git log -1 --format=%cI <path>`).
- 2단계는 처음부터 무엇을 담을지가 아니라 무엇이 바뀌었거나 빠졌는지 묻는다.
- 4단계는 기존 파일을 제자리에서 고친다. 사용자가 반박하지 않은 절은 그대로 둔다. 새 근거가 있는 절은 고친다. 정말 새로운 규칙에만 새 절을 더한다.

### 1. 기록 캐내기

서브에이전트를 나눠 띄우기 전에 현재 작업 공간의 대화 기록을 찾는다. 위치는 호스트 대응표의 대화 기록 위치에서 현재 프로젝트에 해당하는 곳이다. 그 경로만 쓴다. 모든 프로젝트의 대화 기록 폴더를 가로질러 glob하지 않는다. 그러면 작업 공간 경계를 넘어 상관없는 프로젝트의 비공개 대화를 읽게 된다.

그 범위 안의 최근 에이전트 대화에서 되풀이되는 패턴을 훑는다. 기록을 조각으로 나눠 서브에이전트 여러 개를 병렬로 돌린다(예: 최근 2~4주를 세 조각으로 나눈다. 조각마다 자료가 충분해야 한다). 각 서브에이전트의 추론 수준은 일에 맞게 고른다([서브에이전트](../just-mode/references/subagents.md#추론-수준과-속도-고르기)). 조각마다 캐내는 서브에이전트는 부모가 준 작업 공간 범위 경로에서 대화 기록을 읽고, 아래 신호를 찾고, 찾은 패턴을 근거 위치와 함께 짧은 목록으로 정리해 돌려준다. 기본으로 찾을 만한 신호는 다음과 같다.

- 답변 취향(길이, 어조, 형식, "쉽게 말해 줘" 같은 교정)
- 위임 습관(서브에이전트, 모델, 전문 작업 흐름, 병렬성)
- 검증 방식("완료"의 뜻, 단위 테스트인지 실제 실행 재현인지, 검토자)
- 코드와 글 작성 규칙(스타일, 인용하는 원칙, 린트·포맷 도구)
- 과정 관례(워크트리, 커밋, PR, 리뷰·머지 도구)
- 메타 취향(작업 중에 스킬 고치기, 새 스킬 제안하기)

신호를 규칙 후보로 올리기 전에 조각끼리 대조한다. 두 조각 이상에서 본 패턴은 신뢰도가 높다. 하나뿐인 신호는 약하고 대개 버린다.

### 2. 사용자에게 직접 묻기

캐내기로는 아직 대화에 나온 적 없는 의도를 찾을 수 없다. 사용자가 답을 처음부터 직접 쓰게 하지 말고 구조화된 객관식으로 질문한다(질문 도구가 있으면 그것을 쓴다. 호스트 대응표의 사람에게 묻기).

질문은 한두 개로 하고, 질문마다 선택지를 4~6개 두고, 범주 질문은 여러 개 고를 수 있게 한다. 넓게 시작하고("어느 영역이 가장 중요한가요?"), 고른 영역에 대해 구체적인 선택지로 이어 묻는다. 구조화된 질문들이 끝나면 선택지가 놓친 것을 잡는 자유 질문 하나를 한다.

질문 20개를 쏟아 내지 않는다.

### 3. 찾은 것 묶기

합친 신호를 절로 묶는다. 흔한 절은 다음과 같다(해당하는 것만 쓴다).

- **답변 문체.** 길이, 어조, 형식.
- **자율성.** 묻지 않고 얼마나 할지, MCP 도구 사용.
- **먼저 이해하기.** 변경의 범위를 잡거나 조사할 때 어떤 스킬을 쓸지.
- **서브에이전트.** 기본값, 병렬성, 일에 맞는 모델, 전문 작업 흐름.
- **글 / 코드 작성 규칙.** 원칙, 린트 도구, 스타일 가이드.
- **검토와 검증.** 재현 방식, 검증 스킬, 실제 환경 테스트 도구.
- **과정.** git 워크트리, 커밋, PR, 리뷰·머지 도구.
- **스킬.** 스킬 작성 습관, 스킬부터 고치기, 새 스킬 제안하기.

**just-mode** 스킬이 형식의 예다. 어느 정도로 자세히 쓰는지 보려고 읽는다. 내용은 베끼지 않는다. 사용자의 규칙은 just-mode의 규칙과 같지 않다.

### 4. 스킬 초안 쓰기

`skill-creator` 스킬이 있으면 그것으로 스킬을 쓴다. 없으면 SKILL.md 형식(frontmatter `name`·`description`)을 직접 작성한다. 정할 것은 다음과 같다.

- **경로.** 기존 mode 스킬의 범주를 지킨다. 새 mode라면, 저장소에 그 핸들의 개인 범주가 이미 있을 때 `.agents/skills/<handle>/<handle>-mode/SKILL.md`를 쓴다. 아니면 프로젝트의 `.agents/skills/<handle>-mode/SKILL.md`를 기본으로 한다. 프로젝트에 쓸 때는 `.claude/skills/` 아래 같은 경로에 같은 내용을 링크한다(호스트 대응표의 프로젝트 전용 스킬 위치). 사용자가 개인 스킬을 원하면 현재 호스트의 사용자 스킬 설치 폴더 아래 `<handle>-mode/`에 쓴다.
- **핸들.** 사용자의 이름이나 사용자가 고른 식별자를 쓴다.
- **frontmatter `description`.** "코드 작성"이나 "PR 검토" 같은 일반 낱말이 아니라 사용자 이름, `<handle>-mode` 스킬 부르기, "이 사람 방식으로 작업" 같은 요청에서 호출되게 한다.
- **frontmatter 형식.** SKILL.md frontmatter의 YAML 규칙을 따른다. `description`은 YAML 스칼라 하나로 둔다. 문장 부호나 줄바꿈 때문에 필요하면 따옴표로 감싸거나 `description: >-` 뒤에 들여 쓴 이어지는 줄을 쓴다.
- frontmatter `disable-model-invocation: true`를 기본으로 둔다. 사용자가 자기 mode를 매 턴 적용하길 명시적으로 원할 때만 뺀다.

### 5. 글 다듬기

모든 줄에 **unslop** 스킬과 (있으면) `skill-creator`의 글쓰기 지침을 적용한다.

초안을 사용자에게 보여 주고 피드백을 받는다. 여러 번 반복할 것을 예상한다. 가차 없이 줄인다. mode 스킬은 설명서가 아니다.

### 6. 반영하기

기본 브랜치에서 딴 워크트리에서 작업한다. 기본 브랜치 이름은 `git symbolic-ref --short refs/remotes/origin/HEAD`로 알아낸다. 커밋하고 PR을 연다. 기본 브랜치에 직접 push하지 않는다.

## 지킬 선

- **대화 하나에 과적합하지 않는다.** 한 번 말하고 다른 때 뒤집은 취향은 잡음이다. 여러 번 나온 것만 규칙으로 만든다.
- **재치 부리지 않는다.** 다른 스킬의 내용을 다시 쓰거나, 비유를 지어내거나, 에이전트 독자를 위해 "시적인" 글을 쓰는 것은 비용만 들고 얻는 것이 없다. 실제로 할 일만 쓴다.
- **붙여 넣지 말고 참조한다.** 사용자가 쓰는 다른 스킬은 붙여 넣은 발췌가 아니라 경로 참조로 둔다. 사용자가 다른 곳에서 관리하는 원칙 문서도 마찬가지다.
- **절을 최소로 둔다.** 사용자가 그 영역에 기본값이 아닌 구체적인 규칙이 있을 때만 절을 더한다. "분명하게 소통한다"는 절이 아니다. "짧은 문단. 선택지를 비교할 때는 표. 항목이 정말 나란할 때만 글머리 기호."는 절이다.
- **관례는 일반적인 이름으로 쓴다.** 명령문에서는 작성자 이름이 아니라 "사용자"를 쓴다.
- **대칭을 억지로 맞추지 않는다.** 적어 둘 만한 과정 규칙이 없는 사용자라면 과정 절을 통째로 건너뛴다.

## 평가

`-mode` 스킬은 주관적인 결과물이다. `skill-creator`식 테스트·반복 벤치마크 루프는 여기서 쓸모가 없다. 사용자와 함께 읽어 보며 확인한다. 사용자 본인 방식대로 읽히는가? 놓친 것이 있는가? 그다음 반영한다.

description 최적화 루프는 스킬이 알맞은 요청에서 호출되는 정확도가 실제로 문제가 될 때만 돌린다.

## 쓰지 않을 때

- 사용자가 작업 관례가 아니라 특정 작업용 스킬을 원하면 `skill-creator`만 쓴다(없으면 SKILL.md 형식을 직접 작성한다). 캐내기는 필요 없다.
- 사용자가 좁은 작업 흐름 하나(예: "내가 커밋 메시지 쓰는 법")를 담고 싶어 한다. 그것은 mode 스킬이 아니라 일반 스킬이다.
