# 설계 스케치 러너 프롬프트

2단계에서 조율자는 이 파일을 병렬 후보 러너 모두에게 그대로 넘기고, 작업마다 달라지는 입력을 앞뒤에 채운다. 작업, 1단계 사전 조사 결과물, 격리된 작업 디렉터리, 출력을 쓸 경로다. 작업 디렉터리는 가능하면 git 워크트리, 아니면 스케치 디렉터리 아래 러너별 하위 디렉터리다. 중요한 것은 후보끼리 서로 영향을 주지 않는 것이다.

architect의 병렬 탐색에서 후보 설계 하나를 만든다. 먼저 **architect** 스킬을 끝까지 읽는다. 지금 그 작업 흐름 안에 있다. 후보 설계 묶음을 낸다. 타입 스케치, 함수 시그니처, 모듈 구성도, 그리고 [`rationale-template.md`](rationale-template.md) 형식의 근거 글이다.

다음 원칙을 지킨다. 조율자는 이 기준으로 후보를 비교해 기준안을 고른다.

- 호출부 사용 예 먼저. 타입보다 먼저 README 형식의 사용 예와 실제 호출 위치 두세 곳을 쓰고, 타입 스케치는 거기서 도출한다. 사용 예가 명세다. 둘은 일치해야 하므로 어긋나면 사용 예가 아니라 스케치를 고친다.
- 데이터 구조 먼저. 핵심 타입이 맞으면 코드는 저절로 분명해진다. 주된 접근 패턴마다 제안한 구조에서 데이터를 어떻게 찾는지 따라가 본다. 답이 "나중에 맵 / 인덱스 / 캐시를 더하면 된다"면 구조가 틀린 것이다.
- 인터페이스 깊이. 공개 인터페이스 크기에 비해 그 뒤에 숨긴 기능을 비교한다. 구현이 덜 단순해지더라도 복잡도를 호출되는 쪽으로 끌어들이는 단순한 인터페이스를 고른다. 전송·와이어 타입을 공개 API에 두지 않는다. 인터페이스 뒤에서 도메인 타입으로 파싱한다.
- 공유 상태: 두 주체가 함께 쓸 수 있으면 "무슨 일이 생기나?"를 묻는다. 답이 "아무 일도 없다"가 아니면 **principle-separate-before-serializing-shared-state** 원칙 스킬에 따라 기본을 주체별 상태로 두고 읽기 경계에서 합친다.
- 경계를 드러낸다. 본문에는 `not implemented` 오류, 까다로운 로직에는 `// TODO` 의사 코드, 의도와 불변 조건을 밝히는 문서 주석. 독자가 타입과 시그니처만 읽고 입력에서 출력까지 데이터를 따라갈 수 있어야 한다.
- **principle-encode-lessons-in-structure** 원칙 스킬에 따라 불변 조건을 타입에 담는다. 잘못 쓰기 어려운 타입 > 실행 시 검사 > 설명 주석 순으로 낫다.
- **principle-boundary-discipline** 원칙 스킬에 따라 경계에서 검증하고 안에서는 타입을 믿는다. 비즈니스 로직은 순수 함수로 쓴다. 입출력을 맡는 바깥 계층(shell)은 얇게 둔다.
- 불변 조건마다 정본은 하나다. 여러 곳에 복사해 손으로 맞추지 말고 정본에서 도출한다.
- 해당하면 **principle-make-operations-idempotent** 원칙 스킬에 따라 상태 전이를 멱등으로 만든다. 작업이 두 번 실행되거나 중간에 크래시가 나면 어떻게 되는지 따져 본다.
- 짧은 호출 사슬. 흐름을 따라가는 데 파일 세 개 넘게 필요하면 **principle-laziness-protocol**과 **principle-minimize-reader-load** 원칙 스킬에 따라 계층을 평평하게 한다.

이 러너는 병렬 러너 중 하나이고, 러너마다 다른 모델에서 돈다. 지금 모델이 만들 수 있는 가장 좋은 설계를 낸다. 다른 러너를 의식해 무난한 쪽으로 물러서지 않는다. 후보 사이의 차이를 보고 기준안을 고르고 다른 후보에서 가져올 부분을 정한다. 안전해 보이는 중간으로 수렴하면 탐색의 의미가 없어진다.
