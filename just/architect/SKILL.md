# 설계 스케치

타입, 함수 시그니처, 클래스 형태, 모듈 경계를 `not implemented` 본문과 의사 코드로 스케치한다. 여러 모델의 관점을 종합하고, 구현까지 허용한 요청일 때만 코드를 채운다.

## 시작

시작하기 전에 단계마다 항목을 하나씩 둔 할 일 목록을 만든다.

1. 사전 조사
2. 스케치
3. 합의
4. 구현
5. 폐기

## 1. 문제 사전 조사

새 코드가 건드리는 모든 시스템의 실제 머릿속 모델을 세운다. 관련 하위 시스템에 **how** 스킬을 돌린다. 파일 이름만 대는 것은 사전 조사가 아니다. `how`가 정한 형식대로 아키텍처 설명을 만든다. 설계가 소유 관계나 계층을 새로 정하면 기존 구조에도 **why** 스킬을 돌린다. 그러면 기존 구조의 근거를 추측하지 않고 지켜야 할 제약으로 다룰 수 있다.

1단계는 연결할 주변 시스템이 전혀 없는 완전히 새로운 작업일 때만 건너뛴다.

## 2. 스케치

설계 스케치 작업과 1단계 사전 조사 결과물을 넣어 **arena** 스킬을 돌린다. 각 러너의 프롬프트로 `references/runner-prompt.md`를 넘긴다.

러너 구성과 실행할 수 없는 모델 처리는 **arena** 스킬 1단계의 러너 규칙을 따른다. 추론 수준은 `judgment`를 따른다([역할별 모델](../just/references/models.md)).

두 번 설계한다. 첫 안이 충분해 보여도 종합 전에 구조가 확연히 다른 후보를 적어도 둘 요구한다. **principle-exhaust-the-design-space** 원칙 스킬을 구체화한 것이다. 한 구조 안에서 일부만 고친 안이 아니라 구조 전체가 다른 대안이어야 한다.

종합 전에 모든 후보를 [`references/design-red-flags.md`](references/design-red-flags.md)로 걸러 낸다. 다음 기여자는 연 파일만 보고, 가장 가까운 예시를 베끼고, 컴파일되는 가장 짧은 길을 택하는 에이전트라고 가정한다. 한 파일에서 맞아 보이는 변경이 저장소 전체에서도 맞는 설계를 고른다.

쓸 만한 후보는 인터페이스 깊이로 비교한다. 더 작고 단순한 공개 인터페이스 뒤에 더 많은 복잡도를 숨기는 설계를 고른다. 풍부한 인터페이스는 기능을 여러 계층에 흩지 않고 한곳에 모으므로 호출 단계를 짧게 유지할 수 있다.

Arena는 종합한 설계 묶음 하나를 돌려준다. 그 종합 결정이 근거 문서의 "종합 결정" 절을 채운다.

## 3. 합의(선택)

설계 요청이면 종합한 설계와 필요한 설계 문서까지만 내고 끝낸다. 구현까지 허용한 요청이면 바로 구현에 들어간다. 자율 실행도 요청 범위를 넓히지 않는다.

호출한 사람이 명시적으로 요청할 때만 확인 지점을 둔다. "/architect 확인 지점 포함", "구현 전에 멈추고 보여 줘" 같은 요청이다. 이때는 종합한 설계를 보여 주고 승인을 기다린다.

어느 쪽이든 종합한 결과는 **principle-foundational-thinking** 원칙 스킬의 "뼈대 먼저" 방식대로 별도 커밋으로 낼 수 있다. 코드를 채우는 동안 미리 계획하고 범위를 정한 깨짐은 **principle-outcome-oriented-execution** 원칙 스킬에 따라 괜찮다. 구현 전에 설계의 약점을 공격적으로 검토하려면 종합한 스케치에 **interrogate** 스킬을 돌린다.

사용자가 구조에 반대하면(확인 지점에서든 나중에든) 1단계 증거로 다룬다. 코드를 더 쓰기 전에 다시 사전 조사하고 2단계를 다시 돌린다.

## 4. 스케치에 맞춰 구현

`not implemented` 본문을 코드로, 의사 코드를 로직으로 바꾼다. 종합한 스케치가 계약이다. 스케치에서 벗어나야 하는 일은 조용히 넘길 마찰이 아니라 드러내 알려야 할 신호다. 스케치가 예상하지 못한 매개변수가 함수에 필요하면, 스케치가 틀렸는지, 요구 사항을 놓쳤는지, 구현이 범위를 넘었는지 따져 본다.

## 5. 아키텍처가 틀렸으면 폐기

구현하면서 스케치로 감당하지 못하는 마찰이 계속 나오면 스케치를 버린다. **principle-redesign-from-first-principles**와 **principle-fix-root-causes** 원칙 스킬에 따라 틀린 설계에 수정을 덧대지 않는다.

신호는 하나하나의 사례가 아니라 *패턴*이다. 징후:

- 서로 관련 없는 코드에 같은 형태의 우회 코드가 거듭 나온다.
- 서로 관련 없는 여러 엣지 케이스가 모두 특별 분기를 필요로 한다.
- 타입이 컴파일되려면 탈출구(`any`, 캐스트, 실제로는 늘 채워지는 선택 필드)가 필요하다.
- 스케치는 상태를 공유하지 않는다고 했는데 자꾸 "락이 필요하다"는 생각이 든다.
- 호출부가 추상화를 쓰려면 그 내부 규칙을 알아야 한다.
- 구현 곳곳에서 4단계의 스케치 이탈이 서로 독립적으로, 같은 형태로 둘 이상 나온다.

판단해서 쓴다. 엣지 케이스 몇 개로 아키텍처가 틀렸다고 단정하지 않는다. 어떤 문제는 원래 복잡하다. 데이터의 복잡함은 설계의 복잡함이 아니다.

폐기할 때:

1. 지금까지 만든 것에 **how** 스킬을 다시 돌린다.
2. **principle-redesign-from-first-principles**에 따라 새 제약이 처음부터의 가정이었던 것처럼 다시 설계한다.
3. **principle-subtract-before-you-add** 원칙 스킬에 따라 더하기 전에 뺀다. 새 스케치는 커지기 전에 먼저 옛 스케치보다 작아야 한다.
4. 2단계로 돌아가 arena를 다시 돌린다.

## 답변

호출부의 사용 예를 먼저 쓰고 타입 스케치를 거기서 도출한다. 작은 변경이면 필요한 타입과 시그니처를, 큰 작업이면 모듈 구성도와 타입 정의를 낸다. 새 파일을 반드시 만들지는 않는다. 필요한 설계 문서는 `references/rationale-template.md` 형식으로 사용 예와 종합 결정을 담되, 프로젝트의 문서 위치와 **repo-docs** 스킬의 공개 승인 규칙을 따른다. 러너 후보와 심사 결과는 `.local/runs/architect-<이름>/`에 둔다. PR을 열 때는 종합 결정과 버린 대안을 본문에 요약한다.
