# Repo Docs Design

- 저장소 안에 같은 역할의 규칙이 있으면 그것 우선. 없으면 이 스킬이 다른 규칙보다 우선
- 기반: repo-docs 먼저 적용. 이 스킬 범위: 새 기능을 넣는 자리, 설계 문서 다섯 종류(`docs/README.md`, 요구사항, 용어, 아키텍처, 구성 요소 설계)의 템플릿, 코드로 옮기는 규칙
- 필요할 때만 읽기: 인터페이스 문서(프로토콜, 명령, 화면, 데이터, 설정, 오류) → repo-docs-spec; 맥락, 구성 요소, 순서, 상태 그림을 만들거나 바꿀 때 → repo-docs-figures

## 새 기능을 넣는 자리

새 기능: 새 파일 대신 아래 표의 자리에 추가. 파일 목록과 만드는 조건: repo-docs 문서 목록 표

| 새로 정할 것 | 넣는 자리 |
|---|---|
| 기능과 요구사항 | `requirements.md` 기능 표, 기능 요구사항 표의 행 |
| 새 용어 | `glossary.md` 표의 행 |
| 구성 요소 사이 흐름 | `architecture.md` 실행 흐름의 `###` |
| 구성 요소 안 동작 | `components/{식별자}.md` 동작의 `###` |
| 메시지, 명령, 키, 테이블, 설정 키, 오류 코드 | repo-docs-spec 문서의 행이나 `###` |
| 선택지 중 하나를 고른 이유 | `decisions/{날짜}-{주제}.md` (repo-docs-decision) |
| 측정이 필요한 값 | `experiments/{실험}/` |
| 구조와 흐름 그림 | `assets/{이름}.d2` (repo-docs-figures) |

## 공통 규칙

- 설계 문서: 지켜야 할 동작을 현재형으로. 구현 여부, 진행 상황, 날짜, 담당자 금지
- 현재 설계만. 바뀐 이력, 버린 선택지, 옛 설계 금지. 고른 이유가 길면 결정 기록에 쓰고 링크
- 정해지지 않은 것: 문서 대신 `design` 이슈로 생성
- 같은 사실은 한 파일에만. 다른 파일은 링크
- 한 파일 300줄 이내. 넘으면 구성 요소 분할 여부를 `design` 이슈로 생성
- `> [!WARNING]` 알림: 어기면 데이터나 동작을 잃는 규칙에만(repo-docs 서식)

## docs/README.md

```text
# 문서

{이름}의 설계 문서다. 표 순서대로 읽는다.

| 문서 | 내용 |
|---|---|
| [{제목}]({파일}) | {내용} |
```

- 행: repo-docs 문서 목록 표의 `docs/requirements.md`부터 `docs/experiments/README.md`까지 행 중 실제로 있는 파일만, 표 순서. `제목`, `내용`: 그 표 글자 그대로. `{파일}`: 위치 칸 첫 경로에서 `docs/` 뒤 부분
- 구성 요소 설계 행: 아키텍처 표 순서

## requirements.md

```text
# 요구사항

{소개 문단}

## 목표

- {목표}

## 비목표

- {하지 않는 것}

## 사용자

| 사용자 | 쓰는 상황 |
|---|---|
| {사용자} | {상황} |

## 기능

| 기능 | 하는 일 |
|---|---|
| {기능} | {하는 일} |

## 기능 요구사항

| 기능 | 요구사항 | 확인 방법 |
|---|---|---|
| {기능} | {요구사항} | {테스트나 실험} |

## 품질 요구사항

| 항목 | 요구사항 | 확인 방법 |
|---|---|---|
| {항목} | {요구사항} | {테스트나 실험} |

## 제약

- {제약}
```

| 자리 | 규칙 |
|---|---|
| 소개 문단 | 한 문단, 문장 셋. 1: `{누가} {무엇을 할 때} {무엇이 어렵다}.` 2: `{이름}은/는 {무엇을} {어떻게} {한다}.` 3: `{비교 대상}과/와 달리 {차이}.` 비교 대상이 없으면 3 삭제. README 소개 문단의 원본 |
| 목표 | 3~5개. `{대상} {결과}` 명사구: `도구와 무관한 작업 기록 보존` |
| 비목표 | 1~5개. 사용자가 기대할 만하지만 하지 않는 것 |
| 사용자 | 1~4행. 사용자는 역할 명사: `개인 개발자` |
| 기능 | 3~10행. `기능`은 15자 이내 명사구, `하는 일`은 50자 이내 명사구. README 기능과 로드맵의 원본 |
| 기능 요구사항 | 문장 열: `요구사항`. 한 행에 검증할 수 있는 조건 하나. `기능` 칸: 기능 표의 이름. 행 묶음 순서: 기능 표 순서 |
| 품질 요구사항 | 문장 열: `요구사항`. `항목`은 `성능`, `신뢰성`, `보안`, `호환성`, `사용성`, `이식성` 중 하나, 이 순서. 테스트로 판정할 수 있는 조건. 정한 수치가 있으면 수치 필수 |
| 확인 방법 | 테스트: `{파일 경로}`의 `{테스트 이름}`, 실험: 실험 문서 링크. 테스트가 아직 없어도 만들 테스트의 경로와 이름 기입 |
| 제약 | 운영체제, 언어 버전, 외부 도구 순서. 라이선스 제외 |

## glossary.md

```text
# 용어

이 문서의 용어를 코드, 화면, 문서에서 같은 뜻으로 쓴다.

| 용어 | 뜻 | 코드 이름 | 쓰지 않는 말 |
|---|---|---|---|
| {용어} | {뜻} | `{식별자}` | {다른 말} |
```

- 가나다순, 영문은 한글 뒤 알파벳순
- 문장 열: `뜻`. 무엇인지만, 동작 제외
- `코드 이름`, `쓰지 않는 말`: 없으면 `없음`. 여럿이면 `, `로 연결

````text
# 아키텍처

{이름}은/는 {구성 요소 수}개 구성 요소로 이루어진다. {구성 요소 사이 연결 방식 한 문장}

## 맥락

![{결론 문장}](assets/context.svg)

| 외부 요소 | 종류 | 주고받는 것 |
|---|---|---|
| {외부 요소} | {종류} | {주고받는 것} |

## 구성 요소

![{결론 문장}](assets/architecture.svg)

| 구성 요소 | 식별자 | 하는 일 | 기술 | 위치 |
|---|---|---|---|---|
| {구성 요소} | `{id}` | {하는 일} | {기술} | `{경로}` |

## 실행 흐름

### {흐름 이름}

1. {구성 요소}: {동작}

## 배치

| 프로세스 | 시작 주체 | 수명 |
|---|---|---|
| {프로세스} | {시작 주체} | {수명} |

| 경로 | 내용 | 쓰는 구성 요소 |
|---|---|---|
| `{경로}` | {내용} | {구성 요소} |

## 공통 규칙

### {영역}

{규칙 문장. 이유 문장}

## 기술 선택

| 영역 | 선택 | 고른 이유 |
|---|---|---|
| {영역} | {기술} | {이유} |
````

| 자리 | 규칙 |
|---|---|
| 맥락 그림 | 원본 `assets/context.d2`, 맥락 그림 템플릿(repo-docs-figures D2). 외부 요소 표의 행마다 도형 하나 |
| 구성 요소 그림 | 원본 `assets/architecture.d2`, 구성 요소 그림 템플릿(repo-docs-figures D2). 구성 요소 표의 행마다 도형 하나, 같은 이름 |
| 그림 대체 글 | 그림이 보여 주는 결론 한 문장: `사용자 요청은 서버에 저장된 뒤 작업자로 간다` |
| 외부 요소 종류 | `외부 프로그램`, `외부 서비스`, `운영체제`, `파일` 중 하나 |
| 구성 요소 | 실행 단위나 저장소 단위만. 모듈: 구성 요소 설계 문서에 |
| 식별자 | 영어 소문자 kebab-case. 구성 요소 설계 파일 이름과 동일 |
| 실행 흐름 절 | 3~7개. 제목은 명사구: `서버 시작`, `작업자 비정상 종료`. 단계는 `{구성 요소}: {동작}` 명사구, 10단계 이내 |
| 배치 | 채울 사실이 있는 표만. 두 표 모두 없으면 절 삭제. 경로 표: 구성 요소 표 `위치`에 없는 경로만 |
| 공통 규칙 | 여러 구성 요소가 함께 따르는 방식만. 기능 요구사항에 있는 문장 반복 금지 |
| 공통 규칙 영역 | `오류 처리`, `로그`, `동시성`, `저장`, `보안`, `버전 호환` 중 해당하는 것, 이 순서. 영역마다 한 문단, 네 문장 이내 |
| 기술 선택 | 문장 열: `고른 이유`. 한 문장. 결정 기록이 있으면 마침표 바로 앞에 `([결정 기록](decisions/{파일}))`: `표준 라이브러리만으로 구현한다([결정 기록](decisions/x.md)).` |

## components/{식별자}.md

```text
# {구성 요소} 설계

{구성 요소}은/는 {하는 일}. 아키텍처는 [아키텍처](../architecture.md)에 있다.

## 모듈

| 모듈 | 하는 일 | 위치 |
|---|---|---|
| {모듈} | {하는 일} | `{경로}` |

## 동작

### {동작 이름}

![{결론 문장}](../assets/{식별자}-{동작 식별자}.svg)

1. {모듈}: {동작}

## 규칙

| 규칙 | 이유 |
|---|---|
| {규칙} | {이유} |

## 상태

![{결론 문장}](../assets/{식별자}-state.svg)

| 상태 | 뜻 | 다음 상태 |
|---|---|---|
| `{상태}` | {뜻} | `{상태}`, `{상태}` |

## 인터페이스

| 항목 | 시그니처 | 보장 |
|---|---|---|
| {항목} | `{시그니처}` | {보장} |

## 오류 처리

| 상황 | 동작 |
|---|---|
| {상황} | {동작} |

## 검증

| 대상 | 확인 방법 |
|---|---|
| {동작이나 규칙} | {테스트나 실험} |
```

| 절 | 조건과 규칙 |
|---|---|
| 모듈 | 항상. 행 순서는 의존 방향(아래층 먼저) |
| 동작 | 항상. `###` 하나가 동작 하나. 단계는 `{모듈}: {동작}` 명사구, 10단계 이내. 단계에 조건이 있으면 `{모듈}: {조건}이면 {동작}`. 순서 그림은 모듈 셋 이상이 주고받는 동작에만, 원본은 순서 그림 템플릿(repo-docs-figures D2). `{동작 식별자}`: 동작 이름의 영어 kebab-case |
| 규칙 | 지켜야 할 조건이 있을 때. 문장 열: `규칙`, `이유` |
| 상태 | 상태가 셋 이상인 대상이 있을 때. 대상이 둘이면 `###`으로 분리. 상태 그림은 상태가 넷 이상일 때만, 원본은 상태 그림 템플릿(repo-docs-figures D2) |
| 인터페이스 | 공개 계약이 코드에 없을 때만. 계약이 코드에 들어가면 절 삭제, 모듈 표 `위치`로 대체. 문장 열: `보장` |
| 오류 처리 | 항상. 문장 열: `동작` |
| 검증 | 확인 방법이 하나 이상일 때 |

- `components/` 파일 수: 아키텍처 구성 요소 수 이하
- 설정 값은 `configuration.md`, 메시지 형식은 `protocol.md`, 테이블 구조는 `data.md`에. 여기는 링크만
- 코드 위치: 경로와 항목 이름: `src/queue.rs`의 `Queue::accept`. 줄 번호 금지
- `은/는`, `과/와`: 앞말을 읽은 소리의 받침으로 하나만 선택

## 코드로 옮기기

| 내용 | 계약이 코드에 들어가기 전 | 들어간 뒤 |
|---|---|---|
| 목적, 흐름, 규칙과 이유 | 설계 문서 | 설계 문서 |
| 함수와 타입의 입출력, 오류, 불변 조건 | 인터페이스 절 | 코드 문서 주석. 인터페이스 절 삭제 |
| 할 일 | 이슈 | 이슈와 `TODO(#{번호})` |
| 동작 예시와 완료 조건 | 이슈 | 테스트. 검증 절에 위치 |

- 동작, 계약, 설정을 바꾸는 PR: 같은 PR에서 설계 문서 수정(git-pull-request 문서 동반)
