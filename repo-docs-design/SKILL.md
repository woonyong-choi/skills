# Repo Docs Design

- 저장소 안에 같은 역할의 규칙이 있으면 그것 우선. 없으면 이 스킬이 다른 규칙보다 우선
- 기반: repo-docs 먼저 적용. 이 스킬 범위: 새 기능을 넣는 자리, 설계 문서 네 종류(`docs/README.md`, `architecture.md`, `design/{주제}.md`, `glossary.md`)의 절 구성, 코드로 옮기는 규칙
- 필요할 때만 읽기: 코드에 들어간 인터페이스 문서(프로토콜, 명령, 화면, 데이터, 설정, 오류) → repo-docs-spec; 맥락, 구성 요소, 순서, 상태 그림 → repo-docs-figures

## 새 기능을 넣는 자리

| 새로 정할 것 | 넣는 자리 |
|---|---|
| 기능의 목적, 동작, 요구사항 | `design/{주제}.md` |
| 구성 요소와 경계, 깨면 안 되는 조건 | `architecture.md` |
| 프로젝트 고유 용어 | `glossary.md` 표의 행 |
| 코드에 들어간 메시지, 명령, 키, 테이블, 설정 키, 오류 코드 | repo-docs-spec 문서 |
| 선택지 중 하나를 고른 이유 | `decisions/{날짜}-{주제}.md` (repo-docs-decision) |
| 측정이 필요한 값 | `experiments/{실험}/` (repo-docs-experiment), 그 전에는 `미해결 질문` |
| 구조와 흐름 그림 | `assets/{이름}.d2` (repo-docs-figures) |

## 공통 규칙

- 설계 문서: 설계한 동작을 현재형으로. 진행 상황, 날짜, 담당자 금지. 상태는 상태 표 한 칸에만
- 현재 설계만. 바뀐 이력, 옛 설계 금지. 버린 선택지는 `대안` 절 한 줄과 결정 기록 링크
- 정해지지 않은 것: `미해결 질문` 절에 질문과 `design` 이슈 링크. 본문에 확정처럼 쓰기 금지
- 같은 사실은 한 파일에만. 다른 파일은 링크
- 한 파일 300줄 이내. 넘으면 주제 분할
- `> [!WARNING]` 알림: 어기면 데이터나 동작을 잃는 규칙에만(repo-docs 서식)

## docs/README.md

````text
# 문서

Saturn의 설계 문서다. 문서는 한국어로 쓴다. 처음이면 아키텍처부터 읽는다.

| 문서 | 내용 |
|---|---|
| [아키텍처](architecture.md) | 구성 요소, 코드 지도, 불변 조건 |
| [입력 처리](design/input-handling.md) | 입력 접수, 대기, 보류와 재개 |
| [결정 기록](decisions/README.md) | 설계를 정한 이유와 버린 선택지 |
````

- 첫 문단: 문서 묶음 이름, 작업 언어, 읽기 시작점 세 문장
- 행 순서: repo-docs 문서 목록 규칙. `내용`: 그 문서가 답하는 것, 명사구

## architecture.md

- 독자: 반복해서 기여하는 사람. 답할 질문: 코드가 어떻게 나뉘나, 무엇이 어디서 일어나나, 깨면 안 되는 조건은
- 150줄 이내. 자주 바뀌는 세부와 모듈 안 동작은 `design/` 문서 링크
- 머리: `# 아키텍처`와 개요 한 문단(무엇을 하는 시스템인지 한 문장, 구성 요소 수와 연결 방식 한 문장)

| 순서 | 한국어 절 | 영어 절 | 필수 | 내용 |
|---|---|---|---|---|
| 1 | `맥락` | `Context` | 선택 | 외부 요소 그림과 표. 외부 요소가 둘 이상일 때 |
| 2 | `코드 지도` | `Code map` | 필수 | 구성 요소 그림과 표 |
| 3 | `실행 흐름` | `Flows` | 선택 | 구성 요소 사이 흐름 2~5개 |
| 4 | `불변 조건` | `Invariants` | 필수 | 깨면 안 되는 조건과 이유 |
| 5 | `배치` | `Deployment` | 선택 | 프로세스 수명과 파일 위치 |
| 6 | `기술 선택` | `Technology choices` | 선택 | 영역별 기술과 고른 이유 |

````text
## 코드 지도

| 구성 요소 | 하는 일 | 기술 | 위치 |

## 불변 조건

- 엔진만 기록 저장소에 쓴다. 쓰기 충돌을 막기 위해서다.
````

| 자리 | 규칙 |
|---|---|
| 맥락 표 | `외부 요소`, `종류`, `주고받는 것`. 종류는 `외부 프로그램`, `외부 서비스`, `운영체제`, `파일` 중 하나 |
| 코드 지도 표 | `구성 요소`는 코드 식별자 인라인 코드. 실행 단위나 저장소 단위만. 모듈은 `design/` 문서에 |
| 코드 지도 그림 | 원본 `assets/architecture.d2`(repo-docs-figures D2). 표의 행마다 도형 하나, 같은 이름 |
| 실행 흐름 | `###` 하나가 흐름 하나. 단계는 문장, 7단계 이내. 주어는 구성 요소 이름 |
| 불변 조건 | 문장 목록. 항목마다 조건과 이유 한 문장씩. `없다`, `하지 않는다`처럼 부재로 정한 조건 포함 |
| 배치 | 프로세스 표(`프로세스`, `시작 주체`, `수명`)와 경로 표(`경로`, `내용`, `쓰는 구성 요소`). 채울 사실이 있는 표만 |
| 기술 선택 | `영역`, `선택`, `고른 이유`. 이유는 한 문장, 결정 기록이 있으면 링크 |
| 코드 링크 | 경로와 식별자 이름만. 줄 번호와 코드 줄 링크 금지 |

## design/{주제}.md

- 독자: 기여자와 검토자. 답할 질문: 왜 필요한가, 어떻게 동작하나, 무엇이 아직 미정인가
- 파일 이름: 기능 주제의 영어 소문자 kebab-case 1~3단어 `input-handling.md`
- 주제: 사용자가 알아볼 수 있는 기능 단위. 코드 모듈 단위 금지
- 머리: `# {주제 이름}`과 상태 표

```text
| 항목 | 값 |
|---|---|
| 상태 | 제안 |
| 관련 결정 | [엔진만 판단기를 부른다](../decisions/2026-09-29-engine-as-judge-proxy.md) |
```

| 상태 | 뜻 |
|---|---|
| 제안 | 검토 중. 핵심 동작에 미해결 질문 존재 |
| 결정 | 핵심 동작을 정함. 코드 없음 |
| 구현 | `main`에 코드와 통과한 테스트 존재 |

| 순서 | 한국어 절 | 영어 절 | 필수 | 내용 |
|---|---|---|---|---|
| 1 | `요약` | `Summary` | 필수 | 한 문단. 무엇을 하는 기능인지 |
| 2 | `동기` | `Motivation` | 필수 | 누가 어떤 상황에서 무엇이 어려운지, 이 기능이 없으면 생기는 일 |
| 3 | `예시` | `Examples` | 필수 | 사용 장면 1~3개. 이미 있는 기능처럼 현재형으로 |
| 4 | `상세 설계` | `Design` | 필수 | 규칙, 상태, 흐름, 오류 처리, 요구사항 |
| 5 | `단점` | `Drawbacks` | 선택 | 이 설계가 치르는 비용 |
| 6 | `대안` | `Alternatives` | 선택 | 버린 선택지 한 줄씩과 결정 기록 링크 |
| 7 | `미해결 질문` | `Unresolved questions` | 미정이 있으면 필수 | 질문과 이슈 링크 |

| 자리 | 규칙 |
|---|---|
| 예시 | `###` 하나가 장면 하나. 번호 목록의 단계마다 한 문장. 사용자가 보는 것과 시스템이 하는 일 |
| 상세 설계 | `###`으로 나누기. 단계 목록은 문장. 수치의 근거 링크와 미해결 질문 기준(repo-docs 문장) |
| 상세 설계 상태 표 | 상태가 셋 이상인 대상. `상태`, `뜻`, `다음 상태` |
| 요구사항 표 | 상세 설계 마지막 `### 요구사항`. `요구사항`(문장), `검증 계획`(테스트나 실험이 확인할 내용). 테스트가 생기면 `검증 계획`을 `{파일 경로}`의 `{테스트 이름}`으로 교체 |
| 미해결 질문 | `- {질문} ([#{번호}]({이슈 URL}))`. 질문은 선택지가 보이게 |
| 기호 | 처음 나오는 문장에서 정의(repo-docs 문장) |

- 설정 값, 메시지 형식, 테이블 구조: 코드에 들어간 뒤 spec 문서로 옮기고 여기는 링크만

## glossary.md

````text
# 용어

이 프로젝트에서만 쓰는 말이다. 업계에서 널리 쓰는 말은 넣지 않는다.

| 용어 | 뜻 | 원어와 코드 이름 |
|---|---|---|
| 트리 유휴 | 에이전트와 모든 하위 에이전트가 끝난 상태다. | `tree idle` |
````

- 가나다순, 영문은 한글 뒤 알파벳순
- 문장 열: `뜻`. 무엇인지만, 동작 제외
- `원어와 코드 이름`: 없으면 `없음`. 여럿이면 `, `로 연결
- 헷갈리기 쉬운 다른 말이 있으면 `뜻` 칸 끝에 한 문장: `공급자의 세션과 다르다.`

## 코드로 옮기기

| 내용 | 계약이 코드에 들어가기 전 | 들어간 뒤 |
|---|---|---|
| 목적, 흐름, 규칙과 이유 | 설계 문서 | 설계 문서 |
| 함수와 타입의 입출력, 오류, 불변 조건 | 설계 문서 상세 설계 | 코드 문서 주석. 설계 문서는 요약과 링크 |
| 메시지, 명령, 설정, 테이블, 오류 코드 | 설계 문서 상세 설계 | spec 문서 |
| 할 일 | 이슈 | 이슈와 `TODO(#{번호})` |
| 동작 예시와 완료 조건 | 설계 문서 예시, 이슈 | 테스트. 요구사항 표 `검증 계획` 교체 |

- 동작, 계약, 설정을 바꾸는 PR: 같은 PR에서 설계 문서 수정(git-pull-request 문서 동반)
- 설계 문서 상태: 핵심 동작의 코드와 테스트가 `main`에 들어가면 `구현`
