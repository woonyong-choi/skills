# 검토

PR을 규칙과 설계 두 축으로 독립 검토하고, 지적마다 등급을 매겨 반영 여부를 판정한다.

## 방법

- **interrogate** 스킬로 다른 회사 모델 둘 이상이 독립적으로 검토하고, 지적마다 아래 P1~P5 등급을 매긴다.
- 검토자는 작성자의 결론을 전제로 두지 않고 diff, 계약, 시험 증거를 직접 대조한다.
- 규칙과 설계 두 축을 따로 검토한다.

| 축 | 기준 | 보는 것 |
|---|---|---|
| 규칙 | 저장소 규칙, **code-style** 스킬과 언어별 스킬 | 이름, 구조, 오류 처리, 테스트, 금지 항목 |
| 설계 | 이슈 완료 조건, 설계 문서 | 빠진 조건, 범위 밖 변경, 설계와 다른 동작, 문서 동반, 가정, 확인 절의 증거 |

## 등급

| 등급 | 처리 | 예 |
|---|---|---|
| P1 | 반드시 반영한다 | 데이터 손실, 보안, 잘못된 결과 |
| P2 | 반영하거나 근거를 단 답글로 반박한다 | 요구나 테스트 누락 |
| P3 | 반영하거나 후속 이슈 링크를 단다 | 유지보수 비용 증가 |
| P4 | 작성자가 판단한다 | 취향 |
| P5 | 작성자가 판단한다 | 사소한 의견 |

## 댓글

- 줄 단위 댓글은 맨 앞에 `[P1]`~`[P5]`를 쓰고 근거(규칙이나 조건)를 붙인다.
- 리뷰 요약 첫 줄은 `P1 0 · P2 1 · P3 2 · P4 0 · P5 1` 형식이고, 이어서 축별 발견을 쓴다. 발견이 없으면 `발견 없음`이라고 쓴다.

## 반영 확인

- 그 코드를 쓴 작성 에이전트가 아닌 다른 에이전트가 수정 커밋을 보고 판정한다. 해결된 의견에는 `반영 확인: {커밋 7자리}` 답글을 단다.
- 작성자가 스스로 판정하지 않는다.
- 확인은 최대 2번까지 되풀이한다. 합의하지 못하면 결정 기록에 `결정 필요`로 적는다.
