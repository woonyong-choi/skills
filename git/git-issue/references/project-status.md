# 프로젝트 판 상태

이슈와 PR을 판에 올리고, 상태를 옮기고, 닫는 기준의 정본이다.

## 대상과 범위

- Projects v2의 Status 필드를 쓴다.
- 판 상태는 사실 상태(**repo-docs** 스킬)나 설계 상태(**repo-docs-design** 스킬)와 다른 축이다. 판에서 완료됐다는 것만으로 구현됐거나 쓸 수 있다고 판정하지 않는다.
- 대상 판은 `gh api graphql`로 작업 저장소의 `projectsV2`를 조회해 찾고, `--project 번호`를 반복해 고른다. 연결된 프로젝트가 하나면 project_status.py에서 이 옵션을 생략할 수 있다(`colors`는 예외). 프로젝트 이름과 번호를 하드코딩하지 않는다.
- 연결된 프로젝트가 없으면 [새 저장소](#새-저장소) 절차를 바로 실행한다. 권한이 없거나 브라우저가 연결되지 않았으면 미완료와 재개 위치를 기록한다. 이슈만 연결된 상태를 준비 완료로 다루지 않는다. 관련 없는 보드를 고르지 않는다.
- 상태는 아래 상태표의 다섯 역할이다. 저장소 정책이 있으면 그것이 먼저다. 기존 선택지 이름이 다르면 `--status-map '역할=실제 이름'`을 반복해 준다.
- Status 필드나 필요한 선택지가 없으면 알리고 상태 변경을 멈춘다. 처음 설정은 `setup`으로 한다.

## 상태표

열린 이슈는 모두 판에 있고 상태를 하나씩 가진다. 모든 상태에는 나가는 조건과 다음 행동의 주체(AI나 사용자)가 있다. 이유 없이 머무는 이슈와, 체크하지 않은 완료 조건을 둔 채 닫히는 이슈를 만들지 않는다.

| 상태 | 들어가는 조건 | 머무는 동안 | 나가는 조건 |
|---|---|---|---|
| 대기 | 이슈를 만들었다. 독립된 결과 하나이고, 같은 내용의 열린 이슈가 없고, 틀의 필수 절과 완료 조건이 있다 | 없음 | 착수 조건을 채우면 진행으로 간다 |
| 진행 | 착수 조건을 채웠다. 완료 조건이 있고, 막는 열린 이슈가 없고, 남은 결정이 없고, 담당자가 있고, 과업을 연결(bind)했다 | 브랜치 하나를 쓰고, 결정 기록에 다음 할 일(phase `다음`)을 둔다 | PR을 내면 검토로 간다. 막히거나 결정을 기다리면 보류로 간다 |
| 검토 | 이 이슈를 닫는 PR(`Closes:`)을 냈다 | 리뷰의 P1과 P2를 처리한다 | PR이 머지되고 닫는 기준을 채우면 완료로 간다. PR이 머지 없이 닫히면 진행이나 보류로 가고 이유를 반드시 적는다 |
| 보류 | 사용자 결정 대기, 막는 이슈 있음, 사용자 지시로 연기 가운데 하나다 | 막는 이슈는 GitHub 막힘 관계로 잇는다 | 재개 조건을 채우면 대기로 간다. 보류가 30일이 되면 사용자에게 계속할지 취소할지 묻는다 |
| 완료 | 닫는 기준을 채우고 닫았다 | 없음 | 다시 열리면 진행으로 가고, 잘못 판정한 근거와 남은 조건을 적는다 |

- `Refs:`로만 이어진 PR은 이슈 상태를 바꾸지 않는다.
- 재개하면 대기로 옮긴다. 과업을 연결한 세션만 진행으로 옮긴다.
- AI가 만든 이슈를 같은 세션에서 착수하지 않으면 착수하지 않은 이유를 이슈에 한 줄 적는다.
- 완료 항목은 Status 값과 항목을 그대로 두고, 지정 보드에서 필터로 숨긴다. 완료 이력을 남긴다.

## 닫는 기준

- 완료로 닫으려면 완료 조건이 모두 `[x]`이고 줄마다 증거(시험 이름, 명령 결과, PR, 문서 링크)가 있으며 닫는 PR이 머지돼야 한다.
- 체크하지 못한 조건이 있으면 완료로 닫지 않는다. 같은 이슈에서 마저 하거나 사용자 승인을 받아 범위를 줄인다. 범위를 줄일 때는 그 줄을 지우지 않고 `~~취소선~~`과 `후속 #번호`나 `제외: 이유`를 붙이고, 범위 변경 댓글([git-issue 범위 변경](../SKILL.md#범위-변경))을 단다.
- 안 함(not planned)으로 닫는 경우는 사용자 취소, 같은 완료 조건의 중복(`#번호와 중복`), 불필요(이유 한 줄)다.
- bug를 재현하지 못했으면 바로 닫지 않는다. 재현 시도를 기록한 뒤 보류(사유: 재현 정보 대기)로 옮기고 보류 30일 규칙을 따른다.

## 명령

상태가 바뀔 때마다 반드시 `set`을 실행한다. 판에 없는 항목은 올린 뒤 바꾸고, 상태가 같으면 쓰지 않는다.

```sh
python3 <이 스킬 폴더>/scripts/project_status.py set <이슈 또는 PR 번호> '진행'
python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name setup --view <뷰 ID>
python3 <이 스킬 폴더>/scripts/project_status.py check [--number 번호] [--fix]
```

- Python 3.9 이상, 표준 라이브러리, 인증된 `gh`와 저장소와 프로젝트 조회 권한이 필요하다. 바꾸는 명령은 프로젝트 쓰기 권한도 필요하다.
- 저장소의 기본값은 현재 디렉터리다. `--repo owner/name`은 하위 명령 앞뒤 어디에나 둘 수 있다. `--project`와 `--status-map`은 하위 명령 앞에 둔다. 매핑 값에는 중복, 빈 값, 쉼표, 줄바꿈을 쓰지 않는다. `set`에는 역할 이름을 준다.
- `set <번호> <역할>`은 이슈나 PR을 조회한 뒤 연결된 프로젝트마다 올리고 상태를 정한다. 열린 항목을 완료로, 닫힌 항목을 완료 아닌 상태로 정하는 것은 거부한다. 없는 번호면 2로 끝난다. 공백이 든 이름은 따옴표로 감싼다.
- `setup --view ID`는 지정한 뷰만 BOARD_LAYOUT으로 바꾸고 완료 제외 필터와 보류 표시 필터를 적용한다. 다른 필터는 그대로 둔다. 옛 선택지는 `작업 중`을 `진행`으로, `검증 중`을 `검토`로, `선택 필요`를 `보류`로 옮긴다. 선택 필요에 있던 결정 대기와 재개 조건은 보류 사유 필드에 남긴다. 항목 ID와 옮긴 결과를 다시 조회한 뒤 옛 선택지를 지운다. 모르는 상태가 있으면 멈추고 마음대로 지우지 않는다. Status 그룹과 숨긴 열은 반드시 실제 화면에서 확인한다.
- `check`는 판에 없거나 상태가 빈 열린 이슈, 판에 있는데 완료가 아닌 닫힌 이슈, 완료인데 열린 이슈를 출력한다. 보류인데 `보류 사유` 필드에 재개 조건이 없는 이슈와 보류 30일 이상인 이슈는 주의로 출력하고 바꾸지 않는다. 다른 저장소 이슈, 초안, PR은 보지 않는다. `--number`를 주면 그 항목만, 생략하면 저장소 전체를 본다.
- `check --fix`는 판에 없거나 상태가 비었거나 잘못 완료된 열린 이슈를 `대기`로, 판에 있는 닫힌 이슈를 `완료`로 바꾼다. 진행, 검토, 보류와 판에 없는 닫힌 이슈는 그대로 둔다. 빈 상태를 진행으로 짐작하지 않는다. 주의 항목은 바꾸지 않는다.
- 결과는 표준 출력에 낸다. 종료 코드는 성공이나 수정 완료면 0, 읽기 검사의 불일치나 주의가 있으면 1, 프로젝트나 필드나 선택지가 없거나 조회와 변경이 실패하면 2다.
- 여러 프로젝트를 바꾸다 API가 실패하면 앞서 성공한 변경은 그대로 둔다. 원인을 고친 뒤 같은 명령을 다시 실행한다.
- 지정한 실제 프로젝트에서 명령 전후로 항목, 상태, 뷰를 다시 조회해 검증한다. 모의 응답으로 실제 변경이 성공했다고 판정하지 않는다.

## 시작부터 완료까지

1. 시작할 때 결과마다 이슈를 나눌지 판정하고, 연결된 보드를 확인하고, 이슈를 올리고, bind한다. 기존 번호나 이름을 짐작하지 않는다.
2. 단계가 바뀌면 `set <번호> 진행|검토|보류`를 실행한다. 보류하면 이유와 재개 조건을 이슈의 `보류 사유` 필드와 결정 기록에 적는다. 결과를 냈다고 전체가 끝났다고 보지 않는다.
3. 끝낼 때 조건마다 근거를 확인하고, 이슈를 닫고, `check --number 번호 --fix`를 실행한다. 닫기에 실패하면 완료로 옮기지 않는다.

- 새 보드의 자동화는 그 저장소의 열린 항목을 올리고, 올리면 대기로, 닫히거나 PR이 머지되면 완료로 옮긴다. 상태 이동만으로 이슈를 닫는 Auto-close는 쓰지 않는다. 자동화는 보드마다 설정하며 플러그인을 설치해도 퍼지지 않는다. 설정할 수 없으면 사건마다 set과 check로 처리하고 자동화가 설정되지 않았다고 밝힌다.
- 결과의 독립성, 검토 가능성, 완료 근거는 실행자가 판단한다. 스크립트는 등록과 상태의 기계적 불일치만 검사한다. 의미 판정에 오류가 없다거나 사람 없이 완료된다고 보장하지 않는다.

## 새 저장소

연결된 보드가 없거나 자동화를 처음 설정하거나 복구해야 하면 [project-bootstrap.md](project-bootstrap.md)를 반드시 읽는다. 일반 상태 전환에는 다시 조회할 필요가 없다.

## 상태 색상

- 대기는 `GRAY`, 진행은 `BLUE`, 검토는 `GREEN`, 보류는 `RED`이고 완료는 기존 색을 그대로 둔다. 옛 이름 작업 중, 검증 중, 선택 필요는 각각 진행, 검토, 보류의 색을 쓴다.
- 새로 만들거나 다시 설정할 때도 같은 색을 쓴다. 색만으로 상태의 뜻을 전하지 않는다.
- 기존 보드의 색만 고칠 때는 다음 명령을 쓴다. 조회한 Status 필드에만 적용하고, 선택지의 ID, 이름, 설명, 순서를 그대로 둔다. 항목, 뷰, 자동화를 바꾸거나 새 상태를 만들지 않는다. 다시 조회해서 맞지 않으면 실패하고, 색이 같으면 쓰지 않는다.

```sh
python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name --project 번호 colors
```
