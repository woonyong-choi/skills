# 프로젝트 판 상태

- 이슈·PR 등록·상태 이동·닫는 기준의 정본: 이 문서. Projects v2 Status 사용. 사실 상태(repo-docs)·설계 상태(repo-docs-design)는 별도 축, 판의 완료만으로 구현·사용 가능 판정 금지
- 대상: `gh api graphql`로 작업 저장소의 `projectsV2` 조회 후 `--project 번호` 반복으로 선택. project_status.py는 연결 프로젝트가 하나면 생략 가능(`colors` 제외), continuity.py bind는 항상 필수. 프로젝트 이름·번호 하드코딩 금지
- 연결 프로젝트 없음: [새 저장소](#새-저장소) 절차 자동 실행. 권한·브라우저 미연결이면 미완료와 재개 위치 기록, 이슈 단독 연결을 준비 완료로 처리 금지. 관련 없는 보드 선택 금지
- 상태: 상태표의 다섯 역할. 저장소 정책 우선. 기존 선택지 이름이 다르면 `--status-map '역할=실제 이름'` 반복. Status 필드·필요한 선택지 없음: 알림 후 상태 변경 중단, 초기 설정은 `setup`

## 상태표

원칙: 열린 이슈는 모두 판에 있고 상태 하나. 모든 상태에 나가는 조건과 다음 행동의 주체(AI 또는 사용자). 이유 없이 머무는 이슈와 체크 안 된 채 닫히는 완료 조건 금지

상태 → 들어가는 조건 → 머무는 동안 → 나가는 조건:

- 대기 → 이슈 생성. 독립된 결과 하나, 같은 내용의 열린 이슈 없음, 틀의 필수 절과 완료 조건 → 없음 → 착수 조건 충족 시 진행
- 진행 → 착수 조건: 완료 조건 있음, 막는 열린 이슈 없음, 남은 결정 없음, 담당자 지정, 작업 기록 연결(bind) → 브랜치 하나, 작업 기록 next에 다음 행동 → PR 제출 시 검토. 막힘·결정 대기 시 보류
- 검토 → 이 이슈를 닫는 PR(`Closes:`) 제출 → 리뷰 P1·P2 처리 → PR 머지와 닫는 기준 충족 시 완료. PR이 머지 없이 닫히면 진행 또는 보류(이유 필수)
- 보류 → 사유 셋 중 하나: 사용자 결정 대기, 막는 이슈 있음, 사용자 지시로 연기. 사유와 재개 조건을 이슈와 작업 기록에 기록 → 막는 이슈는 GitHub 막힘 관계로 연결 → 재개 조건 충족 시 대기. 보류 30일 시 사용자에게 계속·취소 확인
- 완료 → 닫는 기준 충족 후 닫음 → 없음 → 다시 열리면 진행, 오판 근거와 남은 조건 기록

- `Refs:`로만 연결된 PR은 이슈 상태 유지
- 재개는 대기로. 작업 기록을 연결한 세션만 진행으로 이동
- AI가 만든 이슈를 같은 세션에서 착수하지 않으면 착수하지 않은 이유를 이슈에 한 줄
- 완료 항목: Status 값과 항목 유지, 지정 보드에서는 필터로 숨김 처리. 완료 이력 보존

## 닫는 기준

- 완료: 완료 조건 전부 `[x]`와 줄마다 증거(시험 이름·명령 결과·PR·문서 링크), 닫는 PR 머지
- 체크 못 한 조건: 완료로 닫기 금지. 같은 이슈에서 마저 하거나 사용자 승인으로 범위 축소: 그 줄을 지우지 않고 `~~취소선~~`과 `후속 #번호` 또는 `제외: 이유`, 범위 변경 댓글(git-issue 범위 변경)
- 안 함(not planned): 사용자 취소, 같은 완료 조건의 중복(`#번호와 중복`), 불필요(이유 한 줄)
- bug 재현 실패: 바로 닫기 금지. 재현 시도 기록 후 보류(사유: 재현 정보 대기), 보류 30일 규칙

## 명령

- 상태가 바뀔 때마다 아래 `set` 또는 continuity의 `checkpoint --sync --status` 실행 필수. 판에 없는 항목은 등록 후 변경, 같은 상태면 쓰기 생략

```sh
python3 <이 스킬 폴더>/scripts/project_status.py set <이슈 또는 PR 번호> '진행'
python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name setup --view <뷰 ID>
python3 <이 스킬 폴더>/scripts/project_status.py check [--number 번호] [--fix]
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리, 인증된 `gh`와 저장소·프로젝트 조회 권한. 변경 명령은 프로젝트 쓰기 권한 필요
- 저장소: 기본은 현재 디렉터리, `--repo owner/name`은 하위 명령 앞뒤 모두 허용. `--project`·`--status-map`은 하위 명령 앞. 매핑 값은 중복·빈 값·쉼표·줄바꿈 금지, `set`에는 역할 이름 입력
- `set <번호> <역할>`: 이슈 또는 PR 조회 후 연결 프로젝트마다 등록·설정. 열린 항목의 완료, 닫힌 항목의 미완료 지정 거부. 없는 번호 종료 2, 공백 포함 이름은 따옴표 필수
- `setup --view ID`: 지정 뷰만 BOARD_LAYOUT 전환·완료 제외·보류 표시 필터 적용, 다른 필터 보존. 옛 선택지 `작업 중→진행`, `검증 중→검토`, `선택 필요→보류` 이관(선택 필요의 결정 대기·재개 조건은 보류 사유 필드에 보존). 항목 ID·이관 결과 재조회 뒤 옛 선택지 제거. 알 수 없는 상태는 중단, 임의 삭제 금지. Status 그룹·숨긴 열은 실제 화면 확인 필수
- `check`: 열린 이슈 중 판에 없거나 상태가 빈 것, 판에 있는 닫힌 이슈인데 완료가 아닌 것, 열린 이슈인데 완료인 것 출력. 주의(자동 변경 없음): 진행인데 작업 기록 체크포인트의 다음 없음, 보류인데 `보류 사유` 필드에 재개 조건 없음, 보류 30일 이상. 다른 저장소 이슈·초안·PR 제외. `--number`는 해당 항목만, 생략 시 저장소 전체
- `check --fix`: 판에 없거나 빈 상태·잘못된 완료인 열린 이슈는 `대기`, 판에 있는 닫힌 이슈는 `완료`. 진행·검토·보류와 판에 없는 닫힌 이슈는 유지, 빈 상태를 진행으로 추정 금지. 주의 항목은 변경 없음
- 출력: 표준 출력. 종료 코드: 성공·수정 완료 0, 읽기 검사 불일치·주의 1, 프로젝트·필드·선택지 누락 또는 조회·변경 실패 2
- 여러 프로젝트 변경 중 API 실패: 앞선 성공 유지, 원인 해결 후 같은 명령 재실행
- 검증: 지정한 실제 프로젝트에서 명령 전후 항목·상태·뷰 재조회. 모의 응답으로 실제 변경 성공 판정 금지

## 시작부터 완료까지

- 시작: 결과별 이슈 분리 판정 → 연결 보드 확인 → 이슈 등록 → bind. 기존 번호·이름 추정 금지
- 단계 전환: `checkpoint --sync --status 진행|검토|보류`(체크포인트 댓글 게시 시점: continuity.md). 보류 이유·재개 조건은 이슈와 next에 기록. 결과 제출을 전체 완료로 해석 금지
- 완료: 조건별 근거 확인 → 이슈 닫기 → `check --number 번호 --fix`. 닫기 실패 시 완료 이동 금지
- 새 보드 자동화: 해당 저장소의 열린 항목 등록, 등록→대기, 종료·PR 병합→완료. 상태 이동만으로 이슈를 닫는 Auto-close 사용 금지. 보드별 설정이며 플러그인 설치로 미전파. 설정 불가 시 사건별 set/check로 처리하고 자동화 미설정 명시
- 판정 역할: 결과 독립성·검토 가능성·완료 근거는 실행자 판단. 스크립트는 등록·상태의 기계적 불일치만 검사, 의미 판정 무오류·무인 완료 보장 금지

## 새 저장소

연결 보드가 없거나 자동화 초기 설정·복구가 필요하면 [새 저장소 보드 초기화](project-bootstrap.md) 필수 확인. 일반 상태 전환: 재조회 불필요

## 상태 색상

- 대기 `GRAY`, 진행 `BLUE`, 검토 `GREEN`, 보류 `RED`, 완료는 기존 색상 보존. 옛 이름 작업 중·검증 중·선택 필요는 각각 진행·검토·보류 색상
- 신규 생성·재설정에 같은 색상 적용. 색만으로 상태 의미 전달 금지
- 기존 보드 색상만 교정: `python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name --project 번호 colors`. 조회한 Status 필드에만 적용, 선택지 ID·이름·설명·순서 보존, 항목·뷰·자동화 변경과 새 상태 생성 없음. 재조회 불일치 시 실패, 같은 색이면 쓰기 생략
