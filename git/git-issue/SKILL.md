# Git Issue

- 저장소 안에 같은 역할의 규칙이 있으면 그것 우선. 없으면 이 스킬이 다른 규칙보다 우선
- 범위: 이슈 종류, 라벨, 제목, 본문 틀, 묶음, 상태, 닫기. 브랜치와 PR 흐름(git-branch), PR 본문(git-pull-request), 커밋 형식(git-commit) 제외
- 필요할 때만 읽기: 제목·본문·댓글 작성·검토 → repo-docs; build, docs 제목의 끝말이나 영역 라벨의 scope 단어 → git-commit

## 종류

한 이슈에 종류 하나. 라벨: 종류 라벨 하나, 영역 라벨 하나, 우선순위 라벨 하나.

| 종류 라벨 | 쓰는 때 | 제목 | 예 |
|---|---|---|---|
| `design` | 정해야 할 질문 | `~할지`, `~을 무엇으로 할지` | `연결이 끊긴 요청을 다시 보낼지` |
| `build` | 만들 것 확정 | 대상 + 끝말 (git-commit 설명) | `토큰 만료 시 자동 재발급 추가` |
| `bug` | 설계·기대와 다른 동작 | `~할 때 ~하는 문제` | `재연결 뒤 대기 요청이 두 번 전송되는 문제` |
| `experiment` | 측정·실측 필요 | 대상 + `측정` | `한국어 입력의 분류 오류율 측정` |
| `docs` | 문서만 수정 | 대상 + 끝말 | `설치 방법 갱신` |

- 영역 라벨: `area:{scope}`. scope는 커밋 scope 단어 (`area:core`, `area:tui`, `area:repo`)
- 제목: 한글, 50자 이내, 마침표·물음표 없음. 라벨 이름, 번호 금지

## 본문

- 종류별 틀. 섹션 이름, 순서 그대로. 내용 없으면 빼는 절: `원인`, `범위 밖`, `관련`만
- 틀 파일: `.github/ISSUE_TEMPLATE/{종류 라벨}.md`. 파일 머리 `---` 사이에 GitHub 틀 머리말 `name: {종류 라벨}`, `about: {쓰는 때}`, `labels: [{종류 라벨}]`
- 제목·본문·댓글: 사람이 쓴 문서처럼 쓰는 공통 규칙 (repo-docs 문체). 본문·댓글은 한국어 문체 절의 자리별 기준
- 저장소 파일 링크: 전체 URL `https://github.com/{소유자}/{저장소}/blob/main/{경로}`. 이유: 이슈에서 상대 경로 열기 불가

design

```text
## 질문

{정할 것, `~할지`로 끝나는 명사절}

## 배경

{왜 지금 정해야 하는지 한두 문장}. 관련 설계: [{문서 제목}]({전체 URL})

## 선택지

| 선택지 | 얻는 것 | 잃는 것 |
|---|---|---|
| {선택지} | {얻는 것} | {잃는 것} |

## 정하는 기준

- {기준}

## 관련

- {이슈나 문서 링크}
```

build

```text
## 목표

{끝나면 무엇을 할 수 있는지 한두 문장}

## 따르는 설계

- [{문서 제목}]({전체 URL}#{절})

## 계약

{공개 타입과 함수 시그니처 초안. 계약이 코드에 들어가면 코드 위치로 바꾼다}

## 완료 조건

- [ ] {검증할 수 있는 조건} (확인: `{테스트 이름이나 명령}`)

## 범위 밖

- {하지 않는 것}

## 관련

- {이슈나 문서 링크}
```

bug

```text
## 증상

{무엇이 잘못 보이는지 한 문장}

## 재현

1. {단계}

## 기대 동작

{설계 문서 링크와 해당 규칙}

## 실제 동작

{관측한 동작}

## 환경

| 항목 | 값 |
|---|---|
| 운영체제 | {운영체제} |
| 버전 | {버전} |
| 커밋 | `{커밋}` |

## 원인

{찾은 뒤 채운다}
```

experiment

```text
## 확인할 것

{측정할 것 한 문장}

## 실험 문서

- [{실험}]({design.md 전체 URL})

## 관련

- {이슈나 문서 링크}
```

- `docs` 이슈: build 틀에서 `계약` 절 제외
- 관련 절: 막는 이슈, 막히는 이슈, 상위 이슈, 설계 문서 링크
- 완료 조건: 확인 방법까지. `잘 동작함` 같은 조건 금지

## 공개 웹 링크

- 적용: GitHub 이슈·PR 본문·리뷰·댓글의 파일·문서·코드 위치. 저장소 안 문서끼리의 상대 링크는 적용 제외
- 파일·문서 위치: 짧은 경로나 이름을 링크 글자로 쓴 웹 주소. 코드 줄은 `https://github.com/{소유자}/{저장소}/blob/{커밋 SHA}/{경로}#L{시작}-L{끝}`, 계속 바뀌는 문서는 기본 브랜치 주소 사용. 본문 절의 `main`은 기본 브랜치 예시
- 공개되지 않은 로컬·홈·저장소 밖 작업 폴더·미커밋 폴더(`.local` 등): 링크와 경로 표기 금지. 필요하면 `비공개 원자료`처럼 존재만 표시하고 공개 가능한 내용만 본문에 요약
- 비공개 저장소 링크: 같은 저장소의 이슈·PR·리뷰·댓글에서만 허용. 다른 저장소에서 참조 금지
- 이슈·PR·댓글을 올리기 전에 아래 스크립트로 검사, 위반 0개 확인 필수

```sh
python3 <이 스킬 폴더>/scripts/public_links.py --repo <게시 대상 저장소 루트> <본문 파일>
python3 <이 스킬 폴더>/scripts/public_links.py --repo <게시 대상 저장소 루트> --fix <본문 파일>
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리, Git, 인증된 GitHub CLI(`gh`). 원격은 `origin`, 공개 여부와 기본 브랜치는 `gh repo view` 조회
- 입력: UTF-8 파일, 생략 또는 `-`이면 표준 입력. 저장소 상대 경로는 게시 대상 저장소 루트 기준
- 출력: 검사 결과는 표준 출력에 줄 번호 포함. `--fix`는 수정한 본문만 표준 출력, 남은 위반은 표준 오류. 원본 파일 덮어쓰기 금지
- 자동 수정: HEAD에 포함된 저장소 파일만 웹 링크로 변환, 줄 번호가 있으면 현재 HEAD SHA 고정. 비공개 경로·다른 비공개 저장소 주소는 원문 유지와 위반 보고만 수행
- 종료 코드: 통과 또는 모든 위반 수정 0, 남은 위반 1, 입력·Git·공개 여부 조회 실패 2. 수정 결과 재검사 후 게시

## 우선순위

- 열린 이슈: `P0`, `P1`, `P2`, `P3` 중 우선순위 라벨 하나 필수. 이슈 생성 때 추가, 종류·영역 라벨과 함께 사용

| 라벨 | 색 | 기준 |
|---|---|---|
| `P0` | `B60205` | 이미 쓰는 기능의 장애: 데이터 손실, 보안·권한 우회, 같은 작업 두 번 실행, 사용자 몰래 진행, 멈춤·실행 불가 |
| `P1` | `D93F0B` | 프로젝트의 지금 목표(README나 마일스톤에 적힌 핵심 흐름)를 끝까지 동작하지 못하게 하는 문제 |
| `P2` | `FBCA04` | 공개·배포에 꼭 필요함, 또는 자주 쓰는 기능의 품질 저하 |
| `P3` | `C5DEF5` | 개선, 측정, 정리, 나중에 필요할 때 할 일 |

- 기준 둘 이상: 높은 우선순위
- 막는 이슈: 막히는 이슈 중 가장 높은 우선순위. `design`, `experiment` 이슈는 결정이 막는 작업의 우선순위
- 작업 순서: 높은 우선순위 먼저. 같으면 다른 이슈를 막는 것 먼저. 그것도 같으면 오래된 것 먼저
- 다시 매기기: 막힘 관계 변경, 목표 변경, 장애 새 확인
- 마일스톤: 큰 작업 묶음. 우선순위와 별개

## 묶음과 순서

- 큰 작업(설계 문서 둘 이상 변경, 공개 계약 변경, 이슈 셋 이상): 마일스톤 하나(설명: 목표 한 문장, 성공 기준)
- 나눈 작업: GitHub 하위 이슈. 순서 제약: GitHub 막힘 관계, 기능이 없으면 관련 절에 `막힘: #번호`
- 한 이슈 = 한 세션에 끝낼 분량. 크면 하위 이슈로 분할 (git-branch 작업 단위)

## 상태

상태 표시: GitHub로만. 이슈 본문, 문서에 상태 기록 금지.

| 상태 | 표시 |
|---|---|
| 할 일 | 열림, 담당자 없음 |
| 진행 중 | 담당자 지정 + 작업 브랜치 (git-branch) |
| 막힘 | 막힘 관계 |
| 끝 | 닫힌 이슈(completed) |
| 안 함 | 닫힌 이슈(not planned) + 이유 댓글 |

## 프로젝트 판 상태

- 이슈 등록·상태 이동의 정본: 이 절. 위 상태 절의 열림·담당자·막힘·닫기 표시와 함께 Projects v2의 Status 사용
- 대상: `gh api graphql`로 작업 저장소의 `projectsV2`를 조회한 연결 프로젝트 전부. 프로젝트 이름·번호 하드코딩 금지
- 연결 프로젝트 없음: 생성 없이 사용자에게 알림. 프로젝트 생성은 사용자 요청 때만
- 상태 기본값: 아래 여섯 값. 대상 프로젝트의 Status 필드 또는 필요한 선택지 없음: 알림 후 상태 변경 중단, 초기 설정은 `setup` 사용

| 상태 | 언제 |
|---|---|
| 대기 | `이슈가 있고 아직 시작 안 함` |
| 작업 중 | `구현·실험을 시작함(담당자 지정과 같은 때)` |
| 검증 중 | `PR이나 결과가 나와 테스트·CI·실제 확인을 기다림` |
| 선택 필요 | `사용자 결정을 기다림` |
| 보류 | `다른 이슈에 막혔거나 미룸` |
| 완료 | `근거와 함께 닫음` |

- 이슈 생성 직후: 연결 프로젝트에 등록하고 `대기` 설정
- 이슈를 가져와 구현·실험 시작: 담당자 지정과 같은 때 `작업 중` 설정
- PR 생성 또는 결과 제출 후 테스트·CI·실제 확인 대기: `검증 중` 설정
- 사용자 결정 대기: `선택 필요`, 다른 이슈에 막힘 또는 연기: `보류` 설정
- 결정·막힘 해소 후 작업 재개: `작업 중`, 결과의 검증만 남은 경우 `검증 중` 설정
- 근거와 함께 이슈 닫기: `완료` 설정. PR 머지 때 연결 이슈의 실제 닫힘 확인 후 적용, 일부 작업의 `Refs:` 이슈는 현재 단계 유지
- 위 사건마다 아래 `set` 실행 필수. 판에 없는 이슈는 등록 후 상태 변경, 이미 같은 상태면 쓰기 생략
- 완료 항목: Status 값과 항목 유지, 보드 뷰 필터에 `-status:완료` 추가. 열 자체 숨기기는 API 미지원이므로 사람이 완료 열 메뉴의 `Hide from view` 선택

```sh
python3 <이 스킬 폴더>/scripts/project_status.py set <이슈 번호> '작업 중'
python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name setup
python3 <이 스킬 폴더>/scripts/project_status.py check
python3 <이 스킬 폴더>/scripts/project_status.py check --fix
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리, 인증된 `gh` CLI와 저장소·프로젝트 조회 권한. 변경 명령은 프로젝트 쓰기 권한 필요
- 저장소: 기본은 현재 디렉터리, `--repo owner/name`은 하위 명령 앞뒤 모두 허용
- `set <이슈 번호> <상태>`: 연결 프로젝트마다 이슈 등록 및 지정 상태 설정. 공백을 포함한 상태 이름은 따옴표 필수
- `setup`: 기존 선택지의 ID·이름·색·설명 보존, 빠진 기본값만 추가. 모든 보드 뷰의 기존 필터에 완료 제외 조건 추가, 이미 있으면 쓰기 생략. 테이블·로드맵 뷰는 적용 제외
- `check`: 열린 이슈 중 판에 없는 것, 닫힌 이슈인데 완료가 아닌 것, 열린 이슈인데 완료인 것 출력. 다른 저장소 이슈·초안·PR은 검사 제외
- `check --fix`: 판에 없는 열린 이슈 등록 후 `대기`, 열린 이슈의 잘못된 `완료`는 `대기`, 판에 있는 닫힌 이슈는 `완료`로 변경. 그 밖의 상태와 판에 없는 닫힌 이슈는 유지, 같은 값 재쓰기 금지
- 출력: 표준 출력. 종료 코드: 성공·수정 완료 0, 읽기 검사 불일치 1, 프로젝트·필드·선택지 누락 또는 조회·변경 실패 2
- 여러 프로젝트 변경 중 API 실패: 앞서 성공한 변경은 유지, 원인 해결 후 같은 명령 재실행. 현재 상태가 같은 항목의 쓰기 생략
- 단위 시험: `python3 -m pytest <이 스킬 폴더>/tests/test_project_status.py`. pytest 필요, 가짜 `gh` 실행 함수 주입으로 GitHub 호출 없이 검증

## 범위 변경

- 완료 조건의 범위 변경: 이슈 댓글의 남은 작업표 갱신
- 작업표: 남은 작업, 바뀐 완료 조건, 실행·대기·재작업별 시간 추정, 추정 단위. 작업일은 하루 작업 시간 명시

## 닫기

| 경우 | 연결·닫는 방법 |
|---|---|
| PR이 이슈 완료 조건을 충족 | PR에 `Closes: #번호` |
| 관련 작업, 일부 완료 | PR에 `Refs: #번호` |
| 다른 PR로 이미 완료 확인 | 근거 PR과 이유 댓글 뒤 수동 닫기 |
| design | 결정 댓글 뒤 완료 조건을 충족한 PR로 닫기 |
| 안 함 | 이유 한 문장. 중복이면 `#번호와 중복` |

- 독립 추적이 필요 없는 형식, 주석, 죽은 코드, 문서 동기화 정리: 이슈 없이 PR 허용
- 다른 PR로 완료한 이슈 댓글: `완료 근거: #{PR 번호}`, `닫는 이유: {완료 조건을 충족한 이유}`
- `Closes:`와 `Refs:` 판단 기준의 정본. 브랜치·PR 스킬은 이 절만 참조

결정 댓글

```text
## 결정
```
