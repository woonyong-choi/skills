# Git Issue

- 사용자 지시를 먼저 적용. 해당 주제의 사용자 지시가 없으면 작업 대상 저장소의 같은 주제 규칙 파일(예: `AGENTS.md`, `CONTRIBUTING.md`) 적용. 둘 다 없으면 이 스킬 적용. 다른 스킬과 겹치는 규칙은 머리의 연결에 적힌 스킬 중 그 규칙을 정한 스킬 적용
- 범위: 이슈 종류, 라벨, 제목, 본문 틀, 묶음, 상태, 닫기. 브랜치와 PR 흐름(git-branch), PR 본문(git-pull-request), 커밋 형식(git-commit) 제외
- 필요할 때만 읽기: 제목·본문·댓글 작성·검토 → repo-docs; 공통 끝말의 뜻이나 영역 라벨의 scope 단어 → git-commit

## 종류

한 이슈에 종류 하나. 라벨: 종류 라벨 하나, 영역 라벨 하나, 우선순위 라벨 하나.

| 종류 라벨 | 쓰는 때 | 제목 | 예 |
|---|---|---|---|
| `design` | 정해야 할 질문 | `{대상} 결정` | `끊긴 요청 재전송 정책 결정` |
| `build` | 만들 것 확정 | `{대상} {추가/구현/변경}` | `토큰 만료 시 자동 재발급 추가` |
| `bug` | 설계·기대와 다른 동작 | `{대상} {증상} 수정` | `대기 요청 재연결 뒤 중복 전송 수정` |
| `experiment` | 측정·실측 필요 | `{대상} 측정` | `한국어 입력 분류 오류율 측정` |
| `docs` | 문서만 수정 | `{대상} 문서 갱신` | `설치 방법 문서 갱신` |

- 영역 라벨: `area:{scope}`. scope는 커밋 scope 단어 (`area:core`, `area:tui`, `area:repo`)
- 제목: 한글, 공백 포함 Unicode 문자 수 20자 이내, 대상이 맨 앞, 종류는 표의 끝말로 표시. 마침표·물음표 없음. 라벨 이름, 번호 금지
- 이슈 제목 형식·길이의 정본: 이 절. 공통 끝말의 뜻: [git-commit 설명](../git-commit/SKILL.md#설명) 참조. `결정`·`구현`·`측정`은 이슈 전용 끝말

### 제목 검사

- 이슈를 올리기 전 아래 검사 통과 필수. 대상이 맨 앞인지와 bug의 증상 포함 여부는 직접 확인

```sh
python3 <이 스킬 폴더>/scripts/issue_title.py --kind bug <제목 파일>
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리
- 입력: `--kind`는 위 종류 라벨, 제목은 UTF-8 한 줄 파일. 파일 생략 또는 `-`이면 표준 입력, 파일 끝 개행 하나는 제목 길이에서 제외
- 검사: 공백 포함 길이, 종류별 끝말과 끝말 앞 대상 유무. 끝말만 있는 제목·빈 제목·여러 줄은 위반
- 출력: 위반은 표준 출력에 줄 번호 포함, 입력 오류는 표준 오류. 통과 때 출력 없음
- 종료 코드: 통과 0, 위반 1, 입력 오류 2. 원본 수정과 GitHub 호출 없음
- 시험 사례: `python3 -m pytest <이 스킬 폴더>/tests/test_issue_title.py`. pytest 필요, 수정 전 실패·수정 후 통과와 20자 통과·21자 실패 경계 검증

## 본문

- 종류별 틀. 절 이름, 순서 그대로. 내용 없으면 빼는 절: `원인`, `범위 밖`, `관련`만
- 틀 파일: `.github/ISSUE_TEMPLATE/{종류 라벨}.md`. 파일 머리 `---` 사이에 GitHub 틀 머리말 `name: {종류 라벨}`, `about: {쓰는 때}`, `labels: [{종류 라벨}]`
- 제목·본문·댓글: 사람이 쓴 문서처럼 쓰는 공통 규칙 (repo-docs 문체). 본문·댓글은 한국어 문체 절의 자리별 기준
- 저장소 파일 링크: 전체 URL `https://github.com/{소유자}/{저장소}/blob/{기본 브랜치}/{경로}`. 이유: 이슈에서 상대 경로 열기 불가

design

```text
## 질문

{정할 것, `~할지`로 끝나는 명사절}

## 배경

{왜 지금 정해야 하는지 한두 문장}. 관련 설계: [{문서 제목}]({전체 URL})

## 선택지

| 선택지 | 얻는 것 | 잃는 것 |
|---|---|---|
| {선택지} | {얻는 것} | {잃는 것} |

## 정하는 기준

- {기준}

## 관련

- {이슈나 문서 링크}
```

build

```text
## 목표

{끝나면 무엇을 할 수 있는지 한두 문장}

## 따르는 설계

- [{문서 제목}]({전체 URL}#{절})

## 계약

{공개 타입과 함수 시그니처 초안. 계약이 코드에 들어가면 코드 위치로 바꾼다}

## 완료 조건

- [ ] {검증할 수 있는 조건} (확인: `{테스트 이름이나 명령}`)

## 범위 밖

- {하지 않는 것}

## 관련

- {이슈나 문서 링크}
```

bug

```text
## 증상

{무엇이 잘못 보이는지 한 문장}

## 재현

1. {단계}

## 기대 동작

{설계 문서 링크와 해당 규칙}

## 실제 동작

{관측한 동작}

## 환경

| 항목 | 값 |
|---|---|
| 운영체제 | {운영체제} |
| 버전 | {버전} |
| 커밋 | `{커밋}` |

## 원인

{찾은 뒤 채운다}
```

experiment

```text
## 확인할 것

{측정할 것 한 문장}

## 실험 문서

- [{실험}]({design.md 전체 URL})

## 관련

- {이슈나 문서 링크}
```

- `docs` 이슈: build 틀에서 `계약` 절 제외
- 관련 절: 막는 이슈, 막히는 이슈, 상위 이슈, 설계 문서 링크
- 완료 조건: 확인 방법까지. `잘 동작함` 같은 조건 금지

## 공개 웹 링크

- 적용: GitHub 이슈·PR 본문·리뷰·댓글의 파일·문서·코드 위치. 저장소 안 문서끼리의 상대 링크는 적용 제외
- 파일·문서 위치: 짧은 경로나 이름을 링크 글자로 쓴 웹 주소. 코드 줄은 `https://github.com/{소유자}/{저장소}/blob/{커밋 SHA}/{경로}#L{시작}-L{끝}`, 계속 바뀌는 문서는 기본 브랜치 주소 사용. 기본 브랜치는 저장소 조회 결과 사용
- 공개되지 않은 로컬·홈·저장소 밖 작업 폴더(worktree의 `{이름}.wt` 등)·미커밋 폴더(`.local` 등): 링크와 경로 표기 금지. 근거의 존재를 밝혀야 할 때는 `비공개 원자료`처럼 존재만 표시하고 공개 가능한 내용만 본문에 요약
- 경로 경계: 절대·홈·Windows 경로와 file URL은 토큰 시작(줄 시작, 공백, 여는 괄호·대괄호·중괄호·따옴표·백틱·`<` 뒤)에서만 비공개 경로 판정. 상대 경로 낱말 중간의 `/`는 제외, `.local` 경로 요소와 토큰 시작의 `../`는 차단 유지. HTML 닫는 태그는 경로 검사 제외
- worktree 경로: 같은 토큰 시작 경계에서 `{이름}.wt/`로 시작하거나 경로 마디 하나가 정확히 `{이름}.wt`인 경로 차단. 이름은 한 글자 이상, 백틱 안·밖과 링크 대상 모두 적용. `a.wt.md`, `docs/x.wtf/a.md`, `foo.wtx/a`처럼 `.wt` 뒤에 마디 이름이 이어지면 이 규칙 적용 제외
- 비공개 저장소 링크: 같은 저장소의 이슈·PR·리뷰·댓글에서만 허용. 다른 저장소에서 참조 금지
- 이슈·PR·댓글을 올리기 전에 아래 스크립트로 검사, 위반 0개 확인 필수

```sh
python3 <이 스킬 폴더>/scripts/public_links.py --repo <게시 대상 저장소 루트> <본문 파일>
python3 <이 스킬 폴더>/scripts/public_links.py --repo <게시 대상 저장소 루트> --fix <본문 파일>
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리, Git, 인증된 GitHub CLI(`gh`). 원격은 `--remote`로 지정, 기본 origin, 공개 여부와 기본 브랜치는 `gh repo view` 조회
- 입력: UTF-8 파일, 생략 또는 `-`이면 표준 입력. 저장소 상대 경로는 게시 대상 저장소 루트 기준
- 출력: 검사 결과는 표준 출력에 줄 번호 포함. `--fix`는 수정한 본문만 표준 출력, 남은 위반은 표준 오류. 원본 파일 덮어쓰기 금지
- 링크 규칙 진단: `relative repository link: replace with a public web link` 또는 `repository path in code text: replace with a public web link`. HEAD에 있는 저장소 파일의 상대 링크·코드 표기는 공개 웹 링크로 변환 대상, 상대 경로 자체는 게시 금지 대상에서 제외
- 게시 금지 규칙 진단: `private path`, `path outside repository`, `unpublished file` 뒤 `do not publish; summarize without its location`. 비공개 위치는 공개 링크 변환 없이 위치를 뺀 내용만 요약 대상. 다른 비공개 저장소는 `private repository: do not publish; summarize without its address`
- 자동 수정: HEAD에 포함된 저장소 파일만 웹 링크로 변환, 줄 번호가 있으면 현재 HEAD SHA 고정. 비공개 경로·다른 비공개 저장소 주소는 원문 유지와 위반 보고만 수행
- 종료 코드: 통과 또는 모든 위반 수정 0, 남은 위반 1, 입력·Git·공개 여부 조회 실패 2. 수정 결과 재검사 후 게시

## 우선순위

- 열린 이슈: `P0`, `P1`, `P2`, `P3` 중 우선순위 라벨 하나 필수. 이슈 생성 때 추가, 종류·영역 라벨과 함께 사용

| 라벨 | 색 | 기준 |
|---|---|---|
| `P0` | `B60205` | 이미 쓰는 기능의 장애: 데이터 손실, 보안·권한 우회, 같은 작업 두 번 실행, 사용자 몰래 진행, 멈춤·실행 불가 |
| `P1` | `D93F0B` | 프로젝트의 지금 목표(README나 마일스톤에 적힌 핵심 흐름)를 끝까지 동작하지 못하게 하는 문제 |
| `P2` | `FBCA04` | 공개·배포에 꼭 필요함, 또는 README 핵심 사용 경로 또는 저장소의 사용 빈도 기준에 해당하는 기능의 품질 저하 |
| `P3` | `C5DEF5` | 개선, 측정, 정리, 나중에 필요할 때 할 일 |

- 기준 둘 이상: 높은 우선순위
- 막는 이슈: 막히는 이슈 중 가장 높은 우선순위. `design`, `experiment` 이슈는 결정이 막는 작업의 우선순위
- 작업 순서: 높은 우선순위 먼저. 같으면 다른 이슈를 막는 것 먼저. 그것도 같으면 오래된 것 먼저
- 다시 매기기: 막힘 관계 변경, 목표 변경, 장애 새 확인
- 마일스톤: 큰 작업 묶음. 우선순위와 별개

## 묶음과 순서

- 큰 작업(설계 문서 둘 이상 변경, 공개 계약 변경, 이슈 셋 이상): 마일스톤 하나(설명: 목표 한 문장, 성공 기준)
- 나눈 작업: GitHub 하위 이슈. 순서 제약: GitHub 막힘 관계, 기능이 없으면 관련 절에 `막힘: #번호`
- 한 이슈 = 독립적으로 완료·검증·되돌릴 수 있는 사용자 결과 하나. 독립된 결과는 하위 이슈로 분할 (git-branch 작업 단위)

## 상태

상태 표시: GitHub로만. 이슈 본문, 문서에 상태 기록 금지.

| 상태 | 표시 |
|---|---|
| 할 일 | 열림, 담당자 없음 |
| 진행 중 | 담당자 지정 + 작업 브랜치 (git-branch) |
| 막힘 | 막힘 관계 |
| 끝 | 닫힌 이슈(completed) |
| 안 함 | 닫힌 이슈(not planned) + 이유 댓글 |

## 프로젝트 판 상태

- 이슈·PR 등록·상태 이동의 정본: 이 절. 위 상태 절의 열림·담당자·막힘·닫기 표시와 함께 Projects v2의 Status 사용. 사실 상태(repo-docs)·설계 상태(repo-docs-design)는 별도 축, 판의 완료만으로 구현·사용 가능 판정 금지
- 대상: `gh api graphql`로 작업 저장소의 `projectsV2` 조회 후 `--project 번호` 반복으로 선택. 생략 시 연결 프로젝트 전부. 프로젝트 이름·번호 하드코딩 금지
- 연결 프로젝트 없음: 생성 없이 사용자에게 알림. 프로젝트 생성은 사용자 요청 때만
- 상태 기본값: 아래 여섯 값. 저장소 정책이 있으면 그것 우선. 아래 이름은 역할이며 `--status-map '역할=실제 이름'` 반복으로 기존 선택지에 매핑. 대상 프로젝트의 Status 필드 또는 필요한 선택지 없음: 알림 후 상태 변경 중단, 초기 설정은 `setup` 사용

| 상태 | 언제 |
|---|---|
| 대기 | `이슈가 있고 아직 시작 안 함` |
| 작업 중 | `구현·실험을 시작함(담당자 지정과 같은 때)` |
| 검증 중 | `PR이나 결과가 나와 테스트·CI·실제 확인을 기다림` |
| 선택 필요 | `사용자 결정을 기다림` |
| 보류 | `다른 이슈에 막혔거나 미룸` |
| 완료 | `근거와 함께 닫음` |

| 이슈 상태 | 판 역할 대응 |
|---|---|
| 할 일 | 대기 |
| 진행 중 | 구현·실험 중이면 작업 중, 결과 검증 대기면 검증 중 |
| 막힘 | 사용자 결정 대기면 선택 필요, 외부 의존·연기면 보류 |
| 끝 | 근거와 실제 닫힘 확인 후 완료 |
| 안 함 | 취소 이유와 실제 닫힘 확인 후 완료. 구현 완료 의미로 사용 금지 |

- 이슈 생성 직후: 연결 프로젝트에 등록하고 `대기` 설정
- 이슈를 가져와 구현·실험 시작: 담당자 지정과 같은 때 `작업 중` 설정
- PR 생성 또는 결과 제출 후 테스트·CI·실제 확인 대기: `검증 중` 설정
- 사용자 결정 대기: `선택 필요`, 다른 이슈에 막힘 또는 연기: `보류` 설정
- 결정·막힘 해소 후 작업 재개: `작업 중`, 결과의 검증만 남은 경우 `검증 중` 설정
- 근거와 함께 이슈 닫기: `완료` 설정. PR 머지 때 연결 이슈의 실제 닫힘 확인 후 적용, 일부 작업의 `Refs:` 이슈는 현재 단계 유지
- 위 사건마다 아래 `set` 실행 필수. 판에 없는 이슈·PR은 등록 후 상태 변경, 이미 같은 상태면 쓰기 생략
- 완료 항목: Status 값과 항목 유지, 보드 뷰 필터에 `-status:완료` 추가. 열 자체 숨기기는 API 미지원이므로 사람이 완료 열 메뉴의 `Hide from view` 선택

```sh
python3 <이 스킬 폴더>/scripts/project_status.py set <이슈 또는 PR 번호> '작업 중'
python3 <이 스킬 폴더>/scripts/project_status.py --repo owner/name setup
python3 <이 스킬 폴더>/scripts/project_status.py check
python3 <이 스킬 폴더>/scripts/project_status.py check --fix
```

- 실행 조건: Python 3.9 이상, 표준 라이브러리, 인증된 `gh` CLI와 저장소·프로젝트 조회 권한. 변경 명령은 프로젝트 쓰기 권한 필요
- 저장소: 기본은 현재 디렉터리, `--repo owner/name`은 하위 명령 앞뒤 모두 허용
- `set <이슈 또는 PR 번호> <상태>`: 번호로 이슈 또는 PR 조회 후 연결 프로젝트마다 해당 항목 등록 및 지정 상태 설정. 없는 번호는 종료 코드 2, 공백을 포함한 상태 이름은 따옴표 필수
- `--project`·`--status-map`: 하위 명령 앞에 지정. 매핑 값은 중복·빈 값·쉼표·줄바꿈 금지. `set`에는 기본 역할 이름 입력, 실제 이름은 매핑으로 결정
- `setup`: 명시적 초기 설정 요청 때만 실행. 기존 선택지의 ID·이름·색·설명 보존, 빠진 매핑 선택지만 추가. 모든 보드 뷰의 기존 필터에 완료 제외 조건 추가, 이미 있으면 쓰기 생략. 테이블·로드맵 뷰는 적용 제외
- `check`: 열린 이슈 중 판에 없는 것, 닫힌 이슈인데 완료가 아닌 것, 열린 이슈인데 완료인 것 출력. 다른 저장소 이슈·초안·PR은 검사 제외
- `check --fix`: 판에 없는 열린 이슈 등록 후 `대기`, 열린 이슈의 잘못된 `완료`는 `대기`, 판에 있는 닫힌 이슈는 `완료`로 변경. 그 밖의 상태와 판에 없는 닫힌 이슈는 유지, 같은 값 재쓰기 금지
- 출력: 표준 출력. 종료 코드: 성공·수정 완료 0, 읽기 검사 불일치 1, 프로젝트·필드·선택지 누락 또는 조회·변경 실패 2
- 여러 프로젝트 변경 중 API 실패: 앞서 성공한 변경은 유지, 원인 해결 후 같은 명령 재실행. 현재 상태가 같은 항목의 쓰기 생략
- 단위 시험: `python3 -m pytest <이 스킬 폴더>/tests/test_project_status.py`. pytest 필요, 가짜 `gh` 실행 함수 주입으로 GitHub 호출 없이 검증

## 범위 변경

- 완료 조건의 범위 변경: 이슈 댓글의 남은 작업표 갱신
- 작업표: 남은 작업, 바뀐 완료 조건, 실행·대기·재작업별 시간 추정, 추정 단위. 작업일은 하루 작업 시간 명시

## 닫기

| 경우 | 연결·닫는 방법 |
|---|---|
| PR이 이슈 완료 조건을 충족 | PR에 `Closes: #번호` |
| 관련 작업, 일부 완료 | PR에 `Refs: #번호` |
| 다른 PR로 이미 완료 확인 | 근거 PR과 이유 댓글 뒤 수동 닫기 |
| design | 결정 댓글 뒤 완료 조건을 충족한 PR로 닫기 |
| 안 함 | 이유 한 문장. 중복이면 `#번호와 중복` |

- 독립 추적이 필요 없는 형식, 주석, 죽은 코드, 문서 동기화 정리: 이슈 없이 PR 허용
- 다른 PR로 완료한 이슈 댓글: `완료 근거: #{PR 번호}`, `닫는 이유: {완료 조건을 충족한 이유}`
- `Closes:`와 `Refs:` 판단 기준의 정본. 브랜치·PR 스킬은 이 절만 참조

결정 댓글

```text
## 결정

{고른 선택지 한 문장}

## 이유

{정하는 기준에 비춰 한두 문장}

## 반영

- {설계 문서 PR}
- {후속 이슈}
```

- 닫은 이슈 재오픈 금지. 같은 문제 재발 시 새 이슈에 이전 이슈 링크

## 금지

- 한 이슈에 종류 둘 이상, 다른 이슈 작업 섞기
- 우선순위 라벨 없는 열린 이슈, 우선순위 라벨 둘 이상
- 결정 댓글 없이 design 닫기
- 본문, 댓글에 비공개 기록 링크나 내용
- 제목·본문·댓글의 AI 흔적: `Co-Authored-By`, `Generated with`, 로봇 이모지(`U+1F916`), 모델 이름을 붙인 작성 표시, 생성 문구, 세션 링크
