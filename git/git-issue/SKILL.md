# Git 이슈

작업을 완료 조건이 있는 이슈 하나로 만들고, 판 상태로 진행을 추적하다가 근거와 함께 닫는다.

## 과업 연결과 기록

- 과업 연결 명령, 결정 기록 위치, 훅 동작을 확인해야 할 때는 mode `references/hooks.md`를 읽고 그 문서의 연결 명령을 쓴다.
- 코드를 바꾸는 일(기능, 수정, 리팩터링, UI 개선)은 작업 전에 반드시 이슈를 연결한다. 읽기 전용 조사는 그 결과가 후속 작업의 근거가 될 때만 연결한다. 단순한 질의응답은 연결하지 않는다.
- GitHub 원격이 없거나 사용자가 생략하라고 하면 이슈와 판 연결을 건너뛰고, 결과에 그 사실을 보고하고 작업을 계속한다.
- 요청 결과를 기존 이슈의 완료 조건과 결과별로 대조한다. 정해지지 않은 설계 선택은 **repo-docs-design** 스킬이 맡는다.
- 과업은 이슈 하나의 완료 조건으로 추적하는 작업이다. 기존 조건을 모두 채워도 따로 완료할 결과가 남으면 독립 과업이다. 열린 이슈를 다시 쓰거나 새로 만들어 판에 올린 뒤 bind(세션과 과업, 이슈를 로컬에서 잇는 일)한다.
- 기존 결과에 대한 방법 비교, 반례, 설명, 결함 수정, 작은 정리는 같은 과업이다. 같은 저장소나 같은 주제라는 이유만으로 합치지 않는다.
- 목표, 제약, 계획은 이슈 본문에 둔다. 진행 상태는 판 상태로 둔다. 단계별 결정, 근거, 다음 할 일은 저장소의 결정 기록 `.local/decisions/<과업>.tsv`에 둔다. 이슈에 진행 로그 댓글을 달지 않는다.
- 가설을 사실로, 계획을 처리한 일로 올려 적지 않는다.

## 종류

| 종류 | 쓰는 때 | 제목 | 예 |
|---|---|---|---|
| `design` | 정해야 할 질문이 있다 | `{대상} 결정` | `끊긴 요청 재전송 정책 결정` |
| `build` | 만들 것이 정해졌다 | `{대상} {추가/구현/변경/개선/정리/분리}` | `토큰 만료 시 자동 재발급 추가` |
| `bug` | 설계나 기대와 다르게 동작한다 | `{대상} {증상} 수정` | `대기 요청 재연결 뒤 중복 전송 수정` |
| `experiment` | 측정이나 실측이 필요하다 | `{대상} 측정` | `한국어 입력 분류 오류율 측정` |
| `docs` | 문서만 고친다 | `{대상} 문서 갱신` | `설치 방법 문서 갱신` |

- 종류는 제목 끝말과 고른 틀로 구분한다. 라벨은 쓰지 않는다.
- 제목은 한글로, 공백을 포함한 Unicode 문자 20자 이내로 쓴다. 대상을 맨 앞에 두고 종류는 위 표의 끝말로 나타낸다. 마침표, 물음표, 번호를 넣지 않는다.
- 공통 끝말의 뜻은 [git-commit 설명](../git-commit/SKILL.md#설명)을 따른다. `결정`, `구현`, `측정`은 이슈에만 쓰는 끝말이다.
- 제목, 본문, 댓글을 쓰거나 검토하기 전에 repo-docs `references/writing.md`를 반드시 읽는다.

### 제목 검사

게시하기 전에 다음 검사를 반드시 통과시킨다. 대상이 맨 앞에 있는지와 bug 제목에 증상이 들었는지는 직접 확인한다.

```sh
printf '%s\n' '<제목>' | python3 <이 스킬 폴더>/scripts/issue_title.py --kind <종류> -
```

- Python 3.9 이상과 표준 라이브러리로 돈다.
- `--kind`에 종류를 준다. 제목은 표준 입력(`-`이나 생략)이나 UTF-8 한 줄 파일로 준다. 끝 개행 하나를 뺀 길이, 끝말, 대상을 검사한다. 빈 제목, 여러 줄, 끝말만 있는 제목은 위반이다.
- 통과하면 아무것도 출력하지 않고 0으로 끝난다. 위반은 줄 번호와 함께 표준 출력에 내고 1로 끝난다. 입력 오류는 표준 오류에 내고 2로 끝난다. 원본을 고치거나 GitHub를 부르지 않는다.

## 본문

- 종류별 틀의 코드 블록 안을 채워 `gh issue create --body-file -`로 표준 입력에 넘긴다. 임시 파일을 만들지 않는다.
- 절 이름과 순서를 그대로 둔다. 올리기 전에 주석과 해당 없는 절을 지운다.
- 틀의 정본은 아래 파일뿐이다. 저장소별 `.github` 틀이나 계정의 `.github` 저장소를 만들지 않는다.
- 이슈끼리는 GitHub 하위 이슈와 막힘 관계로 잇는다.

| 종류 | 틀 |
|---|---|
| design | [references/design.md](references/design.md) |
| build | [references/build.md](references/build.md) |
| bug | [references/bug.md](references/bug.md) |
| experiment | [references/experiment.md](references/experiment.md) |
| docs | [references/docs.md](references/docs.md) |

- 이슈에 다는 댓글은 다음뿐이다. 모두 `gh issue comment --body-file -`로 올린다.
  - 검토·검증 피드백 댓글. 아래 공개 피드백 형식을 따른다.
  - 결정 댓글과 범위 변경 댓글. 틀을 채워 올린다.
  - 질문 댓글. 보류로 옮길 때 올린다. 자율 실행이 아니어도 같다. 질문 하나, 그동안 적용한 기본값, `재개 조건: <조건>` 줄을 적는다.
  - 완료 근거와 닫는 이유 댓글. [닫기](#닫기) 절과 머지 없이 닫는 경우에 단다.
  - 다시 연 근거 댓글. 잘못 판정한 근거와 남은 조건을 적는다.
  - 착수하지 않은 이유 댓글. AI가 만든 이슈를 같은 세션에서 착수하지 않을 때 한 줄로 단다.
- 검토·검증 피드백은 [git-pull-request 공개 피드백 형식](../git-pull-request/references/review.md#공개-피드백-형식)을 반드시 읽고 따른다. 일반 댓글, 줄 단위 댓글, 리뷰 본문에 같은 형식을 적용한다.
- 위 피드백 외의 댓글은 개조식 명사 끝으로 쓴다. 처리 확인 항목은 체크박스와 증거(경로, #번호, 링크)로 쓴다. 주석과 해당 없는 줄은 지운다.

## 공개 웹 링크

이슈, PR, 리뷰, 댓글을 쓰거나 게시하기 전에 [references/public-links.md](references/public-links.md)의 규칙과 검사 명령을 반드시 읽고 따른다.

## 다음 작업

다음 순서로 고른다.

1. 사용자가 지정한 이슈를 고른다.
2. 판의 대기 열에서 맨 위 이슈를 고른다. 판 순서가 우선순위다. 열린 이슈에 막힌 이슈는 건너뛴다. 대기 이슈는 `python3 <이 스킬 폴더>/scripts/project_status.py queue`가 판 순서대로 보여 준다.
3. 판이 없으면 [references/project-status.md](references/project-status.md#새-저장소)의 새 저장소 절차로 판을 만든 뒤 고른다.

판에 이슈를 올리거나 판 순서를 정할 때는 다음 기준을 쓴다. 위에 있을수록 판의 위에 둔다.

1. 이미 쓰는 기능의 장애를 가장 먼저 한다. 데이터 손실, 보안과 권한 우회, 같은 작업의 두 번 실행, 사용자 몰래 진행, 멈춤과 실행 불가가 여기에 든다.
2. 프로젝트의 지금 목표(README나 상위 이슈에 적힌 핵심 흐름)가 끝까지 동작하지 못하게 하는 문제를 한다.
3. 공개나 배포에 꼭 필요한 일을 한다. README 핵심 사용 경로나 저장소의 사용 빈도 기준에 드는 기능의 품질 저하도 여기에 든다.
4. 개선, 측정, 정리, 나중에 필요할 때 할 일은 마지막에 한다.

## 묶음과 순서

- 큰 작업(설계 문서 둘 이상 변경, 공개 계약 변경, 이슈 셋 이상)은 상위 이슈 하나 아래 GitHub 하위 이슈로 나눈다. 순서 제약은 GitHub 막힘 관계로 건다.
- 상위 이슈는 작업 종류의 틀을 쓰고, 완료 조건은 `- [ ] 하위 이슈 전부 완료` 한 줄로 둔다. 하위 이슈 목록을 본문에 적지 않는다.
- 이슈 하나는 독립적으로 완료하고 검증하고 되돌릴 수 있는 사용자 결과 하나다. 독립된 결과는 하위 이슈로 나눈다([git-branch 작업 단위](../git-branch/SKILL.md#작업-단위)).

## 프로젝트 판 상태

판은 저장소에 연결한 GitHub Projects v2 보드다. 이슈를 만들거나 착수하거나 결과를 제출할 때, 결정 대기, 막힘, 재개, 닫기 때, PR을 만들거나 머지할 때, 판을 처음 설정하거나 검사할 때는 그 전에 [references/project-status.md](references/project-status.md)를 반드시 읽는다.

상태(대기, 진행, 검토, 보류, 완료)마다 들어가는 조건, 머무는 동안 할 일, 나가는 조건, 닫는 기준, 사건별 등록과 상태 이동, 실패 처리의 정본은 그 문서다. 이슈 본문이나 문서에 현재 상태를 겹쳐 적지 않는다.

## 범위 변경

- 완료 조건은 사용자 결과마다 관측이나 근거와 잇는다. 구현 수단이나 검사 명령으로 결과를 대신하지 않는다.
- 완료 조건의 범위를 바꾸면 [references/scope-change.md](references/scope-change.md) 틀로 댓글을 단다. 시간 추정은 적지 않는다.

## 닫기

| 경우 | 잇는 방법과 닫는 방법 |
|---|---|
| PR로 이슈 완료 조건을 모두 채우고 체크했다 | PR과 커밋에 `Closes #번호`를 쓴다 |
| 관련 작업이거나 일부만 끝냈다 | PR과 커밋에 `Refs #번호`를 쓴다 |
| 다른 PR로 이미 끝났다 | `완료 근거: #{PR 번호}`, `닫는 이유: {조건 충족 이유}` 댓글을 단 뒤 직접 닫는다 |
| 저장소 추적 파일 변경 없이 GitHub 메타데이터만 고쳤다 | [프로젝트 판 닫는 기준](references/project-status.md#닫는-기준)의 재조회 근거와 닫는 이유 댓글을 남긴 뒤 직접 닫는다 |
| 사용자가 명시적으로 승인한 메시지 전용 이력 재작성을 끝냈다 | [프로젝트 판 닫는 기준](references/project-status.md#닫는-기준)의 원본 보존·전후 객체 대조·원격 확인 근거를 남긴 뒤 직접 닫는다 |
| design 이슈 | [references/decision.md](references/decision.md) 결정 댓글을 단 뒤 반영 PR로 닫는다. 결정으로 생긴 구현 조건은 후속 build 이슈의 완료 조건이 된다 |

- 완료와 안 함의 닫는 기준은 [references/project-status.md](references/project-status.md#닫는-기준)를 따른다.
- 정상 완료 뒤 같은 문제가 다시 생기면 새 이슈를 만들고 이전 이슈 링크를 건다.

## 하지 않는 것

- 한 이슈에 종류를 둘 이상 담거나 다른 이슈의 작업을 섞지 않는다.
- 완료 조건 없는 이슈를 만들지 않는다.
- 실제 근거 없이 완료 조건을 체크하지 않는다.
- 결정 댓글 없이 design 이슈를 닫지 않는다.
- 본문과 댓글에 비공개 기록의 링크나 내용을 넣지 않는다.
- 작성 표시는 [git-commit 하지 않는 것](../git-commit/SKILL.md#하지-않는-것)을 따른다.

## 답변

- 만들거나 고친 이슈의 번호, 제목, 주소를 적는다.
- 판 상태를 바꿨으면 바뀐 상태를 적는다. 판 연결을 건너뛰었으면 그 이유를 적는다.
- 닫았으면 닫은 방법과 근거를 적는다.

## 구분

- 브랜치와 PR 흐름은 [git-branch](../git-branch/SKILL.md)가 맡는다.
- PR 본문은 [git-pull-request](../git-pull-request/SKILL.md)가 맡는다.
- 커밋 형식은 [git-commit](../git-commit/SKILL.md)이 맡는다.
